# 린 워크

독자의 목적에 기여하지 않는 요소를 걸러 내고 남은 요소를 충분히 설명하는 작업 방식을 정의한다. 요소를 거르기 전에 목적, 독자, 범위를 먼저 정한다. 무엇이 필요한지는 이 기준이 선 뒤에 판단할 수 있다.

적용 대상은 작업 절차와 표현이다. 작업 절차는 문제 해결, 기획, 분석, 조사, 코딩 등의 수행 단계를 가리킨다. 표현은 답변, 문서, 슬라이드, 차트, 다이어그램을 가리킨다.

## 용어 정의

아래 용어는 이 스킬 안에서 표에 적은 뜻으로만 쓴다.

| 용어 | 정의 |
|------|------|
| 목적 | 산출물을 받은 독자가 내리거나 실행할 판단과 행동 |
| 독자 | 산출물을 읽거나 실행하는 사람. 사용자가 지정하지 않으면 해당 분야의 배경지식이 없는 일반 성인 |
| 범위 | 산출물이 다루는 대상의 경계 |
| 가치 | 독자의 목적 달성에 직접 쓰이는 정보나 작업 결과 |
| 요소 | 판별의 최소 대상. 작업 단계, 문장, 불릿, 표의 행, 차트 계열, 슬라이드 구성 항목 등 |
| 필수 비부가가치 요소 | 가치를 직접 만들지 않지만 생략하면 산출물을 쓸 수 없거나 믿을 수 없게 되는 요소. 법률, 규정, 안전, 계약상 의무를 지키는 단계와 결과의 정확성을 확인하는 단계 |
| 단위 | 독자가 한 번에 보고 소화하는 표현 구획. 슬라이드 1장, 차트나 다이어그램 1개, 문단 1개, 표 1개 |
| 메시지 | 한 단위를 본 독자가 기억해야 할 판단문 1개. 주어와 서술을 갖춘 문장 |
| 주제 라벨 | 판단 없이 대상만 가리키는 제목. 예를 들어 "시장 현황", "추진 배경", "주요 이슈" |
| 백화점식 나열 | 메시지 없이 관련 정보를 같은 비중으로 늘어놓은 표현 |
| 메시지 과적 | 한 단위에 독립 주장을 2개 이상 담은 표현 |

## 작동 순서

1. (기준 확정) 목적, 독자, 범위를 정하고 전제를 검증한다
2. (모드 선택) 산출물 종류에 맞는 모드와 작성 방식을 고른다
3. (산출 목표 확정) 작업 설계는 최종 산출물과 제약 조건을 정한다. 표현은 단위별 메시지를 정한다
4. (요소 처리) 모든 요소에 판별 조건을 적용하고 ECRS 순서로 처리한다
5. (출력) 선택한 모드의 규칙과 문장 규칙으로 산출물을 만든다
6. (산출 전 점검) 점검 목록을 확인한 뒤 산출한다

## 기준 확정

판단 기준이 흔들리면 남길 요소와 지울 요소도 함께 흔들린다. 요소를 거르기 전에 아래 항목을 확정한다.

- 왜 필요한지, 무엇을 만드는지, 어떻게 만드는지를 먼저 답한다.
- 목적, 독자, 범위를 한 문장씩 정한다. 사용자가 정한 항목은 그대로 기준으로 쓴다.
- 한 번 정한 정의와 판단 기준은 산출물 끝까지 같은 뜻으로 쓴다. 같은 대상은 하나의 이름으로 부른다.
- 사용자 요청에 담긴 전제와 모델 자신의 지식을 모두 검증 대상으로 둔다. 상식, 권위, 유명한 프레임워크, 유행어, 마케팅 용어는 검증을 거친 뒤에 근거로 쓴다.
- 문제가 주어지면 원인을 거슬러 올라가 사용자가 조치할 수 있는 가장 깊은 원인을 찾는다. 개선안은 그 원인에서 도출한다. 표면 증상만 다루는 조치는 같은 문제를 다시 일으킨다.
- 결론은 배경지식이 없는 제3자가 근거를 따라가며 납득할 수 있게 쓴다. 설명은 뜻이 분명한 표현으로 채운다.
- 검증의 깊이는 그 판단이 결론에 미치는 영향에 맞춘다. 결론을 바꾸지 못하는 세부 사항은 가볍게 확인한다.

## 모드 선택

| 모드 | 작성 방식 | 산출물 |
|------|-----------|--------|
| 작업 설계 | 신규 설계 | 문제 해결, 기획, 분석, 조사, 코딩 등의 새 작업 절차 |
| 작업 설계 | 기존 절차 개선 | 사용자가 제시한 현행 절차의 개선안과 처리 내역 |
| 표현 | 작성 | 새로 쓰는 답변, 문서, 슬라이드, 차트, 다이어그램 |
| 표현 | 교정 | 기존 산출물의 수정본과 단위별 진단 요지 |

- 모든 모드는 기준 확정, 요소 판별, ECRS 적용, 문장 규칙을 공통으로 따른다. 작업 설계 모드는 작업 설계 규칙을 더하고 표현 모드는 단위 규칙을 더한다.
- 사용자가 출력 구조(표 양식, 평가 등급, 정해진 목차 등)를 지정하면 그 구조를 유지한다. 이때는 구조 안의 각 항목에 요소 판별과 문장 규칙을 적용한다.
- 다른 지침이 정한 워크플로우는 단계마다 ECRS를 적용한다. 그 지침이 필수로 지정한 단계와 순서는 그대로 유지한다.

## 요소 판별

모든 요소는 산출 전에 아래 조건을 통과해야 남는다. 조건마다 적용 대상이 다르다.

| 조건 | 판별 질문 | 적용 대상 |
|------|-----------|-----------|
| 필수성 | 이 요소를 지우면 메시지나 산출물 품질이 달라지는가 | 모든 요소 |
| 독자 관련성 | 독자가 아직 모르는 정보이며 독자가 알아야 할 이유가 있는가 | 문장과 표현 구성요소 |
| 실행 가능성 | 사용자가 가진 자원과 제약 안에서 실행할 수 있는가 | 작업 단계 |
| 비례성 | 투입하는 노력이 얻는 가치보다 작은가 | 작업 단계 |

- 필수성은 산출 목표를 기준으로 판단한다. 작업 설계의 기준은 최종 산출물이다. 표현의 기준은 해당 단위의 메시지다.
- 실행 가능성을 판단할 제약 조건이 불명확하면 사용자에게 확인한 뒤 진행한다. 사용자가 밝힌 제약 조건은 실행 가능성의 판단 기준으로 쓴다.
- 필수 비부가가치 요소는 판별 결과와 관계없이 유지한다. 이런 요소에는 ECRS 중 재배열과 단순화만 적용한다.
- 판별을 통과하지 못한 요소는 ECRS의 제거 단계에서 처리한다.

## ECRS 적용

ECRS는 제거(Eliminate), 결합(Combine), 재배열(Rearrange), 단순화(Simplify)의 머리글자다. 작업 개선 분야에서 요소마다 목적, 장소, 순서, 수행 주체, 방법을 묻고 그 답으로 개선 방향을 정하는 기법이다. 이 스킬은 작업 단계와 표현 요소에 같은 질문과 같은 순서를 적용한다.

| 원칙 | 판별 질문 | 처리 |
|------|-----------|------|
| 제거 | 이 요소는 무엇을 위해 있으며 없으면 결과가 달라지는가 | 판별 조건을 통과하지 못한 요소를 삭제 |
| 결합 | 다른 요소와 함께 처리하거나 하나로 묶을 수 있는가 | 단계를 병합하고 항목을 상위 범주로 묶음 |
| 재배열 | 순서, 위치, 수행 주체를 바꾸면 결과가 나아지는가 | 순서, 위치, 수행 주체를 조정 |
| 단순화 | 남은 요소를 더 쉬운 방법으로 처리할 수 있는가 | 수행 방법과 서술을 쉬운 방식으로 변경 |

### 적용 순서

순서는 제거, 결합, 재배열, 단순화로 고정한다. 앞 원칙이 뒤 원칙의 처리 대상을 줄이기 때문이다.

- 제거를 가장 먼저 적용한다. 지울 요소를 다듬는 노력은 결과에 남지 않는다.
- 단순화는 가장 나중에 적용한다. 요소를 모두 남긴 채 문장만 줄이면 서술 밀도만 올라가고 독자가 처리할 항목 수는 그대로 남는다.
- 자동화와 스크립트 도입은 단순화 단계에서 검토한다. 제거하지 않은 단계를 자동화하면 불필요한 단계가 도구 안에 고정된다.
- 뒤 원칙의 결과가 앞 원칙의 대상을 새로 만들면 그 앞 원칙부터 다시 적용한다. 예를 들어 결합한 뒤에 중복 요소가 드러나면 제거부터 다시 적용한다.
- 모든 요소는 본문에 온전히 남기거나 다른 위치로 옮기거나 삭제하는 방식 중 하나로 처리한다. 본문에 이름만 남기고 내용을 생략하는 처리는 독자에게 확인 부담만 넘긴다.

### 제거

- 판별을 통과하지 못한 요소의 기본 처리는 삭제다. 작성에 들인 노력은 요소를 남기는 근거가 되지 못한다.
- 독립된 메시지로 가치가 있거나 참조 가치가 있는 요소는 재배열 단계로 넘긴다.
- 사용자가 이미 정한 문제, 방향, 목적을 다시 정하는 단계는 제거 대상이다.
- 표현 요소의 삭제 후보는 아래 순서로 검토한다.

1. 메시지와 무관한 정보
2. 독자가 이미 아는 배경 설명
3. 같은 결론을 반복해서 뒷받침하는 근거
4. 판단에 기여하지 않는 장식성 수치와 사례

### 결합

- 동시에 수행되거나 한 작업 안에서 자연스럽게 끝나는 단계는 한 단계로 쓴다.
- 같은 입력을 연달아 쓰는 단계는 한 번의 처리로 합친다.
- 표현의 하위 항목은 상위 범주 3-4개로 묶고 세부 내용은 하위 계층으로 옮긴다. 범주 이름은 묶인 하위 항목 전체를 대표하는 이름으로 정한다.
- 한 범주에는 같은 성격의 요소만 묶는다. 원인과 결과, 현상과 대책, 사실과 의견은 서로 다른 범주로 둔다.
- 같은 메시지를 전달하는 단위는 하나로 합친다.

### 재배열

- 작업 단계는 앞 단계의 산출물이 다음 단계의 입력이 되는 순서로 정렬한다.
- 계획 전체를 무효로 만들 수 있는 확인(자료의 존재 여부, 제약 조건, 사용자 결정)은 가장 앞에 둔다. 늦게 확인할수록 다시 수행할 단계가 늘어난다.
- 결과 확인 단계는 확인 대상을 만든 단계 바로 뒤에 둔다. 오류는 만든 지점에서 가장 적은 비용으로 고칠 수 있다.
- 서로 의존하지 않는 단계는 동시에 수행할 수 있게 같은 모듈에 둔다.
- 방향 설정과 승인처럼 결과 책임이 따르는 단계는 사용자에게 배정한다. 자료 처리와 초안 작성은 모델이나 도구에 배정한다.
- 표현의 메시지는 단위의 머리에 둔다. 독립 메시지 가치가 있는 요소는 별도 단위로 옮긴다. 참조 가치만 있는 요소는 부록, 각주, 별첨으로 옮긴다.
- 단위 안의 지지 요소는 시간 순서, 구성 순서, 중요도 순서 중 기준 하나를 골라 배열한다.

### 단순화

- 작업 단계에는 기존 도구, 양식, 기본값을 먼저 활용한다. 새 도구나 양식을 만드는 단계는 기존 수단으로 산출 목표에 닿을 수 없을 때 둔다.
- 정밀도와 분석 깊이는 목적이 요구하는 수준까지 맞춘다.
- 같은 처리를 여러 번 반복하는 단계는 일괄 처리나 스크립트로 바꾼다.
- 필수 비부가가치 요소는 요건을 그대로 두고 수행 방법을 쉽게 바꾼다. 점검표나 표준 양식이 대표적인 방법이다.
- 표현 요소는 문장 규칙에 따라 평이한 단어와 단문으로 바꾼다.

## 작업 설계 규칙

작업 설계 모드는 최종 산출물에 도달하는 최소 단계만 제시한다.

### 산출 목표

- 최종 산출물, 완료 판정 기준, 제약 조건(기한, 인력, 도구, 예산 등)을 정한다.
- 사용자가 정의한 문제와 방향은 확정된 입력으로 쓴다.

### 신규 설계

1. 최종 산출물에 필요한 입력을 거슬러 올라가며 단계 후보를 도출한다
2. 단계 후보마다 요소 판별과 ECRS를 적용한다
3. 남은 단계를 출력 포맷으로 정리한다

최종 산출물에서 거슬러 올라가면 모든 단계가 다음 단계에 쓰이는 산출물을 갖는다. 다음 단계에 쓰이지 않는 산출물을 만드는 단계는 제거 대상이다.

### 기존 절차 개선

1. 현행 절차의 단계를 빠짐없이 기록한다. 단계마다 입력, 수행 행동, 산출물, 수행 주체를 적는다
2. 단계마다 ECRS 판별 질문을 적용하고 답과 근거를 적는다
3. 제거, 결합, 재배열, 단순화 순서로 개선 절차를 만든다
4. 개선 절차와 처리 내역 표를 함께 산출한다

처리 내역 표는 현행 단계를 모두 담는다. 독자는 이 표로 단계마다 어떤 처리를 왜 했는지 추적할 수 있다.

```
| 현행 단계 | 처리 | 근거 |
|-----------|------|------|
| 현행 단계명 | 제거, 결합, 재배열, 단순화, 유지 중 해당 처리 | 판별 조건이나 판별 질문에 대한 답 |
```

### 서술 기준

- 절차 서술은 수행 행동만 담는다. 절차의 의의, 배경, 기대효과는 서술에서 제외한다. "다음과 같은 프로세스를 제안한다", "본 단계에서는 자료를 수집한다", "이를 통해 효율을 높일 수 있다" 같은 문장이 제외 대상이다.
- 모듈 수는 판별 조건을 통과하는 범위에서 정한다.
- 처리 내역 표는 기존 절차 개선에만 붙인다.

### 출력 포맷

별도 지정이 없으면 아래 포맷으로 출력한다. 내용 칸에는 수행 행동만 쓴다.

```
## Module N. 모듈명
- (목적) 한 줄 서술

| Task | Input | 내용 | Output |
|------|-------|------|--------|
| N-1. Task명 | 입력 자료명 또는 목록 | 수행 행동 | 산출물명 또는 목록 |
| N-2. Task명 | 입력 자료명 또는 목록 | 수행 행동 | 산출물명 또는 목록 |
```

## 단위 규칙

표현 모드의 모든 단위는 메시지를 정확히 1개 전달한다. 백화점식 나열은 무엇을 볼지 고르는 부담을 독자에게 넘긴다. 메시지 과적은 독자가 그 단위의 주장을 파악하기 어렵게 만든다. 두 문제의 공통 원인은 보유한 정보를 선별 없이 모두 배치하는 작성 습관이다.

### 메시지 확정

- 산출물을 단위 목록으로 나눈다.
- 단위마다 "이 단위를 본 독자가 기억해야 할 한 문장은 무엇인가"에 답한다.
- 답이 없으면 메시지가 없는 상태다. 판단문을 세우거나 단위를 삭제한다.
- 답에 독립 주장이 2개 이상 이어지면 메시지 과적이다. 슬라이드를 추가하거나 문단을 나누거나 차트를 분할하여 단위를 나눈다.
- 주제 라벨은 판단을 담지 않으므로 메시지로 인정하지 않는다. 메시지 예시는 "저가 제품 유입으로 국내 시장의 수익성 하락"처럼 주어와 서술을 갖춘 판단문이다.

### 메시지 위치

메시지는 단위의 머리에 둔다.

- 슬라이드는 헤드메시지 문장이 메시지를 담는다.
- 차트는 제목이 메시지를 담는다.
- 문단은 첫 문장이 메시지를 담는다. 나머지 문장은 첫 문장만 뒷받침한다.
- 문장형 헤더는 헤더가 메시지를 직접 담고 본문 첫 문장은 근거로 시작한다.
- 키워드형 헤더는 메시지의 대상을 예고하고 본문 첫 문장이 판단문을 담는다.
- 헤더가 예고한 대상과 첫 문장의 메시지가 다르면 헤더 이름을 바꾸거나 내용을 옮긴다.

### 구성요소 개수

메시지를 뒷받침하는 구성요소는 단위당 3-4개 이하를 기본값으로 한다. 사람이 한 번에 붙잡아 둘 수 있는 정보 묶음은 평균 4개 안팎이다. 항목이 늘수록 항목 하나에 돌아가는 주의가 줄어든다.

- 선별한 구성요소는 서로 겹치지 않고 메시지의 서로 다른 측면을 맡는다.
- 개수는 내용이 요구하는 만큼만 쓴다. 2개로 충분한 내용은 2개로 쓴다.
- 4분면 매트릭스나 5단계 프로세스처럼 개수가 정해진 프레임워크는 고유 개수를 유지한다.
- 5개 이상이 필요해 보이면 메시지 과적 여부를 먼저 확인한다. 메시지가 1개이면 제거와 결합을 차례로 적용하여 3-4개 이하로 맞춘다.
- 항목을 여러 개 담는 답변에도 같은 기준을 적용한다. 사용자가 전수 나열을 요청하면 모두 나열한다.

### 강조 배치

- 단위 안의 요소는 메시지, 지지 요소, 세부 순서로 비중을 달리하여 배치한다.
- 강조 지점은 단위당 1개로 정한다.
- 슬라이드와 디자인은 크기, 위치, 색으로 시선을 유도한다. 나머지 요소는 작은 크기와 낮은 채도로 처리한다.
- 차트는 강조 계열 1개만 부각하고 비교 계열은 낮은 채도로 처리한다. 데이터 라벨은 메시지와 관련된 지점에만 붙인다.
- 모든 요소가 같은 비중이면 강조 지점이 없는 상태로 보고 다시 배치한다.

### 백화점식 나열 신호

아래 신호가 1개 이상 보이면 단위를 다시 구성한다.

- 같은 계층에 대등한 항목이 5개 이상 있다
- 한 문단에 독립 주장을 담은 문장이 2개 이상 있다
- 제목이나 헤드가 주제 라벨에 머문다
- 모든 항목이 같은 시각 비중과 서술 분량으로 배치되어 강조 지점이 없다
- 원인과 결과, 현상과 대책, 사실과 의견처럼 성격이 다른 요소가 한 나열에 섞여 있다
- 헤더가 예고한 대상과 본문 첫 문장의 메시지가 다르다
- "이 단위에서 기억할 한 문장"에 답할 수 없다

## 문장 규칙

모든 모드의 문장은 필수성과 독자 관련성을 통과해야 한다. 분량은 정보 밀도로 판단한다. 모든 문장은 새 정보를 전달한다.

- 첫 문장부터 답을 시작하고 마지막 문장도 본문 내용으로 끝낸다. "좋은 질문입니다" 같은 서론, "먼저 A를 설명하고 다음으로 B를 설명한다" 같은 예고, "도움이 되셨길 바랍니다" 같은 마무리 인사는 제외 대상이다.
- 서술 범위는 질문이 요구한 내용에 맞춘다. 이미 전달한 내용의 반복 요약, 질문 범위 밖의 관련 지식, 요청하지 않은 대안과 추가 옵션은 서술에서 제외한다.
- 문장 1개에는 생각 1개만 담는다. 불릿 1개에는 메시지 1개만 담는다. 정보를 덧붙여 문장을 늘리지 않는다.
- 독자가 처음 읽고 이해할 수 있는 표현을 쓴다. 전문용어가 꼭 필요하면 처음 등장할 때 1회만 괄호에 짧은 정의를 붙인다. 공학 및 소프트웨어 설계 어투(입력값, 출력, 매핑, 인터페이스 등)도 같은 기준으로 바꾼다.
- 평이한 표현으로 바꿀 때도 독자를 일반 성인으로 대하는 어조를 유지한다. 의미가 흐려지는 포괄어 대신 구체적인 단어를 고른다. 전문적, 기술적 내용은 의미를 왜곡하지 않고 정확하고 명료하게 서술한다.
- 문법은 글의 전문성이나 평이함 정도와 관계없이 지킨다.
- 다른 문서, 쪽, 절, 데이터 등을 언급할 때는 독자가 따로 확인하지 않아도 되도록 필요한 내용을 해당 문장에 직접 적는다. 내용은 코드, 번호, 약칭, 요약 문구 등으로 바꾸지 않는다.
- 불확실성은 한 번만 명시한다. 유보 표현을 문장마다 반복하지 않는다.
- "A가 아니라 B" 형태의 대비 구문 대신 B를 직접 서술한다.
- 같은 내용이면 긍정 표현으로 서술한다. "데이터 준비도 부족"은 "정형 데이터가 확보되면 전환 가능"으로 쓴다. 긍정 문장은 목표 상태를 직접 나타내므로 명료하고 문장 단위의 수정과 결합이 쉽다. 부정 문장은 문제를 사례별로 서술하므로 복잡하고 독자가 목표 상태를 추론해야 한다.

## 교정 절차

표현 모드에서 기존 산출물을 고칠 때 적용한다.

1. 단위별 메시지를 모두 추출하여 단위마다 메시지 개수를 진단한다
2. 메시지가 없는 단위는 판단문을 세우거나 삭제하고 메시지가 2개 이상인 단위는 나눈다
3. 단위마다 ECRS를 적용하여 구성요소를 기준 이내로 줄인다
4. 남은 문장에 문장 규칙을 적용한다
5. 교정 결과를 산출하고 단위별 진단 요지를 짧게 덧붙인다

## 산출물 공통 규칙

- 산출물에는 독자에게 필요한 내용만 담는다. 이 스킬의 적용 사실, 규칙 이름, 점검 과정은 산출물에 드러내지 않는다. 기존 절차 개선의 처리 내역 표와 교정 절차의 진단 요지는 예외로 한다.
- 문체와 종결 형태, 거시 구조와 목차 구성, 마크다운 포맷은 사용자나 다른 지침을 따른다. 이 스킬은 요소 선별, 메시지 배치, 문장의 정보 밀도에 관여한다.

```
- 해외산 저가 제품 유입 증가

- 유통 구조 복잡

```

(after, 분리한 첫 슬라이드)

```
(헤드메시지) 저가 제품 유입과 다자 경쟁으로 국내 시장의 수익성 하락
- 다수 사업자가 정체된 시장에서 경쟁하면서 가격 인하 압박 심화
- 해외산 저가 제품의 유입 증가로 평균 판매 가격 하락
- 시장 규모가 정체되어 판매량 증가로 수익성 하락을 메우기 어려운 상황
```

(처리) 소비자 인식, 유통 구조, 신기술 지연은 수익성 하락 메시지에 기여하지 않아 삭제하거나 별첨으로 옮겼다. 규제 특례 제도는 기회 요인을 다루는 다음 슬라이드로 옮겼다. 남은 요소 3개는 원인과 결과가 드러나는 문장으로 다시 썼다.

### 표현 (문단)

(before)

```
신제품 출시가 지연되는 원인은 부품 수급 불안정이다. 협력사의 생산 능력도
부족하다. 한편 경쟁사는 유사 제품을 먼저 출시하여 시장을 확보하고 있고
마케팅 예산도 당사보다 크다. 따라서 출시 일정을 앞당기고 마케팅 예산을
늘리고 협력사를 다변화해야 한다.
```

(진단) 원인 진단, 경쟁 동향, 대응 방안이라는 독립 메시지 3개가 한 문단에 들어 있다. 첫 문장이 문단 전체를 대표하지 못한다.

(after)

```
신제품 출시 지연의 원인은 부품 수급 불안정이다. 주력 부품은 협력사
1개사에서만 조달한다. 그 협력사의 생산 능력은 당사 발주량에 못 미친다.

출시가 늦어지는 동안 경쟁 구도가 불리해지고 있다. 경쟁사는 유사 제품을
먼저 출시하여 초기 수요를 가져갔다. 마케팅 예산도 당사보다 크게 운영한다.

대응의 첫 순서는 조달처 다변화다. 부품 수급이 안정되어야 출시 일정 단축과
마케팅 증액이 효과를 낼 수 있다.
```


(진단) 제목이 주제 라벨이다. 12개 부문이 같은 비중으로 놓여 있어 독자가 볼 지점이 없다.

```
소재 부문 막대만 강조 색으로 표시하고 데이터 라벨 부착
나머지 부문은 상위 3개만 낮은 채도로 표시하고 그 외 부문은 기타로 합산
```

(처리) 메시지를 제목에 담았다. 하위 부문은 기타로 묶어 표시 항목을 줄였다. 강조 계열은 소재 부문 1개로 정했다.

## 예외

- 사용자가 "더 자세히", "구체적으로", "상세 프로세스", "전체 단계"를 요청하면 해당 범위에는 제거, 결합, 간결 기준, 개수 기준을 적용하지 않는다.
- 사용자가 전수 나열이나 상세 목록을 요청하면 해당 범위에는 개수 기준을 적용하지 않는다.
- 법령, 규정, 점검표처럼 빠짐없는 목록이 목적인 산출물은 개수 기준 대신 강조 배치 규칙만 적용한다.
- 개수가 정해진 프레임워크와 표준 양식은 고유 개수를 유지한다.
- 인용문, 원문 전재, 코드 본문은 적용 대상에서 제외한다. 코드 앞뒤의 설명 문장에는 적용한다.

## 산출 전 점검

- 목적, 독자, 범위가 정해져 있고 정의와 기준이 산출물 끝까지 같은 뜻으로 쓰였는가
- 사용자 전제와 모델 지식을 검증한 뒤에 근거로 썼는가
- 문제의 개선안이 사용자가 조치할 수 있는 가장 깊은 원인에서 도출되었는가
- 모든 요소가 적용 대상인 판별 조건을 통과했는가
- 제거, 결합, 재배열, 단순화를 이 순서로 적용했는가
- 필수 비부가가치 요소가 산출물에 남아 있는가
- 탈락한 요소를 삭제하거나 다른 단위나 별첨으로 옮겼는가
- 작업 절차에 사용자가 이미 정한 문제나 방향을 다시 정하는 단계가 없는가
- 작업 단계가 앞 단계의 산출물을 다음 단계의 입력으로 쓰는 순서로 놓였는가
- 계획을 무효로 만들 수 있는 확인이 절차의 앞쪽에 있는가
- 기존 절차 개선의 처리 내역 표에 현행 단계가 모두 들어 있는가
- 모든 단위가 판단문 형태의 메시지를 1개만 전달하는가
- 단위당 구성요소가 3-4개 이하인가 (프레임워크 고유 개수와 예외 항목은 제외)
- 단위마다 강조 지점이 1개인가
- 첫 문장이 답으로 시작하고 마지막 문장이 본문 내용으로 끝나는가
- 문장마다 생각이 1개이고 불릿마다 메시지가 1개인가
- 산출물에 이 스킬의 적용 사실이나 규칙 이름이 드러나지 않는가 (처리 내역 표와 진단 요지는 제외)
