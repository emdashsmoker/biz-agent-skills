# RFP 분석과 제안전략 수립

RFP를 읽고 입찰 여부와 제안 방향을 정하는 데 필요한 정보를 문서로 정리한다. 작업은 두 모드로 나뉜다. 두 모드를 가르는 기준은 필요한 입력이다. RFP만으로 확정할 수 있는 내용은 분석 모드가 맡는다. 제안사 정보나 외부 조사가 있어야 정할 수 있는 내용은 전략 모드가 맡는다. 전략 모드는 분석 모드의 결과 위에서 시작한다.

## 용어

아래 용어는 모든 산출물에서 같은 뜻으로 쓴다.

| 용어 | 뜻 |
|---|---|
| RFP | 발주처가 입찰 참가자에게 배포하는 문서 묶음. 제안요청서, 과업지시서, 입찰공고문, 평가 기준표를 포함한다 |
| 발주처 | 과업을 발주하고 제안서를 평가하는 기관 |
| 제안사 | 이 스킬을 쓰는 사용자의 조직. 컨소시엄이면 구성사 전체 |
| 과업 | RFP가 수행을 요구하는 일 전체 |
| 요구항목 | RFP 과업 내용 중 더 나눌 수 없는 최하위 항목. T1, T2 형식의 ID를 붙인다 |
| 모듈 | 과업을 결과물 단위로 나눈 수행 묶음. Module 1, Module 2로 표기한다 |
| Task | 모듈을 이루는 수행 단위. Task 1-1처럼 상위 모듈 번호를 잇는다 |
| 산출물 | 모듈이나 Task가 만드는 문서, 데이터, 회의 결과 |
| 성과 | 과업이 끝난 뒤 발주처에서 일어나는 변화. 누구의 무엇이 언제 어떤 상태가 되는지로 적는다 |
| 표면 니즈 | RFP의 배경과 목적 문장이 밝힌 요구 |
| 이면 니즈 | 발주처가 이 시점에 발주한 사정. 공개 자료로 뒷받침하는 가설로 다룬다 |
| 차별화 포인트 | 경쟁사가 같은 근거로 주장하기 어려운 제안사의 강점. 실적, 데이터, 인력 중 하나 이상을 근거로 갖는다 |
| 추진전략 | 과업의 어려운 지점을 넘기 위해 제안사가 더하는 수행 방식 |
| 핵심 워딩 | RFP가 과업명, 산출물명, 단계명, 대상 명칭에 쓰는 원문 표기 |
| [확인] | 입력 자료로 채우지 못한 칸의 표시. 사용자 답변이나 원문으로만 채운다 |

## 모드 선택

| 구분 | 분석 모드 | 전략 모드 |
|---|---|---|
| 필요한 입력 | RFP | RFP, 제안사 정보, 웹검색 허용 여부 |
| 산출물 | 01_RFP분석.md | 01_RFP분석.md, 02_제안전략서.md, 03_수행계획요약.md |
| 읽을 참조 파일 | references/analysis.md | references/analysis.md, references/strategy.md, references/competition.md, references/modules.md |
| 사용자 질의 | RFP가 없을 때 제출 요청 | 착수 질의 1회, 스토리라인 확인 1회 |

요청에서 모드가 드러나면 그 모드로 바로 진행한다. "RFP 정리해줘", "배점표 뽑아줘"는 분석 모드다. "제안전략 세워줘", "수주 전략", "경쟁사 분석", "모듈 구성해줘"는 전략 모드다. 모드가 드러나지 않으면 아래 문구로 한 번 묻는다. 답을 기다리는 동안에는 RFP 변환만 진행한다.

> RFP 분석과 제안전략 수립 중 어떤 작업이 필요한지 알려주세요. 분석은 RFP만으로 사업 조건, 참가자격, 평가 기준, 과업 내용을 정리합니다. 전략 수립은 분석에 더해 회사의 실적, 인력, 강점 정보를 받아 참여 판단, 경쟁 구도, 추진전략, 수행 구조까지 설계합니다.

- RFP가 없으면 "RFP(제안요청서, 과업지시서, 입찰공고문)를 파일로 제출해 주세요."라고 요청한다.
- 유사실적 선별만 요청하면 references/strategy.md의 유사실적 선별 절만 수행한다. 선별 기준에 과업 유형과 핵심 워딩이 쓰이므로 분석 모드를 먼저 수행한다.

## 입력 문서 변환

RFP와 첨부 문서는 scripts/parse.py로 마크다운으로 바꾼 뒤 읽는다. 의존 패키지 설치를 가장 먼저 수행한다.

```bash
pip install "markitdown[all]" python-hwpx pdfplumber olefile beautifulsoup4 lxml pyhwp six
python scripts/parse.py <입력 파일> <출력 파일.md>
python scripts/parse.py <입력 파일> <출력 폴더> --chunk --chunk-size 2000
```

| 형식 | 변환 엔진 | 실패 시 대체 경로 |
|---|---|---|
| PDF | markitdown(본문), pdfplumber(표) | 없음 |
| HWPX | python-hwpx 마크다운 변환 | python-hwpx 텍스트 추출, XML 직접 해석 |
| HWP | pyhwp(hwp5txt) | olefile 바이너리 해석 |
| DOCX, PPTX, XLSX, HTML, CSV, JSON, XML, TXT, EPUB, ZIP, 이미지, 오디오 | markitdown | 없음 |

- PDF는 본문과 표를 따로 추출한다. 표가 있으면 `<파일명>_tables.md`가 함께 생긴다. 배점표와 제출 서류 목록은 대개 표에 있으므로 두 파일을 모두 읽는다.
- pyhwp는 HWP의 표를 `<표>`로 대체한다. 표 내용이 필요하면 사용자에게 같은 문서의 HWPX나 PDF 파일을 요청한다.
- pyhwp 설치나 실행이 실패하면 스크립트가 olefile 경로로 자동 전환한다. 이 경로는 표 내용까지 읽지만 일부 글자가 깨지거나 한자가 빠질 수 있다.
- 추출 글자 수가 0이면 스캔 이미지 PDF일 가능성이 높다. 사용자에게 OCR이 필요하다고 알린다.
- 암호가 걸린 파일은 암호를 푼 파일을 요청한다.
- 긴 문서는 `--chunk` 옵션으로 제목 단위로 나눠 읽는다.

HWP 바이너리 해석 경로 관련 표기: 본 제품은 한컴의 HWP 문서 파일(.hwp) 공개 문서를 참고하여 개발하였습니다.

## 분석 모드

1. 변환본을 처음부터 끝까지 읽는다. 과업 내용, 평가 기준, 참가자격은 본문, 표, 붙임 서식에 흩어져 있다.
2. references/analysis.md의 양식과 규칙으로 01_RFP분석.md를 작성한다.
3. 배점 합계, 금액 환산, 기간 계산은 코드로 수행하고 원문 수치와 대조한다.
4. 응답에는 파일 위치, 참여를 막을 수 있는 참가자격 조건, 확인 필요 사항만 적는다.

추출은 원문을 읽은 판단으로 한다. RFP마다 절 구성, 번호 체계, 표 사용 방식이 달라서 정규식 추출은 항목을 빠뜨리거나 잘못 잡는다. 스크립트는 형식 변환만 맡는다.

## 전략 모드

| 단계 | 할 일 | 산출물 | 다음 단계 조건 |
|---|---|---|---|
| 1 분석 | 분석 모드 전체 수행 | 01_RFP분석.md | 분석 파일 완성 |
| 2 착수 질의 | 분석 결과와 함께 아래 질의를 한 번에 제시 | 사용자 답변 | 답변 수령 |
| 3 전략 수립 | references/strategy.md 순서로 작성. 경쟁 구도는 references/competition.md, 수행 구조는 references/modules.md를 따른다 | 02_제안전략서.md | [확인]이 사용자 판단 항목만 남음 |
| 4 스토리라인 확인 | 스토리라인 절과 모듈총괄표를 제시하고 수정 요청을 반영 | 02_제안전략서.md의 확인 기록 | 사용자 확인 |
| 5 요약 | 확인된 내용으로 수행계획 요약 작성 | 03_수행계획요약.md | 완료 전 점검 통과 |

착수 질의는 아래 항목을 한 턴에 묻는다.

- 참여 범위(과업 전체 또는 일부)와 컨소시엄 구성 여부, 구성사별 역할
- 제안사 정보. 사업 분야, 인력 규모, 보유 인증, 수행실적 목록(과업명, 발주처, 기간, 금액, 주요 내용). 표를 복사한 텍스트나 파일이면 충분하다
- 연구책임자 후보와 참여인력 후보의 학위, 경력, 유사 과업 이력
- 자문위원 후보 명단 보유 여부
- 월 평균 인건비 단가와 투입 가능 인력. 수행 여력과 원가 계산에 쓴다. 없으면 두 계산을 생략한다
- 보유한 과거 낙찰 결과나 경쟁사 정보
- 웹검색 허용 여부. 허용하지 않으면 이면 니즈의 근거와 경쟁 구도는 사용자 제공 자료로만 채운다
- 분석 모드가 판정한 과업 유형이 맞는지

답을 받지 못한 항목은 [확인]으로 남기고 진행한다.

스토리라인을 따로 확인받는 이유는 수정 비용이다. 논지는 수십 줄짜리 표에서 합의할 때 고치기 쉽다. 제안서 원고를 쓴 뒤에 논지를 바꾸면 원고 전체를 다시 써야 한다.

순수 소프트웨어 개발 과업은 references/modules.md 모듈 골격의 적용 범위 밖이다. 이 경우 수행 구조는 RFP 과업 구조를 그대로 모듈로 쓴다. 분석 모드와 전략 모드의 나머지 절차는 그대로 적용한다.

## 작성 원칙

- RFP 요구를 정리하기 전에 발주처가 왜 이 시점에 이 과업을 발주했는지와 결과물이 어디에 쓰이는지를 먼저 따진다.
- 사실과 가설을 나눈다. RFP에서 온 사실은 원문 위치(쪽 또는 조항 번호)를 붙인다. 가설은 "가설"로 표시하고 근거 자료를 붙인다.
- 채울 근거가 없는 칸은 [확인]으로 남긴다. 추정값을 사실처럼 적지 않는다.
- 합계, 비율, 금액 환산, 점수 계산은 코드로 한다. 암산한 수치는 쓰지 않는다.
- 사업명, 기관명, 산출물명, 과업명은 원문 표기를 그대로 쓴다. 심사위원은 RFP 워딩과 제안서 워딩을 대조하며 읽는다.
- 같은 층의 항목은 하나의 기준으로 나눈다. 항목끼리 겹치지 않고 합쳐서 빠짐이 없게 묶는다. 분류 기준의 이름은 결과 문서에 쓰지 않는다.
- 결과 문서는 존대 없는 개조식 간결체로 쓴다. 한 문장에는 한 가지 내용만 담는다.
- 대등한 명사 두 개는 "와", "과" 대신 "및"으로 잇는다. "예산과 인력 확보"는 "예산 및 인력 확보"로 쓴다. 비교 대상이나 협력 상대를 나타내는 "와", "과"는 그대로 둔다. BSC의 "학습과 성장" 같은 관용 명칭의 "와", "과"도 그대로 둔다.
- 굵은 글씨는 탈락, 감점, 참여 제한으로 이어질 수 있는 조건에만 쓴다.
- 모르는 정보는 모른다고 적는다.

## 근거와 출처

- 웹 자료는 1차 자료를 우선한다. 법령, 정부와 공공기관 발간물, 공식 통계, 기관 홈페이지 공지, 학술 논문이 여기에 속한다.
- 언론 보도는 보도가 인용한 원출처를 찾아 인용한다. 원출처를 찾지 못하면 보도만으로 결론을 세우지 않는다.
- 개인 블로그, 익명 커뮤니티, 위키 본문, AI 자동생성 사이트는 근거로 쓰지 않는다. 경쟁 구도의 수행 공개 경로에서 기관이 직접 게시한 글은 그 기관의 자기 진술로 인정한다.
- 출처는 "기관명 또는 저자명(연도), 자료명(URL)" 형식으로 적는다. URL은 해당 자료가 있는 페이지 주소까지 적는다.
- 법령 조문은 원문을 확인한 조문만 번호와 함께 인용한다.
- 고시금액, 참여 하한 같은 제도 수치는 개정된다. 공고일 기준 현행 값을 확인한 뒤 쓴다.
- 인력 후보와 자문위원 후보는 사용자가 제공한 명단만 쓴다. 성명을 지어내거나 웹에서 개인을 찾아 명단을 만들지 않는다. 경쟁 구도 표에는 기관명만 적는다.

## 대화 응답

- 응답에는 파일 위치, 진행 단계, 사용자가 판단할 항목, 오류만 적는다. 파일 본문을 응답에 옮겨 적지 않는다.
- 질문은 한 턴에 묶는다. 합리적 기본값이 있는 항목은 적용한 기본값을 밝히고 진행한다.
- 수정 결과는 바뀐 위치만 알린다.
- 파일 전달 도구가 있는 환경이면 그 도구로 파일을 전달한다. 도구가 없으면 경로를 안내한다. 파일을 저장할 수 없는 환경이면 결과 문서를 응답 본문에 출력한다.

## 완료 전 점검

- RFP 과업 내용의 최하위 항목이 요구항목표에 원문 그대로 모두 옮겨졌는가
- 배점 합계를 코드로 계산해 원문 총점과 맞췄는가
