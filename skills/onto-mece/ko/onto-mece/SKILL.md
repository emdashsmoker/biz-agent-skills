# 온톨로지 사고 점검

분류하고 묶고 구조를 짜고 판단을 내릴 때 따르는 점검 기준이다. 기준은 온톨로지 설계 원칙과 MECE 원칙에서 가져와 글쓰기와 판단에 맞게 옮겼다.

## 용어

아래 용어는 이 문서 전체에서 같은 뜻으로 쓴다.

- (분류 기준) 대상을 나누는 잣대 한 가지. 예를 들어 기업 규모, 추진 시점, 발생 영역이 있다
- (범주) 분류 기준으로 나눈 각 칸
- (사례) 범주에 배치하는 개별 대상
- (계층) 상위 범주와 하위 범주가 이어지는 단계
- (관계) 두 범주나 두 사례를 잇는 연결. 방향과 유형과 수량을 가진다

## 적용 방식

원칙은 사고 과정 안에서 적용하고 산출물에는 결과만 담는다. 독자에게 필요한 정보는 분류 결과이며 분류에 쓴 원칙의 이름은 독자에게 새 정보를 주지 않는다.

- 산출물에 원칙명(상호배제, 열린 세계 가정, is-a, part-of 등)을 쓰지 않는다
- 산출물이 원칙을 지켰다고 스스로 평가하는 문장을 쓰지 않는다. 예를 들어 "누락 없이 전체를 포괄하는 분류"라는 문장을 쓰지 않는다
- 사용자가 어떤 자료의 분류 구조를 검토해 달라고 요청하면 검토 결과를 그대로 제시한다

## 분류 규칙

### 분류 전 질문

분류를 시작하기 전에 아래 질문에 답한다. 답하지 못하면 분류 기준을 먼저 정한다. 분류의 목적이 정해져야 어떤 기준이 쓸모 있는지 가릴 수 있기 때문이다.

- 이 분류로 어떤 판단을 내리려 하는가
- 분류 대상의 범위는 어디까지인가
- 분류 기준이 한 가지인가
- 범위 안의 모든 사례를 빠짐없이 배치할 수 있는가

### 기준 단일화

한 분류 안에서는 분류 기준을 한 가지로 통일한다. 기준이 섞이면 한 사례가 여러 범주에 동시에 들어가거나 어느 범주에도 들어가지 않는다.

- (위반 예시) "기술별, 산업별, 시급성별" 범주가 같은 계층에 섞여 있다
- (올바른 예시) 1차 분류를 "기술별"로 통일하고 2차 분류에서 "산업별"로 나눈다
- 기준이 여러 개 필요하면 단계를 나누어 다단계 분류로 만든다

### 상호배제

범주끼리 겹치는 사례가 있으면 분류 기준을 다시 설계한다.

- 한 사례가 두 범주에 동시에 해당하는지 반례를 찾아 점검한다
- 동시에 해당할 수 없는 범주 쌍을 먼저 식별하고 그 쌍에 겹치는 사례가 있는지 확인한다
- 겹침이 생기면 범주 경계를 다시 정의하거나 두 범주를 상위 범주로 합친다
- 겹침을 피할 수 없으면 태그 방식(한 사례가 여러 태그를 가짐)으로 바꾸고 산출물에 태그임을 표기한다

### 전체포괄

범주를 모두 합치면 분류 대상 전체가 되어야 한다.

- "어느 범주에도 들어가지 않는 사례가 있는가"를 스스로 묻고 찾아본다
- 그런 사례가 있으면 분류가 불완전하다
- "기타" 범주를 두면 기타의 비중이 다른 어느 범주보다도 작아야 한다
- 기타의 비중이 그보다 크면 분류 기준을 다시 설계한다

### 범주 수

의사결정이나 보고를 위한 분류는 같은 계층에 범주 3-4개를 권장한다. 범주가 많을수록 독자가 범주 간 차이를 한 번에 비교하기 어렵다.

- 5개를 넘으면 중간 계층이 빠졌는지 확인하고 묶을 수 있는지 검토한다
- 2개이면 둘 중 하나만 가능한 상황이 맞는지 따로 확인한다. 제3의 선택지가 있으면 거짓 양자택일이다
- 생물 분류, 산업분류코드, 법령 조문처럼 이미 정해진 분류 체계는 범주가 5개를 넘어도 정상이다

### 빈 범주

정의한 범주에는 사례가 1개 이상 있어야 한다.

- 사례가 없는 범주는 삭제한다
- 앞으로 사례가 생길 근거가 있으면 범주를 유지하고 그 근거를 적는다
- 빈 범주가 생겼다면 분류 기준이 대상에 맞지 않는다는 신호일 수 있으므로 기준을 다시 본다

### 형식 편향

분석 방법이나 출력 형식에 맞추려고 분류를 바꾸지 않는다. 대상의 실제 모습을 먼저 파악하고 표현 방식은 그다음에 정한다.

- "차트로 그리기 편하다"는 분류 기준이 될 수 없다
- 특정 프레임워크의 칸 수에 맞추려고 대상을 나누거나 합치지 않는다
- 결론을 먼저 정하고 그 결론이 나오도록 범주를 거꾸로 짜지 않는다

## 계층 규칙

상하위 관계에는 세 종류가 있고 서로 섞지 않는다. 섞으면 상위 범주의 속성이 하위 범주에 잘못 이어져 뒤따르는 판단이 연달아 틀린다.

### 종류 관계

"X는 Y의 일종이다"가 성립할 때만 X를 Y의 하위 범주로 둔다.

- (성립) 전기차는 자동차의 일종이다. 이동수단이라는 자동차의 속성이 전기차에도 성립한다
- (불성립) 배터리는 전기차의 일종이다. 배터리는 전기차의 부품이다
- 상위 범주의 속성 중 하나라도 하위 범주에서 성립하지 않으면 종류 관계로 두지 않는다

### 부분 관계

"X는 Y의 부분이다"는 종류 관계와 다른 관계다. 목차를 짤 때 하위 항목이 상위 항목의 일종인지 부분인지 먼저 가린다.

- 전략과제는 전략의 일종인가. 아니다
- 전략과제는 전략의 부분인가. 그렇다. 전략과제는 전략을 이루는 구성요소다
- 구성요소를 하위 종류처럼 배치하지 않는다

### 속성 관계

"X는 Y를 가진다"는 속성 관계다. 속성을 하위 범주로 배치하지 않는다.

- 프로젝트는 예산을 가진다. 예산은 프로젝트의 속성이므로 프로젝트의 하위 범주로 두지 않는다

### 계층 깊이

실무 문서는 3단계 이내를 권장한다. 단계가 깊을수록 상위 속성이 하위까지 제대로 이어지는지 확인할 부담이 커진다.

- 4단계 이상이면 중간 계층이 정말 필요한지 다시 본다
- 생물 분류나 행정구역처럼 이미 정해진 체계는 깊어도 정상이다

## 연결 규칙

### 고립 범주

모든 범주는 다른 범주와 1개 이상의 관계로 이어져야 한다.

- 어떤 범주와도 관계가 없는 범주가 있으면 그 범주가 이 분류에 속하는지 다시 본다
- 고립이 정당하면(신규 영역, 예외 사례 등) 그 사유를 확인한다
- 구조도에서 연결선이 없는 항목은 관계가 누락되었거나 다른 구조에 속한다

### 신규 범주 연결

기존 분류에 새 범주를 추가할 때는 기존 범주와의 관계를 적는다. 관계를 적지 않으면 새 범주가 어느 기준에 속하는지 독자가 알 수 없다.

- 새 범주와 기존 범주의 관계(상위, 하위, 병렬, 의존, 선후 등)를 명시한다
- 새 범주 때문에 기존 범주의 범위나 경계가 바뀌는지 확인한다
- 새 범주 때문에 기존 범주 간 겹침이 생기면 분류 기준을 다시 설계한다
- (위반 예시) "단기, 중기, 장기" 과제 분류에 "긴급 과제"를 그냥 추가한다. "긴급"이 시간 기준인지 우선순위 기준인지 알 수 없다
- (올바른 예시) "긴급"이 우선순위 기준임을 밝히고 별도 분류로 분리하거나 기존 시간 분류에 우선순위 속성을 부여한다

### 관계 방향

관계에는 방향이 있다. "A가 B에 영향을 미친다"와 "B가 A에 영향을 미친다"는 서로 다른 관계다.

- 방향을 적지 않은 관계 서술은 모호하므로 방향을 명시한다
- 양방향이 모두 성립하면 방향마다 근거를 따로 제시한다

### 관계 유형

"관련이 있다"로 뭉뚱그리지 않고 관계의 유형을 특정한다.

- (인과) A가 발생해서 B가 발생한다. 시간 순서와 작동 방식을 확인한다
- (상관) A와 B가 함께 변한다. 이것만으로 인과라고 쓰지 않는다
- (의존) A가 없으면 B가 존재할 수 없다. 어느 쪽이 어느 쪽에 의존하는지 확인한다
- (연관) A와 B가 관련이 있다. 관련의 구체적 내용을 적는다

### 관계 수량

관계에 수량 조건이 있으면 명시한다.

- 1:1, 1:N, N:M 중 어느 관계인지 확인한다
- 반드시 있어야 하는 관계인지 없어도 되는 관계인지 구분한다
- 정한 조건이 현실과 맞는지 반례를 찾아 점검한다

## 정의 규칙

개념을 정의할 때 정의하려는 단어를 정의 문장에 다시 쓰지 않는다. 순환 정의는 독자에게 새 정보를 주지 않는다.

- (판별) 정의 문장에서 정의 대상 단어를 지웠을 때 뜻이 통하지 않으면 순환 정의다
- 동의어나 파생어로 바꿔 쓴 경우도 순환 정의다
- (위반 예시) "디지털 전환이란 디지털 기술을 활용하여 전환하는 활동"
- (올바른 예시) "디지털 전환이란 기존 업무 프로세스를 소프트웨어 기반으로 재설계하여 효율을 높이는 활동"
- 순환에 빠지면 상위 개념, 구성요소, 목적, 속성 중 하나 이상을 써서 다시 정의한다

## 정보 부재 규칙

### 열린 세계

명시되지 않은 사실은 미지로 처리한다. "확인되지 않음"과 "존재하지 않음"은 다른 판단이다.

- 정보가 없다는 사실을 부정의 근거로 쓰지 않는다
- (위반 예시) "해당 기업의 ESG 보고서가 검색되지 않으므로 ESG 활동을 하지 않는다"
- (올바른 예시) "해당 기업의 ESG 보고서가 확인되지 않아 ESG 활동 여부는 미확인이다"

### 닫힌 세계 전환

"없음"은 전수 조사가 끝난 범위에서만 단정한다.

- 셀 수 있는 대상을 빠짐없이 조사한 경우에만 부재를 단정한다
- 조사가 불완전하거나 범위가 좁으면 미지로 둔다
- 부재를 단정할 때는 조사 범위와 전수 조사의 근거를 함께 적는다

## 예시

아래 예시는 원칙을 적용하기 전(before)과 후(after)를 비교한다.

### 예시 1. 분류 기준 혼재와 범주 중복

(before)

```markdown
## 공공기관 정보화 사업의 문제점
- 예산 편성의 비효율
- 전문 인력 부족
- 부서 간 칸막이
- 레거시 시스템 노후화
- 정보보호 미흡
- 성과 평가 체계 부재
- 특정 업체 종속
```

(문제) 7개 항목이 한 계층에 섞여 있다. 예산은 자원 영역이고 칸막이는 조직 영역이며 레거시 시스템은 기술 영역이다. "전문 인력 부족"과 "성과 평가 체계 부재"는 둘 다 인력 운영 문제로도 읽혀 경계가 겹친다. 범주 수도 5개를 넘는다.

(after)

```markdown
## 공공기관 정보화 사업의 문제점

### 자원 배분
- 정보화 예산이 유지보수에 편중되어 신규 사업 투자 여력 부족
- 전문 인력의 내부 확보가 어려워 외주 의존 고착

### 기술 기반
- 레거시 시스템 노후화로 신규 시스템 연동이 어렵고 보안 취약점 누적
- 특정 업체의 독자 규격에 묶여 시스템 교체 시 전환 비용 과다

### 조직 운영
- 부서별 개별 발주 관행으로 기관 전체 정보화 전략과 불일치
- 정보화 성과를 측정할 기관 차원의 평가 기준 미수립
```

(바꾼 이유) 분류 기준을 "문제가 발생하는 영역" 한 가지로 통일하고 7개 항목을 3개 범주로 묶었다. 정보보호와 업체 종속은 기술 기반으로, 성과 평가는 조직 운영으로 옮겨 겹침을 없앴다.

### 예시 2. 종류, 부분, 속성 관계 혼동

(before)

```markdown
## 스마트시티 추진 체계

### 스마트시티 하위 항목
- 스마트 교통
- 스마트 에너지
- 스마트 안전
- 통합 플랫폼
- 도시 데이터 허브
- 시민 참여 거버넌스
- IoT 센서 네트워크
```

(문제) 스마트 교통은 스마트시티 서비스의 일종이다. 통합 플랫폼과 IoT 센서 네트워크는 스마트시티를 이루는 기반 시설이다. 시민 참여 거버넌스는 스마트시티가 가진 운영 방식이다. 세 종류의 관계가 한 계층에 섞여 있다.

(after)

```markdown
## 스마트시티 추진 체계

### 서비스 영역 (스마트시티 서비스의 유형)
- (스마트 교통) 실시간 교통 정보로 신호를 제어하고 대중교통 운행을 조정
- (스마트 에너지) 건물 에너지 소비를 모니터링하고 분산 에너지 자원을 관리
- (스마트 안전) CCTV 영상 분석으로 재난을 조기에 감지하고 긴급 대응

### 기반 시설 (스마트시티를 이루는 기술 요소)
- (통합 플랫폼) 서비스 간 데이터를 연계하고 통합 관제를 수행하는 소프트웨어
- (도시 데이터 허브) 도시 운영 데이터를 수집, 저장, 개방하는 데이터 저장소
- (IoT 센서 네트워크) 현장 데이터를 수집해 플랫폼에 전달하는 물리 장비

### 운영 방식 (스마트시티 운영을 위한 의사결정 구조)
- (시민 참여 거버넌스) 서비스 기획과 평가 단계에 시민 의견을 반영하는 절차
```

(바꾼 이유) 종류, 부분, 속성 관계를 별도 섹션으로 나누고 각 섹션 안에서는 한 가지 관계만 쓰도록 정리했다. 섹션 이름 옆 괄호에는 관계를 쉬운 말로 적고 원칙명은 쓰지 않았다.

### 예시 3. 정보 부재를 부정으로 전환

(before)

```markdown
## 국내 제조업 AI 도입 현황
- (대기업) 자체 AI 연구소를 운영하며 공정 최적화에 AI를 적극 활용
- (중견기업) 일부 기업이 품질 검사 자동화에 AI를 도입했으나 도입률은 낮음
- (중소기업) AI 도입 사례가 거의 없으며 인식 수준도 미흡
- (소상공인) AI 도입 역량이 전무하여 정책 지원 대상에서 제외하는 것이 현실적
```

(문제) 중소기업의 "사례가 거의 없음"은 조사 근거 없이 부재를 단정했다. 소상공인의 "역량이 전무"는 정보 부재를 부정의 근거로 쓴 뒤 정책 방향까지 정했다. 기업 규모 분류가 "대기업은 도입, 소상공인은 미도입"이라는 결론에 맞춰 짜였을 가능성도 있다.

(after)

```markdown
## 국내 제조업 AI 도입 현황
- (대기업) 공정 최적화와 품질 예측에 AI를 적용한 사례가 공개 자료에서 다수 확인됨. 도입 범위와 성과는 기업마다 다름
- (중견기업) 품질 검사 자동화 등 특정 공정에 AI를 도입한 사례가 확인됨. 도입률은 별도 조사 결과 확인 필요
- (중소기업) 도입 현황 전수 조사 결과가 확인되지 않아 도입 수준 판단 보류
- (소상공인) 도입 역량 조사 결과가 확인되지 않아 판단 보류. 정책 대상 제외 여부는 조사 결과 확보 후 결정
```

(바꾼 이유) "거의 없음", "전무"처럼 근거 없는 부재 단정을 "미확인"이나 "판단 보류"로 바꿨다. 정책 결론은 조사 결과 확보를 전제 조건으로 달았다. 기업 규모 분류는 유지하고 범주마다 근거 수준을 구분했다.

### 예시 4. 순환 정의

(before)

## 용어 정의

- (데이터 거버넌스) 데이터를 거버넌스하는 체계

- (클라우드 네이티브) 클라우드에 네이티브한 방식으로 설계된 아키텍처

## 용어 정의
- (디지털 전환) 기존 업무 프로세스를 소프트웨어 기반으로 재설계하여 운영 효율을 높이는 활동
- (데이터 거버넌스) 조직 내 데이터의 품질, 접근 권한, 생애주기를 관리하는 정책과 절차
- (AI 역량) 업무 목적에 맞는 AI 모델을 고르고 운영 환경에 적용할 수 있는 조직의 기술 준비도

### 예시 5. 신규 범주의 고립

(before)

```markdown
## 디지털 전환 추진 과제 (v2, 신규 과제 추가)

### 기존 과제
- (단기) 업무 프로세스 자동화
- (중기) 데이터 분석 환경 구축
- (장기) AI 기반 의사결정 체계 도입

### 신규 추가 과제
- 보안 강화
- 조직문화 혁신
- ESG 데이터 관리
```

(문제) 신규 과제 3건이 기존 시간 분류(단기, 중기, 장기)와 어떤 관계인지 적혀 있지 않다. 보안 강화가 단기인지 중기인지 알 수 없고 ESG 데이터 관리가 데이터 분석 환경 구축과 선후 관계인지 의존 관계인지 알 수 없다.

(after)

```markdown
## 디지털 전환 추진 과제 (v2)

### 단기
- 업무 프로세스 자동화
- 자동화 대상 시스템의 보안 요건을 사전에 정의하여 보안 정책을 함께 수립

### 중기
- 데이터 분석 환경 구축
- ESG 데이터를 분석 환경의 수집 대상에 포함
- 부서 간 데이터 공유 기준을 수립하여 조직문화 전환을 병행

### 장기
- AI 기반 의사결정 체계 도입
- 단기에 수립한 보안 정책과 중기에 구축한 분석 환경을 전제로 설계
```

(바꾼 이유) 신규 과제를 독립 범주로 두지 않고 기존 시간 분류 안에서 해당 시점의 과제와 연결했다. 보안 강화는 단기 자동화의 요건으로, ESG 데이터 관리는 중기 분석 환경의 수집 범위로, 조직문화 혁신은 중기 데이터 공유 기준과 함께 추진하는 과제로 연결했다.

## 산출 전 점검

산출물에 분류, 그룹핑, 구조화, 판단이 들어가면 아래 질문을 확인한다.

- 분류 기준이 한 가지로 통일되어 있는가
- 반례를 찾아봤을 때 두 범주에 동시에 들어가는 사례가 없는가
- 어느 범주에도 들어가지 않는 사례가 없는가
- 같은 계층의 범주가 5개를 넘으면 중간 계층을 검토했는가
- 사례가 없는 빈 범주가 없는가
- 분석 방법이나 출력 형식에 맞추려고 분류를 바꾸지 않았는가
- "기타"의 비중이 다른 어느 범주보다도 작은가
- 상하위 관계가 종류, 부분, 속성 중 무엇인지 구분되어 있는가
- 종류 관계에서 상위 범주의 속성이 하위 범주에도 성립하는가
- 다른 범주와 관계가 없는 고립 범주가 없는가
- 새로 추가한 범주와 기존 범주의 관계가 적혀 있는가
- 관계의 방향과 유형이 특정되어 있는가
- 정의 문장에 정의 대상 단어가 다시 나오지 않는가
- 정보가 없다는 사실을 부정의 근거로 쓰지 않았는가

## 예외

- 사용자가 분류 기준을 직접 지정하면 그 기준을 먼저 적용한다. 그 기준에서 이 문서의 원칙과 맞지 않는 부분이 보이면 사용자에게 알린다
- 코드의 분류 구조도 적용 대상이다. 함수 분리, 조건 분기, 예외 처리, 열거형, 클래스 상속을 점검한다
- 범주 수와 계층 깊이의 권장값은 문서 독자를 위한 기준이다. 코드는 도메인 명세가 정한 범주 수와 깊이를 따른다
- 순위나 목록처럼 단순 나열을 요청받으면 분류와 구별하여 이 규칙을 강제하지 않는다
