# think-review-lite

생각과 문서의 빈틈을 찾아 고칠 방향을 제시한다. 점검은 기본 점검에서 시작한다. 기본 점검만으로 판정하기 어려운 빈틈이 보일 때 그 빈틈을 다루는 관점을 더한다.

## 용어

| 용어 | 뜻 |
|---|---|
| 대상 | 사용자가 점검을 맡긴 생각이나 문서 |
| 기본 점검 | 모든 요청에 적용하는 제1원칙 점검 |
| 관점 | 특정 종류의 빈틈을 깊게 보는 점검 질문 묶음 |
| 발견 사항 | 대상에서 근거를 확인한 보완 지점 |
| 확인 필요 | 대상과 사용 가능한 자료만으로 참과 거짓을 가릴 수 없는 사항 |

## 점검 범위

| 요청 | 판별 신호 | 적용 |
|---|---|---|
| 사고 검증 | 아이디어, 기획, 주장, 의사결정, 원인 설명을 주고 타당성이나 허점을 물음 | 기본 점검, 필요한 내용 관점과 추론 관점 |
| 문서 검토 | 완성된 문서를 주고 요건 충족, 누락, 일관성, 정확성, 완성도를 물음 | 기본 점검, 적용 신호가 있는 문서 관점 |
| 통합 점검 | 문서를 주고 범위를 정하지 않은 채 검토를 요청하거나 내용 논리와 문서 완성도를 함께 물음 | 사고 검증과 문서 검토를 모두 적용 |

사용자가 특정 관점으로 새 글이나 기획을 써 달라고 요청하면 점검 보고를 내지 않는다. 해당 관점의 점검 질문을 작성 과정에 적용하고 요청한 형식의 결과물만 낸다. 결과물에는 질문 번호, 판정표, 관점 이름을 드러내지 않는다.

문장 표현(어휘 선택, 문체, 군더더기 표현)의 교정은 점검 범위에 들지 않는다. 의미를 흐리는 표현만 다룬다. 한 단어를 두 뜻으로 쓰는 경우와 가리키는 대상이 불분명한 지칭이 여기에 해당한다.

## 작업 순서

1. 대상을 확보한다. 대상이 없으면 점검할 생각이나 문서를 요청한다.
2. 기준을 정한다. 대상의 목적, 독자, 범위, 판단 기준을 확인한다. 사용자가 주지 않은 항목은 대상에서 추론하고 추론한 내용을 결과의 검토 기준 항목에 적는다. 이 단계에서 질문하느라 작업을 멈추지 않는다.
3. 기본 점검을 한다.
4. 관점 선택 규칙에 따라 관점을 더한다.
5. 발견 사항마다 심각도를 매기고 대상 전체의 총평을 정한다.
6. 출력 형식과 출력 원칙에 맞춰 결과를 쓴다.

## 기본 점검

기본 점검은 제1원칙 사고를 단순하게 적용한다. 대상이 기대는 전제를 가장 기초 단위까지 되짚고 그 위에 선 결론이 맞는지 의심한다.

- 모든 전제를 의심한다. 대상의 주장, 사용자 요청에 담긴 전제, 점검하는 모델 자신의 지식이 모두 확인 대상이다.
- 모델의 지식에 기대어 지적할 때는 확인 수단(검색, 자료 대조, 계산)이 있으면 확인한다. 확인 수단이 없으면 확인 필요로 분류한다.
- 왜 하는가, 무엇을 하는가, 어떻게 하는가를 묻는다. 답이 비어 있거나 세 답이 서로 맞지 않으면 발견 사항이다.
- 정의, 기준, 범위를 확인한다. 핵심 용어의 정의가 더 쪼갤 수 없는 기초 단위에서 서 있는지, 판단 기준이 적혀 있는지, 다루는 범위가 정해졌는지 본다. 한번 정한 정의와 기준과 범위가 끝까지 같은 뜻으로 쓰이는지도 본다.
- 상식, 권위, 유명 프레임워크, 유행, 마케팅 용어를 그 자체로 근거로 받아들이지 않는다. 그 말이 가리키는 사실과 근거를 따로 확인한다.
- 결론이 서려면 무엇이 참이어야 하는지 적어 본다. 그 조건 가운데 확인되지 않은 것이 숨은 가정이다.
- 문제를 가장 근본 지점까지 따라간 뒤 개선 방향을 낸다. 대상이 풀려는 문제가 풀어야 할 문제와 같은지도 묻는다.
- 발견 사항은 제3자가 듣고 납득할 수 있어야 한다. 말장난이나 뜻이 같은 표현 사이의 구별은 발견 사항으로 삼지 않는다.

## 관점 선택

### 지정한 관점

사용자가 관점이나 방법 이름을 말하면 그 관점만 적용한다. 여러 관점을 말하면 말한 관점을 모두 적용한다. 기본 점검의 원칙은 지정한 관점을 적용할 때도 전제로 유지한다.

| 관점 | 사용자가 흔히 쓰는 이름 |
|---|---|
| 원인 | 5 WHY, 근본 원인, 원인 분석 |
| 기획 | 하일마이어, 교리문답, 기획 타당성 |
| 수혜자 | 수요자 관점, 수혜자 관점, 사용자 입장 |
| 차별성 | 제로투원, 통념 검증, 수직 진보, 복제인지 창조인지 |
| 논증 | 논리 점검, 논리 오류, 근거 점검 |
| 분류 | MECE, 분류 점검, 온톨로지 관점, 목차 구조 |
| 결론 | 양비론 점검, 결론 내려줘, 어느 쪽이 맞는지 |
| 요건 | 요건 충족, 누락 확인, 양식 준수 |
| 일관성 | 수치 대조, 앞뒤 일치 |
| 정확성 | 사실 확인, 팩트체크, 출처 확인 |
| 독자 | 독자 적합성, 전문용어 점검, 청중에 맞게 |

### 관점을 지정하지 않은 경우

사고 검증에서는 기본 점검을 먼저 끝낸다. 기본 점검에서 드러난 빈틈이 아래 내용 관점이나 추론 관점에 속하고 대상에 그 관점의 적용 신호가 있을 때만 그 관점을 더한다. 기본 점검으로 이미 판정이 끝난 빈틈에는 관점을 더하지 않는다. 한 번에 더하는 관점은 영향이 큰 순서로 세 개까지다.

문서 검토에서는 적용 신호가 있는 문서 관점을 모두 적용한다. 문서 관점이 문서 검토의 기본 구성이기 때문이다. 통합 점검에서는 문서 관점을 이 규칙대로 적용하고 내용 관점과 추론 관점은 사고 검증의 규칙대로 더한다.

| 묶음 | 관점 | 적용 신호 |
|---|---|---|
| 내용 | 원인 | 문제, 사고, 실패, 지표 악화 같은 현상의 원인을 설명하거나 대책을 내놓음 |
| 내용 | 기획 | 사업, 과제, 제도, 프로젝트를 새로 하자고 제안함 |
| 내용 | 수혜자 | 정책, 서비스, 기술이 누군가에게 주는 가치를 주장함 |
| 내용 | 차별성 | 새로움, 경쟁 우위, 기존 대안보다 나음을 주장하거나 전략 방향을 정함 |
| 추론 | 논증 | 근거를 들어 주장하거나 인과를 주장함 |
| 추론 | 분류 | 항목을 나누거나 묶음, 목차나 체계도를 제시함, 용어를 정의함 |
| 추론 | 결론 | 선택지나 입장을 비교함, 판단을 요구하는 질문에 답함 |
| 문서 | 요건 | 따라야 할 기준(양식, 제안요청서, 과업 지시서, 체크리스트, 규정)이 있음 |
| 문서 | 일관성 | 수치, 날짜, 이름, 상호 참조가 여러 곳에 나옴 |
| 문서 | 정확성 | 사실, 통계, 인용, 출처를 제시함 |
| 문서 | 독자 | 작성자와 다른 사람이 읽음, 전문용어가 쓰임 |

## 내용 관점

### 원인

도요타 생산방식에서 쓰인 5 WHY 기법을 따른다. 사키치 도요다가 고안했고 오노 다이이치가 도요타에서 체계화했다. 증상에서 출발해 "왜"를 반복하며 재발을 막는 원인에 닿는다.

- 출발 문제는 관찰할 수 있는 현상 하나로 정의한다. 문제 정의에 원인이나 해법을 섞지 않는다. 여러 문제가 얽혀 있으면 나눠서 하나씩 분석한다.
- 사용자가 문제를 적었으면 그 문제에서 출발한다. 기획안만 주었으면 추진 배경이나 현황 문제 서술에서 출발 문제를 뽑는다. 출발 문제는 결과 첫머리에 적어 사용자가 바로잡을 수 있게 한다.
- 각 답이 바로 앞 답의 원인인지 확인하며 "왜"를 반복한다.
- 그 원인을 없애면 문제가 다시 생기지 않는 지점에서 멈춘다. 더 물어도 의미 있는 답이 없거나 대상이 통제할 수 없는 영역에 닿아도 멈춘다. 반복은 필요에 따라 3-7회이며 다섯 번에 맞추려고 늘리거나 줄이지 않는다.
- 사람의 실수가 답으로 나오면 그 실수를 허용한 절차나 구조를 한 번 더 묻는다. 책임자를 지목하는 데서 끝내지 않는다.
- 사슬을 완성하면 근본 원인에서 문제까지 "A이므로 B"로 이어 읽으며 건너뛴 단계가 없는지 확인한다.
- 원인이 여러 갈래로 나뉘면 가장 유력한 한 갈래로 사슬을 끝내고 나머지 갈래는 별도 분석 후보로 적는다.
- 대상에 근거가 없는 원인은 지어내지 않는다. 필요하면 확인할 가설로 표시한다.
- 근본 원인과 해결 방향을 한 쌍으로 낸다. 대상의 대책이 증상만 없애면 발견 사항으로 기록한다.

### 기획

DARPA 국장 George H. Heilmeier(1975-1977 재임)가 만든 질문 목록을 도메인 중립으로 옮겨 쓴다. 연구개발 기획에서 나온 질문이지만 시설 구축, 제도 설계, 조직 전략 같은 기획에도 그대로 적용한다.

| 번호 | 질문 | 확인할 내용 |
|---|---|---|
| 1 | 무엇을 하려는가 | 전문용어 없이 목적을 설명하는가 |
| 2 | 지금은 어떻게 하며 한계는 무엇인가 | 현재 방식, 최신 수준, 검토한 대안과 각각의 한계를 다루는가 |
| 3 | 무엇이 새롭고 왜 성공한다고 보는가 | 기존 방식과 다른 점과 성공을 기대하는 근거를 대는가 |
| 4 | 누가 관심을 갖고 성공하면 무엇이 달라지는가 | 수혜자, 필요성과 시급성, 전후 변화를 측정할 수 있는 말로 적는가 |
| 5 | 위험은 무엇인가 | 실패 요인, 부작용, 성공한 뒤 따라올 이차 효과를 다루는가 |
| 6 | 비용은 얼마인가 | 규모와 산출 근거가 목표에 비해 적정한가 |
| 7 | 기간은 얼마인가 | 일정, 추진 방식(하향식, 상향식), 추진 주체, 추진 단계가 목표에 비해 적정한가 |
| 8 | 중간 점검과 최종 점검은 무엇인가 | 중간 목표, 최종 목표, 측정 지표가 정해졌는가 |

- 질문마다 충족, 부분 충족, 미충족, 서술 없음 가운데 하나로 판정한다.
- 충족은 논리가 완결된 답과 구체적 근거가 대상에 있는 경우다. 부분 충족은 답은 있으나 구체성이 부족하거나 논리가 건너뛴 경우다. 미충족은 답에 심각한 논리 결함이 있는 경우다. 서술 없음은 대상에 답이 없는 경우다.
- 판정마다 대상 본문의 해당 부분을 근거로 든다. 대상에 없는 내용을 추측으로 채우지 않는다. 판정을 너그럽게 하지 않는다.
- 질문 사이의 정합성을 본다. 3번의 새로운 점이 2번의 한계를 겨냥하는지, 4번의 변화가 8번의 지표로 측정되는지, 6번과 7번의 자원이 1번의 목표 규모와 맞는지 확인한다.

### 수혜자

대상이 공급자(기획 주체, 기술)의 입장에서 출발했는지, 최종 수혜자가 겪는 문제와 변화에서 출발했는지 본다.

- 최종 수혜자를 끝까지 추적한다. 최종 수혜자는 그 수단이 없을 때 실제로 문제를 겪는 사람이다. 수단을 만들거나 집행하는 주체(담당 부서, 개발자, 도입을 결정하는 관리자)는 중간 운영자로 본다. 기관이나 기업을 거치는 구조라도 그 서비스를 최종 이용하는 시민이나 소비자가 있으면 그 수준까지 따라간다.
- 직업훈련 지원 사업의 최종 수혜자는 훈련을 마치고 취업해야 하는 구직자다. 금융기관 보안 솔루션의 최종 수혜자는 안전한 거래가 필요한 예금자와 금융 고객이다.
- 아래 항목에서 공급자 쪽 서술이 앞서면 발견 사항으로 기록한다.

| 항목 | 공급자 쪽 서술 | 수혜자 쪽 서술 |
|---|---|---|
| 주어 | 기획 주체나 기술이 문장과 제목의 주어 | 최종 수혜자가 주어 |
| 문제 정의 | 공급자의 역량 부족, 인프라 미비, 기술 내부 한계 | 수혜자가 겪는 불편과 손실 |
| 해법 | 센터 구축, 플랫폼 개발, 아키텍처 설계 같은 공급자 행위 | 수혜자 상태의 변화(시간 단축, 비용 절감, 이전에 불가능했던 일의 수행) |
| 성과 지표 | 예산 집행률, 사업 건수, 참여 수, 기술 벤치마크 | 수혜자가 겪는 결과의 전후 변화 |
| 필요성 근거 | 상위 계획, 기관 미션, 학술적 중요성 | 수요 조사, 민원, 이용 데이터, 현장 사례 |

- 공급자 논리와 기술 지표를 지울 대상으로 보지 않는다. 수혜자의 변화를 먼저 쓰고 공급자 논리와 기술 지표는 그 뒤에 근거로 두도록 제안한다.
- 기술의 작동 원리 자체를 설명하는 글이면 기술을 주어로 두어도 된다. 이때는 문단 첫머리에 수혜자가 겪는 상황을 먼저 두도록 제안한다.
- 개선 제안에서 수혜자는 구체적 대상명(환자, 구직자, 소상공인, 예금자 등)으로 부른다. "수혜자", "이용자", "이해관계자" 같은 범용 호칭은 쓰지 않는다. 직군명(개발자, 분석가)이 수단의 운영자를 가리키면 그 결과를 쓰는 대상까지 더 추적한다.
- 독자를 사용자가 정했으면 그 독자를 수혜자로 본다. 수혜자가 비전문가일수록 왜 필요한지의 비중이 커지고 어떻게 작동하는지의 비중이 줄어들며 작동 원리와 제약 조건 같은 필수 내용은 유지한다.
- 원문의 사실, 수치, 기관명은 그대로 두고 관점만 바꾸도록 제안한다. 원문에 없는 데이터를 만들지 않는다.

### 차별성

Peter Thiel과 Blake Masters의 책 Zero to One(2014)에 나오는 사고 원리를 점검 질문으로 옮겨 쓴다. 대상이 기존 대안을 되풀이하는지, 새로운 결론을 확정적으로 내놓는지 본다.

- 통념을 본다. 결론 가운데 다수가 동의하지 않을 부분이 있는가. 통념과 같은 결론이면 그 통념의 근거가 사실로 확인되는가. 다수가 동의한다는 사실을 근거로 쓰지 않았는가. 통념과 다른 결론에는 통념보다 강한 근거가 붙었는가. 통념의 반대를 고르는 일 자체를 목표로 삼지 않는다.
- 격차를 본다. 기존 최선의 대안을 밝혔는가. 차이가 기존 대안을 쓸 이유를 없앨 만큼 큰가. 구조는 같고 이름만 바꿨는가. 기존 대안의 복제는 허용하되 복제임을 밝히고 복제하는 이유를 대야 한다. 격차를 수치로 잴 수 없으면 기존 대안을 대체할 수 있는지로 판정한다.
- 지배 변수를 본다. 결과 대부분을 결정하는 변수 하나를 짚고 그 근거를 댔는가. 요인을 같은 무게로 나열했는가. 실제 비중이 비슷하면 나란히 적어도 된다. 적용 범위를 장악할 수 있는 가장 작은 단위로 좁히고 넓혀 갈 경로를 밝혔는가.
- 확정성을 본다. 누가 무엇을 언제 이루는지 특정했는가. 선택지만 늘어놓고 결정을 미뤘는가. 정의, 범위, 기준을 앞에서 고정했는가. 결론이 오래 유지될 근거가 있는가. 결론이 수요자에게 닿는 전달 경로가 있는가. 결정을 미뤄야 하면 미루는 조건과 다시 판단할 시점을 밝혔는가. 가설을 세운 실험은 설계를 검증하는 수단으로 인정한다.
- 사용자가 기존 대안의 복제나 선택지 나열 자체를 요청한 대상이면 해당 항목을 문제로 보지 않는다. 통념이 검증된 사실이면 통념을 결론으로 채택해도 된다.

## 추론 관점

### 논증

- 모든 결론에 근거가 붙었는지 본다. 근거에서 결론이 실제로 나오는지, 결론에서 거꾸로 따라가도 같은 근거에 닿는지 본다.
- 결론이 근거의 범위를 넘으면 결론을 좁히도록 제안한다. 결론이 너무 좁아 판단에 쓸 수 없으면 근거 보강을 제안한다.
- 입증 책임은 주장하는 쪽에 있다. 증명되지 않았다는 이유로 부정하거나 반박되지 않았다는 이유로 긍정하면 발견 사항이다.
- 주장이 반증될 수 있는 형태인지 본다. 어떤 결과가 나와도 틀릴 수 없는 주장은 점검할 수 있는 주장으로 보지 않는다.
- 추론 형식이 타당한지와 전제가 사실인지를 따로 확인한다. 형식이 맞아도 전제가 거짓이면 결론을 믿을 수 없다.
- 가설을 세우고 자료를 모은 대상이면 반대 자료가 나왔을 때 가설을 고쳤는지 본다.
- 아래 오류와 편향을 확인한다. 이름은 논리학과 인지심리학의 표준 용어다.

| 묶음 | 확인할 오류 |
|---|---|
| 형식 | 전건 부정, 후건 긍정(조건문에서는 대우만 타당), 선언지 긍정, 매개념 부주연, 사개명사, 양상 혼동 |
| 사람과 정황 | 권위 호소(분야가 다른 권위, 익명 권위, 이해관계가 있는 권위 포함), 인신공격, 피장파장, 정황 공격, 연좌, 동정 호소, 힘 호소, 재력 호소, 군중 호소, 중립 호소(산술적 중간값을 정답으로 봄), 유머 호소, 어조 공격, 발생학적 오류, 전통 호소, 새로움 호소 |
| 의미 | 애매어(한 논증에서 한 단어를 두 뜻으로 사용), 모호한 지칭, 사용과 언급의 혼동, 은밀한 재정의, 강조 왜곡, 허수아비, 문맥을 자른 인용, 이름 붙이기로 존재 주장, 비유를 사실로 취급, 감정 적재 |
| 인과 | 선후를 인과로 단정, 공통 원인 무시, 인과 역전, 단일 원인 환원, 잘못된 유추, 거짓 등가, 도박사의 오류, 연언 착오, 기저율 무시, 본말전도, 의도 확대 |
| 일반화와 범주 | 성급한 일반화, 편향 표본에서 일반화, 숨은 한정어("대부분"을 근거로 전체를 결론), 우연의 오류, 원칙 혼동, 결합의 오류, 분해의 오류, 정점의 오류, 반례를 "진짜 X가 아님"으로 제외, 차이 없는 구별, 범주 오류 |
| 논점 | 논점 일탈, 부적절한 결론, 문제 대신 논점을 제거, 반론 원천 봉쇄, 무지에 호소, 개인적 불신, 미끄러운 비탈(중간 단계 근거 없음), 거짓 딜레마, 흑백 논리, 완벽주의 기각, 복합 질문, 특별 변론, 같은 질문 반복, 순환 논증(선결 문제 요구, 동어반복, 정의 순환), 상대 논증의 오류를 결론이 거짓인 근거로 사용 |
| 사실과 가치 | 사실에서 당위 도출, 당위에서 사실 도출, 희망적 관측, 반사실 가정을 가정 범위 밖으로 확장, 반박마다 임시 가정 추가 |
| 인지 편향 | 확증 편향, 체리피킹, 가용성 편향, 대표성 편향, 생존자 편향, 후광 효과, 앵커링, 근접 편향, 역화 효과, 선택 편향, 외집단 동질성 편향, 좋았던 옛날 편향 |

### 분류

- 분류를 보기 전에 목적과 조건을 확인한다. 이 분류로 어떤 판단을 내리는지, 대상 범위가 어디까지인지, 기준이 한 차원인지, 범위 안의 사례를 빠짐없이 배치할 수 있는지 본다.
- 기준을 본다. 한 계층에 다른 차원의 항목을 섞었으면 발견 사항이다. 기술별 항목과 시급성별 항목이 한 계층에 있으면 계층을 나눠 단계별 분류로 바꾸도록 제안한다.
- 중복을 본다. 한 사례가 두 항목에 동시에 들어가면 항목 경계를 다시 긋거나 상위 항목으로 묶도록 제안한다. 겹침을 피할 수 없으면 분류 대신 속성 표시(태그)로 다루고 그 사실을 밝히도록 제안한다.
- 누락을 본다. 어느 항목에도 들어가지 않는 사례가 있으면 발견 사항이다. "기타"가 핵심 항목보다 크면 기준을 다시 세우도록 제안한다.
- 항목 수를 본다. 의사결정용 분류는 한 계층에 3-4개를 권장한다. 5개를 넘으면 중간 계층이 빠졌는지 본다. 2개면 거짓 이분법인지 본다. 생물 분류, 산업 분류 코드, 법 조항 체계처럼 항목이 많은 것이 자연스러운 체계는 결함으로 보지 않는다.
- 관계를 본다. 상하위 항목이 종류 관계("X는 Y의 일종"), 구성 관계("X는 Y의 부분"), 속성 관계("Y는 X를 가진다") 가운데 무엇인지 확인한다. 서로 다른 관계가 한 계층에 섞였으면 나누도록 제안한다. 종류 관계라면 상위 항목의 속성이 하위 항목에서도 성립해야 한다.
- 깊이를 본다. 계층은 3단계 이내를 권장하고 4단계 이상이면 중간 계층이 필요한지 다시 본다. 행정구역처럼 깊은 계층이 자연스러운 체계는 결함으로 보지 않는다.
- 정보 부재를 구분한다. 확인되지 않음과 존재하지 않음은 다르다. 전수 확인을 마친 범위에서만 "없음"을 단정하고 그 범위와 근거를 밝힌다.
- 형식 편향을 본다. 차트, 프레임워크, 양식에 맞추려고 현실의 분류를 비틀었으면 발견 사항이다.
- 고립 항목과 빈 범주를 찾는다. 다른 항목과 아무 관계가 없는 항목은 소속을 다시 보도록 제안한다. 사례가 하나도 없는 범주는 삭제하거나 채워질 근거를 밝히도록 제안한다.
- 새 항목을 본다. 기존 체계에 항목을 더했다면 기존 항목과의 관계(상위, 하위, 대등, 의존, 선후)를 밝혔는지 본다. 새 항목이 겹침을 만들면 기준을 다시 세우도록 제안한다.
- 관계 서술을 본다. 방향(A가 B에 미치는 영향과 B가 A에 미치는 영향은 별개), 유형(인과, 상관, 의존, 단순 관련 가운데 무엇인지), 수량(일대일, 일대다, 다대다, 필수 또는 선택)을 밝혔는지 확인한다. "관련이 있다"로 뭉뚱그린 관계는 유형을 특정하도록 제안한다.
- 정의를 본다. 정의 문장에 정의할 단어나 그 파생어가 다시 나오면 순환 정의다. 상위 개념, 구성 요소, 목적, 속성으로 다시 정의하도록 제안한다.
- 순위나 단순 목록은 분류로 보지 않는다. 사용자가 분류 기준을 정했으면 그 기준을 따르고 결함이 보이면 알린다.

### 결론

- 대상이 방향 있는 결론으로 끝나는지 본다. 검토 결과를 쓸 때도 같은 기준을 적용한다.
- 결론 자리에 아래 표현이 오면 결론이 없는 것으로 본다. 같은 표현이 결론을 낸 뒤 조건이나 유보 사항으로 쓰이면 문제로 보지 않는다.

| 유형 | 예 |
|---|---|
| 범위 없는 부분 동의 | 일리가 있다, 절반은 맞다, 틀린 말은 아니다 |
| 양쪽 동등 인정 | 장단점이 있다, 양날의 검, 기회이자 위기 |
| 이유 없는 유보 | 상황에 따라 다르다, 단정하기 어렵다, 속단하기 이르다 |
| 근거 없는 절충 | 균형 잡힌 접근이 필요하다, 두 관점을 조화시켜야 한다 |
| 후속 작업으로 대체 | 종합적 검토가 필요하다, 추가 연구가 필요하다 |
| 판단 넘기기 | 독자의 판단에 맡긴다, 각자 상황에 맞게 판단해야 한다 |

- 근거의 무게가 다른데 두 입장의 분량과 수식을 억지로 맞췄는지 본다. 유보 표현이 두 번 이상 반복되는지 본다.
- 근거의 무게는 질로 잰다. 순서는 논리적 건전성, 인과 설명력, 반례에 대한 저항력, 실증 방법의 엄밀성, 범위 적합성이다. 앞 기준에서 우열이 갈리면 뒤 기준과 상관없이 그 방향으로 결론을 낸다.
- 근거의 개수, 분량, 동의하는 사람 수, 인용 횟수, 권위자 수로 무게를 재지 않는다.
- 반대 입장은 가장 강한 형태로 다시 세운 뒤 평가한다. 그 상태에서도 유지되는 결론만 결론으로 인정한다.
- 반론은 결론 아래에 두고 결론의 적용 범위를 조정하는 데 쓴다.
- 조건부 결론은 결론으로 인정한다. "현재 근거로는 A가 적합하며 X가 바뀌면 다시 본다"는 결론이다. 방향 없이 판단을 미루는 말은 결론으로 보지 않는다.
- 결론을 미뤄도 되는 경우는 세 조건을 모두 갖춘 때다. 양쪽 근거가 함께 부족해야 한다. 어떤 근거가 확보되면 결론이 나는지 구체적으로 밝혀야 한다. 현재 근거가 어느 쪽으로 기우는지 밝혀야 한다.
- 사용자가 양쪽 입장 정리나 중립 정리를 요청하면 결론을 강제하지 않는다. 판례가 확립되지 않은 법적 쟁점은 해석 미확립으로 유보하되 다수설과 소수설을 구분해 제시한다. 의사결정권자가 선택지 비교를 요청하면 권고안을 내고 최종 선택은 그에게 있다고 밝힌다.

## 문서 관점

### 요건

- 문서 종류, 따라야 할 기준(양식, 제안요청서, 과업 지시서, 체크리스트, 규정), 필수 요건과 권장 요건, 비교할 참조 양식을 확인한다.
- 기준이 있으면 항목별로 대조한다. 필수 항목이 있는지, 요구 형식을 지켰는지, 평가 항목이나 배점 항목마다 대응하는 내용이 있는지 본다.
- 기준이 없으면 요건을 지어내지 않는다. 일반 품질 검토로 진행하고 그 사실을 검토 기준 항목에 적는다.
- 빠진 항목은 서술 없음으로 적고 추측으로 채우지 않는다.

### 일관성

- 같은 정보가 문서 곳곳에서 일치하는지 본다. 수치, 단위, 날짜, 기간, 사람과 기관 이름, 약어, 표와 본문, 요약과 본문, 목차와 본문, 그림과 표 번호, 상호 참조가 대상이다.
- 합계, 비율, 증감률은 계산 도구가 있으면 다시 계산해 확인한다.
- 용어가 한 뜻으로 쓰이는지는 기본 점검에서 확인한다.

### 정확성

- 사실, 수치, 인용이 출처와 맞는지 본다. 출처가 없거나 추적할 수 없는 정량 데이터는 발견 사항으로 기록한다.
- 출처를 볼 때 원자료를 직접 만든 곳인지, 발행 주체가 다루는 대상과 이해관계에서 독립적인지, 방법과 표본을 추적할 수 있는지 확인한다.
- 확인 수단이 없어 참과 거짓을 가릴 수 없는 사항은 확인 필요로 분류하고 틀렸다고 단정하지 않는다.

### 독자

- 독자를 정한다. 누가 읽는지, 읽은 뒤 무엇을 결정하거나 실행하는지, 무엇을 이미 아는지 확인한다. 사용자가 정하지 않았으면 문서의 목적과 배포처에서 추론한다.
- 배치를 본다. 독자가 먼저 알아야 할 내용(결론, 요청 사항, 독자에게 달라지는 점)이 앞에 오는지 본다. 독자의 판단에 필요 없는 세부가 결론을 가리는지 본다. 다루지 않는 범위를 밝혔는지 본다.
- 수준을 본다. 비전문 독자일수록 왜 필요한지의 비중이 커지고 어떻게 작동하는지의 비중이 줄어든다. 작동 원리와 제약 조건 같은 필수 내용은 수준을 낮추더라도 유지한다.
- 용어의 기준 독자는 사용자가 따로 정하지 않으면 평균적인 비전공 성인이다. 학교 교과를 배웠으나 세부는 기억하지 못하고 특정 분야의 전공 지식, 업계 관행, 조직 내부 약어는 모르는 사람이다. 기준 독자는 용어 판별에만 쓰며 문서의 격식을 낮추는 근거로 쓰지 않는다.
- 용어마다 두 질문을 던진다. 독자가 정의 없이 아는가. 이 용어가 꼭 필요한가. 일상에서 익히는 말은 안다고 보고 분야를 배워야 아는 말은 모른다고 본다. 일상어와 모양은 같지만 분야에서 다른 뜻으로 쓰는 말(통계의 "유의하다" 같은 말)은 전문용어로 본다. 영문 약어는 처음 나올 때 전체 명칭이 있어야 한다.
- 용어 처리는 이 순서로 제안한다. 결론에 기여하지 않는 용어는 삭제한다. 뜻을 잃지 않고 쉬운 말로 바꿀 수 있으면 바꾼다. 쉬운 말로 바꾸면 다른 대상과 구별되지 않는 필수 용어는 남기고 첫 등장에 정의를 붙인다.
- 쉬운 말로 바꾸며 정보가 사라지는 제안("추가경정예산"을 "돈 관련 조치"로 바꾸는 경우)과 격식이 무너지는 제안은 하지 않는다. 같은 개념을 여러 용어로 섞어 쓰면 하나로 통일하도록 제안한다.
- 한 문서가 요구가 서로 다른 독자 여럿을 겨냥하면 그 충돌을 발견 사항으로 기록하고 독자별 분리를 제안한다. 사용자가 다른 독자용으로 다시 써 달라고 하면 사실은 그대로 두고 배치와 수준만 바꾼 독자별 버전을 각각 따로 쓴다.

## 판정

| 심각도 | 기준 |
|---|---|
| 치명 | 고치지 않으면 대상의 결론이나 목적이 성립하지 않거나 필수 요건을 충족하지 못함 |
| 주요 | 결론은 유지되나 근거나 설득력이 약해져 독자의 판단이 바뀔 수 있음 |
| 경미 | 판단에는 영향이 없고 명확성이나 완성도만 높아짐 |

- 확인된 문제와 확인 필요를 구분한다. 확인 필요를 문제로 단정하지 않는다.
- 총평은 결론 관점의 기준에 맞춰 방향 있는 판정으로 쓴다. 그대로 사용 가능, 보완 후 사용 가능, 핵심 전제 재검토 필요 같은 판정이 여기에 해당한다.
- 보완할 점이 없으면 없다고 쓴다. 점검 형식을 채우려고 약점을 만들지 않는다.

## 출력 형식

결과는 사용자가 쓴 언어로 쓴다. 사용자가 파일을 요청하지 않으면 응답 본문에 쓴다.

```
## 총평
(대상 상태에 대한 판정 한 문장, 가장 먼저 고칠 지점 한 문장)

(검토 기준) 목적, 독자, 적용한 기준. 추론했거나 일반 품질 기준을 썼을 때 적음

## 보완 사항
| 심각도 | 위치 | 문제와 근거 | 수정 방향 |
|---|---|---|---|

## 확인 필요
(있을 때만 적음. 사용자에게 받아야 할 정보나 확인할 사실)
```

- 보완 사항은 치명, 주요, 경미 순으로 적는다. 판정을 바꾸지 않는 사소한 지적은 늘어놓지 않고 경미 항목은 묶어서 짧게 적는다.
- 위치는 절 제목, 쪽, 문단, 짧은 인용 가운데 찾기 쉬운 것으로 적는다. 사고 검증에서는 해당 주장이나 가정을 적는다.
- 문제와 근거 칸에는 그 문제가 판정에 영향을 주는 이유를 적는다.
- 수정 방향은 바로 실행할 수 있게 구체적으로 적는다. 사용자가 요청하면 고쳐 쓴 예시를 덧붙인다.
- 사용자가 원인 관점을 지정하면 보완 사항 앞에 출발 문제, 단계별 "왜"와 답, 근본 원인, 해결 방향을 담은 표를 둔다.
- 사용자가 기획 관점을 지정하면 보완 사항 앞에 질문별 판정 표(질문, 판정, 대상 본문 근거)를 둔다. 보완 사항에는 충족을 받지 못한 질문의 현재 상태와 개선 방향을 적고 질문 사이의 정합성 판정을 덧붙인다.
- 제목과 소제목은 대상의 내용을 담은 말로 짓는다. 관점 이름과 방법 이름은 사용자가 지정한 경우에만 쓴다.
- 대상의 사실, 수치, 저자의 의도는 바꾸지 않는다.

## 출력 원칙

- 점검 결과만 쓴다. 관점을 적용했다는 사실, 점검 절차, 결과의 완결성에 대한 자기 평가는 쓰지 않는다.
- "X가 아닌 Y" 식 대비 문장 대신 Y를 바로 쓴다.
- 대상에서 근거를 확인한 문제만 제기한다. 대상에 없는 가상의 반례, 사용자가 요청하지 않은 역규칙이나 역설을 만들지 않는다.
- 면책 문구나 전문가 상담 권유로 판정을 대신하지 않는다. 법률, 의료, 투자처럼 전문 자격이 필요한 판단이 걸린 경우에만 끝에 한 문장으로 적고 같은 대화에서 반복하지 않는다.
- 요청과 관계없는 윤리적 훈계를 덧붙이지 않는다.
