# logical-write

보고서, 기획서, 제안서, 분석 글을 마크다운 개조식으로 쓰고 고치는 규칙이다. 제목 계위(`#`, `##`)와 항목 계위(`-`, `+`)는 hwpx, docx 보고서의 장절 번호와 항목 기호에 그대로 대응한다. 사람이 옮겨 적기 쉽고 LLM이 가공하기도 쉽다.

규칙은 논리, 구조, 문장, 표현으로 나뉜다. 논리는 무엇을 말할지, 구조는 어떤 순서로 말할지, 문장은 한 줄을 어떻게 쓸지, 표현은 어떤 말을 고를지 정한다. 이 파일에는 핵심 규칙만 두고 세부 기준과 예시는 `references/` 파일에 둔다.

## 작업 모드

요청 문구로 작업 모드를 정한다.

| 모드 | 요청 예시 | 산출물 |
|---|---|---|
| 작성 | "써줘", "작성해줘" | 결과물만 출력한다 |
| 교정 | "고쳐줘", "다듬어줘", "교정해줘" | 교정 유형을 유형별 한 줄로 요약한 뒤 교정문을 출력한다. 교정문 안에는 교정 사실을 적지 않는다. 원문의 사실, 수치, 출처, 인용은 그대로 둔다 |
| 진단 | "검토해줘", "진단해줘", "점검해줘" | 점검 항목별 통과 여부, 미통과 위치, 개선 방향을 제시한다. 구조를 다시 짜야 하면 재배치 안을 함께 제시한다 |

세 모드 모두 산출물에 이 스킬의 이름, 규칙 이름, 프레임워크 이름(SCQA, MECE, So What 등), 점검 과정을 드러내지 않는다. 진단 보고도 구조 자체를 지적한다. "결론이 첫 섹션에 없음"으로 쓰고 "피라미드 원칙 위반"으로 쓰지 않는다.

## 문장 모드

두 문장 모드는 접속 표현과 절을 잇는 어미를 허용하는지만 다르다. 나머지 규칙은 같다.

| 구분 | 단문 모드 (기본값) | 연결 모드 |
|---|---|---|
| 접속 표현 (그리고, 그러나, 그래서, 그렇기 때문에, 이는, 이에 따라 등) | 쓰지 않는다. 문장 사이 관계는 항목 배치와 계위로 드러낸다 | 앞뒤 문장 사이에 인과, 부연, 대비, 시간, 조건 관계가 실제로 있을 때만 쓴다 |
| 절을 잇는 어미 (-으며, -이며, -고, -면서, -지만, -함에 따라, -할 경우 등) | 쓰지 않는다. 두 사실은 문장을 나눠 쓴다. 한 문장 안의 수단이나 원인은 "-하여", "-으로"처럼 5W1H 요소 하나로 담는다 | 핵심 메시지를 보강하는 인과, 조건, 구체화, 수단 절에만 쓴다 |
| 공통 규칙 | 1문장 1메시지, 5W1H 요소별 1회, 명사형 종결, 괄호형 소제목, 출처 표기 | 단문 모드와 같다 |

모드는 다음 기준으로 정한다.

- 기본값은 단문 모드다.
- 사용자가 "흐름 있게", "서사적으로", "연결되게", "스토리라인 있게", "맥락 있게", "narrative" 등을 요청하면 연결 모드로 쓴다.
- 사용자가 "단문으로", "끊어서", "엄격하게" 등을 요청하면 단문 모드로 쓴다.
- 모드는 요청 단위로 적용한다. 사용자가 섹션을 지정하면 그 섹션에만 적용하고 지정이 없으면 산출물 전체를 한 모드로 쓴다.
- 작성 도중 모드를 사용자에게 묻지 않는다.

같은 내용을 두 모드로 쓰면 다음과 같다.

```markdown
## 반복 입력 항목의 통합 필요
- 현장 담당자는 같은 고객 정보를 여러 화면에 반복 입력하여 건당 처리 시간 증가
    + 월말 정산 기간에 입력량 집중으로 반복 입력 불편 신고 증가
    + 입력 오류 수정 요청은 반복 입력 항목에서 주로 발생
- 운영팀은 반복 입력 항목을 단일 화면으로 통합하여 입력 부담 경감 추진
    + 통합 대상 항목은 현장 설문 결과로 우선순위 설정
    + 시범 부서의 처리 시간 변화를 확인한 후 전 부서로 확대
```

## 작성 절차

큰 단위에서 작은 단위 순서로 쓴다.

1. 목적과 독자를 정한다. 요청 문구만 보지 말고 요청한 이유를 추론한다. 요청을 처리하는 데 필요한 최소 범위, 독자가 이미 아는 내용, 핵심 용어의 정의와 범위와 기준을 먼저 정한다. 한 번 정한 정의, 범위, 기준은 글 끝까지 바꾸지 않는다.
2. 핵심 메시지를 정한다. 독자가 기억할 판단문 한 문장을 쓴다. 대립하는 입장 사이에서 판단해야 하면 `references/judgment.md`를 읽는다.
3. 구조를 설계한다. 거시 구조를 하나 고르고 헤더 이름과 헤더 사이의 흐름부터 정한다. `references/structure.md`를 읽는다. 항목을 나누거나 묶을 때는 `references/classification.md`를 읽는다.
4. 섹션을 쓴다. 섹션마다 메시지 하나를 두고 주장마다 근거를 붙인다. 문장은 `references/sentence.md`, 주장과 근거는 `references/logic.md`를 따른다.
5. 점검한다. 아래 산출 전 점검 목록을 확인한다. 표현은 `references/expression.md`, `references/vocabulary.md`, `references/terms.md`로 점검한다.
6. 헤더 이름을 마지막으로 다시 본다. 헤더만 읽어도 하위 내용을 알 수 있어야 한다.

| 파일 | 내용 | 읽는 시점 |
|---|---|---|
| `references/sentence.md` | 5W1H 판정 절차, 모드별 세부 규칙, 문장 부호, 종결, '것' 등 빈자리 명사, 문장 리듬 | 문장을 쓰거나 고칠 때 |
| `references/structure.md` | 결론 우선 배치, 거시 구조, 분석 단계 순서, 헤더 작명, 단위당 메시지, 표와 데이터 배치, 진단 항목 | 구조를 설계하거나 진단할 때 |
| `references/logic.md` | 주장과 근거의 짝, 가설 사고, 형식적 오류, 비형식적 오류, 인지 편향, 입증 책임 | 주장을 세우거나 논증을 검토할 때 |
| `references/judgment.md` | 양비론 판별, 근거의 질 평가, 반론 배치, 결론 유보 조건 | 대립하는 입장 사이에서 결론을 낼 때 |
| `references/classification.md` | 분류 기준, 겹침과 빠짐 점검, 계층 관계, 정의, 정보 부재 처리 | 항목을 나누고 묶거나 개념을 정의할 때 |
| `references/expression.md` | 의미 없는 표현, LLM 정형 수사, 메타 서술 | 산출 전 점검, 교정 |
| `references/vocabulary.md` | 선호, 비선호, 신중 어휘와 번역투 | 산출 전 점검, 교정 |
| `references/terms.md` | 전문용어 판별 기준과 처리 순서 | 비전문 독자 대상 글, 전문용어가 많은 글 |

## 출력 형식

```markdown
# 문서 제목
## 섹션 제목
- 주장 (들여쓰기 없음)
    + 주장의 근거 (4칸 들여쓰기)
    + 대등한 두 번째 근거
> (데이터명) 정성 또는 정량 근거 데이터 설명

> 기관명 또는 저자명(연도), 자료명(URL)
```

- `-` 항목에는 주장을 쓰고 `+` 항목에는 그 주장의 근거나 부연을 쓴다.
- `+` 항목은 대등한 항목이 2개 이상일 때만 쓴다. 1개만 남으면 상위 문장에 합치거나 별도 `-` 항목으로 올린다. 상위 항목이 고유명칭이나 프레임워크이고 하위 항목이 그 정의나 범위를 한 줄로 제시하는 경우는 1개도 허용한다.
- `+` 항목은 3-4개를 권장한다.
- `+` 기호는 들여쓰기 전용이다. 문장 안에서 나열이나 연결에 쓰지 않는다.
- `>` 블록은 근거 데이터, 출처, 전문용어 설명에만 쓴다. 블록이 여러 개면 빈 줄로 나눈다.
- 문장 앞에 소제목을 붙일 때는 `- (소제목) 내용` 형식을 쓴다. `소제목 : 내용`, `소제목 - 내용` 형식은 쓰지 않는다.
- 소제목은 내용을 담은 키워드로 짓는다. "(설명)", "(이유)", "(주장)", "(근거)", "(섹션1)" 같은 빈 라벨과 같은 소제목의 반복은 쓰지 않는다. 소제목은 필요한 항목에만 붙인다.
- 같은 상위 항목 아래의 소제목은 같은 분류 기준을 따른다. 같은 그룹 안에서는 모든 항목에 소제목을 붙이거나 모든 항목에 붙이지 않는다.
- 같은 계위의 헤더는 키워드형이나 문장형 중 하나로 통일한다.
- 헤더 하나에는 주제 하나만 담는다. "정책동향", "기술동향"처럼 나누고 "정책동향 및 기술동향"처럼 "및", "와", "/"로 두 주제를 묶지 않는다.
- 범위 표기에는 물결표(`~`) 대신 하이픈(`-`)을 쓴다. 물결표 두 개가 한 줄에 있으면 마크다운에서 취소선으로 표시된다.
- 표준 한글 자판으로 입력할 수 있는 문자를 쓰는 것을 권장한다.

## 핵심 규칙

### 문장

- 한 문장에는 메시지 하나만 담는다. 누가, 언제, 어디서, 무엇을, 왜, 어떻게는 한 문장에 각각 한 번만 나온다. 문장마다 Why, What, How를 담는 구성을 권장한다.
- 명사형으로 끝맺는다(-함, -임, -필요, -전망, -예정). 존댓말, 구어체, 유행어, 속어, 은어는 쓰지 않는다. 학술 문체 수준의 격식을 유지한다.
- 명사형 종결은 자연스러운 한국어로 쓴다. "목차명에는 키워드 기반 재구성으로 반영"은 "목차명은 키워드 기반으로 재구성"으로 고친다.
- 명사만 이어 붙인 문장은 쓰지 않는다. "연구 기술 자원 역량 상태"는 "연구 인프라 보유 여부"처럼 조사를 살려 쓴다.
- 쉼표는 같은 범주를 3개 이상 나열할 때만 쓴다. 2개는 "A 및 B"로 쓴다. 연결용 쉼표는 지우기만 하지 말고 문장을 나누거나 명사형으로 재구성한다.
- 문장 끝 마침표, 세미콜론, 구분 기호(/, |, ·, →, vs), 연결 하이픈("단기-중기"), 과도한 축약어, 불필요한 외래어나 한자어는 쓰지 않는다.
- 의존명사 '것'과 '곳', '부분', '셈' 같은 빈자리 명사로 지시 대상을 감추지 않는다.
- "A가 아닌 B", "단순한 A가 아니라 B" 같은 부정 후 긍정 대비 구문을 쓰지 않는다. B를 바로 쓴다.
- 같은 뜻이면 긍정 표현을 쓴다. "데이터 준비도 부족"보다 "정형 데이터를 확보하면 전환 가능"이 낫다.

### 구조

- 결론을 먼저 둔다. 문서 제목이나 첫 섹션에 글 전체의 결론을 두고 각 섹션의 첫 문장에 섹션의 결론을 둔다.
- 글 전체의 거시 구조는 SCQA(상황, 전개, 질문, 답변), Why-What-How(필요성, 조치, 실행), SCR(상황, 문제, 해결) 중 하나로 통일한다.
- 환경 분석과 전략을 함께 다루는 글은 거시환경, 미시환경, 내부현황, 벤치마킹, 전략, 이행 순서를 지킨다.
- 상위 항목은 하위 항목의 결론이고 하위 항목은 상위 항목의 근거다. 같은 계위의 항목은 같은 종류로 묶고 한 가지 순서로 배열한다.
- 섹션, 항목 묶음, 표 하나에는 메시지 하나를 둔다. 메시지를 지지하는 구성요소는 3-4개를 권장한다. 5개 이상이면 상위 범주로 묶는다.
- 섹션은 따로 떼어 읽어도 뜻이 통하게 쓴다. 다른 섹션과 합치거나 분리하기 쉬워야 한다.
- 표는 글의 핵심을 요약할 때 쓰고 글이 길면 반드시 쓴다. 표는 글 전체에 3개 이하를 권장한다. 표는 관련 주장 바로 뒤에 두고 표 두 개를 연달아 두지 않는다. 표를 `>` 블록이나 코드 블록 안에 넣지 않는다.

### 논리와 판단

- 모든 주장에는 근거를 붙인다. 근거에서 주장으로, 주장에서 근거로 양방향 추적이 되어야 한다.
- 근거는 표면에서 멈추지 않는다. "왜"를 반복하여 근본 원인까지 추적한다.
- 요청 내용, 통념, 권위, 유행어, 유명 프레임워크, 자기 지식을 그대로 받아들이지 않고 검증한다.
- 사실과 판단을 한 문장이나 한 분류에 섞지 않는다.
- 분류는 한 기준으로 나누고 항목끼리 겹치지 않게, 전체에서 빠지는 항목이 없게 만든다. 같은 계위 항목은 3-4개를 권장한다.
- 결론은 한쪽 방향으로 낸다. 반론은 가장 강한 형태로 검토한 뒤 결론 아래에 둔다. 중간값을 결론으로 내세우지 않는다.
- 권위 있는 기관의 이름을 근거로 대신 쓰지 않는다. 정보가 없다는 사실을 부정의 근거로 쓰지 않는다.
- 현실 검증 없이 형식만 빌린 논리를 쓰지 않는다. 실물 수요를 무시한 숫자 설계, 목적에 맞춰 사실을 꾸미는 논리, 금지 목록에만 기대는 방어 설계, 반증할 수 없는 이론, 근거 없는 장밋빛 전망, 선도 사례의 형식만 복제한 방안이 여기에 해당한다. 비용 숫자만 좇는 관점과 과장된 마케팅 관점도 피한다.
- 사용자가 요청하지 않은 반례, 역설, 역규칙, 반대 논리, 여집합 설명, 대체 규칙을 임의로 끼워 넣지 않는다.
- 결론은 중립적이고 객관적인 사실 인식에서 끌어낸다. 중간 지대를 대변하지 않는다. 단정적이거나 공격적인 논리로 비약하지 않는다.

### 근거와 출처

- 정량 데이터는 산출 근거나 조사 근거가 분명할 때만 쓴다. 제3자가 근거를 물으면 5W1H로 답할 수 있어야 한다.

```markdown
- (올바른 예) OO리서치의 20XX년 조사에 따르면 국내 A 시장은 20XX년 약 B원에서 20XX년 약 D원으로 연평균 약 N% 성장 전망 (C 방법론 적용, 낙관 시나리오)
- (틀린 예) A 시장은 N% 성장 전망
```

- 핵심 정량 데이터는 글 전체에 3개 이하를 권장한다. 많을수록 어느 수치가 중요한지 흐려진다.
- 시계열 데이터는 3-5년 이상을 권장하고 연평균 증가율이나 전체 대비 비중을 함께 적는다.
- 수치 계산은 모델이 직접 하지 않고 코드로 한다.
- 출처는 "기관명 또는 저자명(연도), 자료명(URL)" 형식으로 적는다. 정량 데이터가 있는 문장 바로 아래 `>` 블록에 둔다. 같은 출처의 데이터가 이어지면 데이터 묶음 끝에 한 번만 적는다. 정성 인용의 출처는 섹션 끝에 둘 수 있다.
- 정량 데이터는 원출처가 분명하고 검증할 수 있는 자료만 쓴다. 뉴스 기사나 블로그에 실린 수치는 원출처를 확인한 뒤 원출처를 인용한다.
- 편집과 검증 절차가 있는 1차 자료를 인용한다. 정부와 공공기관 발간물, 국제기구 보고서, 학술 논문, 공신력 있는 연구기관과 금융기관 자료, 대형 오픈소스 프로젝트 공식 문서가 여기에 해당한다. 출처가 불분명한 블로그, 위키, 익명 게시판은 인용하지 않는다.
- 기관명과 자료명은 원문 표기를 그대로 쓴다. 존재하지 않는 출처는 만들지 않는다. URL은 도메인만 남기지 말고 자료에 바로 접근하는 전체 경로를 적는다.
- 숫자는 천 단위 쉼표와 단위를 함께 적는다(1,000,000 또는 100만).
- 문헌을 소개하거나 인용할 때는 독자가 원문을 다시 찾지 않아도 되게 핵심 내용을 빠짐없이 담는다.
- 모르는 정보는 모른다고 적는다.
- 인명, 기관명, 자료명, 정책명, 사업명, 제품명은 공식 전체 명칭을 쓴다. 사용자가 요청하지 않으면 줄이거나 바꾸지 않는다.

### 표현

- 글 자체, 작성자, 작성 과정, 사용자의 요청, 사용한 도구를 대상으로 삼는 메타 서술을 쓰지 않는다.
- 지워도 의미가 그대로 남는 수식어, 평가어, 접착제 표현을 쓰지 않는다.
- "3대 전략", "4개 방안"처럼 개수를 미리 선언하지 않고 내용을 바로 쓴다.
- 독자가 이미 아는 내용을 다시 설명하지 않는다. 정보 과부하를 피한다.
- 단정적이고 공격적인 어휘(절대, 차단, 오직, 유일, 무조건)를 피하고 독자가 받아들일 수 있는 정중한 완곡 표현을 쓴다. 완곡 표현이 지나치면 뜻이 흐려지므로 명백히 잘못된 것은 분명하게 지적한다.
- 따뜻한 어조를 쓰되 객관성을 잃지 않는다. 전문가끼리만 통하는 과시적 표현을 피한다.
- 쉽고 단순한 논리와 어휘를 쓴다. 쉬움의 대상은 논리 전개와 개념 설명이다. 어조는 성인 실무자 대상 공식 문서 수준의 격식을 유지한다.
- 전문 컨설팅 보고서 수준의 전문성과 완성도를 목표로 한다.

## 우선순위와 적용 범위

- 사용자가 직접 지정한 구조, 분류 기준, 문장 모드, 표기 방식, 독자 수준, 분량은 이 스킬의 기본값보다 우선한다.
- 사용자가 수사적 표현, 메타 서술(예: "서두에 보고서 목적을 적어줘"), 결론 후행 배치, 양쪽 입장의 균형 정리, 전수 나열을 명시적으로 요청하면 해당 규칙을 적용하지 않는다.
- 학술 논문의 연구 목적과 연구 방법 섹션처럼 장르 관례상 필요한 서술은 관례를 따른다.
- 인용 원문, 법령 조문 원문, 코드 자체는 고치지 않는다. 앞뒤 설명 문장에만 규칙을 적용한다.
- 고유명사, 법률 용어, 기술 표준 명칭은 어휘 규칙의 대상이 아니다.
- 사용자의 표기 지침과 충돌하면 표기 방식은 사용자 지침을 따르고 정형 표현에 해당하는지는 이 스킬의 기준으로 판단한다.

## 산출 전 점검

- 문서 제목이나 첫 섹션에 결론이 있고 각 섹션 첫 문장이 섹션의 결론인가
- 헤더만 읽어도 흐름과 하위 내용을 알 수 있는가
- 각 섹션과 항목 묶음이 메시지 하나만 전달하는가
- 분류 기준이 한 가지이고 항목끼리 겹치거나 빠진 곳이 없는가
- 모든 주장에 근거가 있고 결론이 근거 범위 안에 있는가
- 결론이 한쪽 방향으로 나 있는가
- 한 문장에 5W1H 요소가 각각 한 번만 나오는가
- 단문 모드에서 접속 표현과 절을 잇는 어미가 없는가
- 연결 모드에서 접속 표현이 실제 관계를 드러낼 때만 쓰였고 한 문장에 연결 어미가 쌓이지 않았는가
- 명사형 종결이 자연스럽고 존댓말과 구어체가 없는가
- `+` 항목이 2개 이상일 때만 쓰였는가
- 정량 데이터마다 근거와 출처가 있는가
- 메타 서술, 의미 없는 수식, 개수 선언, 부정 후 긍정 대비 구문이 없는가
- 산출물에 스킬 이름, 규칙 이름, 프레임워크 이름이 드러나지 않았는가
- 요청하지 않은 반례나 역규칙을 끼워 넣지 않았는가
- em dash, 물결표, 문장 끝 마침표가 없는가
