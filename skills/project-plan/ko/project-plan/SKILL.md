# 프로젝트 오버뷰와 WBS

이 스킬은 계약 체결 후 수행 중인 프로젝트의 오버뷰 1건과 작업 일정표 1건을 만든다. 목표는 PM과 PL이 매주 열어 보는 표 한 장이다. 날짜 계산, 일정 여유 비율, M/M 합계는 `scripts/plan.py`가 계산한다. 이 문서의 파일 경로는 SKILL.md가 있는 폴더를 기준으로 한다.

## 설계 원칙

관리할 항목이 많은 계획표는 작성만 되고 쓰이지 않는 경우가 많다. 그래서 계획표를 아래 원칙으로 가볍게 유지한다.

- (표 하나) 작업 행은 과업 크기에 따라 늘거나 줄어든다. 1개월 과업은 할 일 목록 수준의 짧은 표가 되고 1년 과업은 긴 표가 되며, 규칙은 같다.
- (기본 구성) M/M은 기본으로 켜고 RACI는 기본으로 끈다. 사용자가 요청하면 각각 끄거나 켠다.
- (역할 분담) 모델은 문서 해석, 초안 작성, 재계획을 맡는다. 코드는 날짜, 비율, 합계를 계산한다. 진도 추적은 사용자가 쓰는 엑셀이나 PM 도구에서 이어간다.
- (모르는 값) 자료에 없는 수치는 `[확인 필요: 항목]`으로 표시한다. 날짜 칸은 비워 둘 수 없으므로 가정 날짜를 넣고 비고에 `[확인 필요: 날짜]`를 적는다. 그럴듯한 값으로 채운 표는 틀린 일정과 예산의 근거가 된다.

## 입력 자료

자료가 없으면 먼저 "과업지시서(RFP), 제안서, 착수보고서, 계약서와 참여 인력 서류 중 가진 자료를 올려 주세요"라고 요청한다. 문서를 직접 읽을 수 없는 환경에서는 `python scripts/to_md.py 파일들 -o inputs.md`로 텍스트를 먼저 뽑는다.

| 자료 | 가져올 내용 |
|---|---|
| 과업지시서(RFP) | 과업 범위, 과업 항목, 납품 산출물, 보고 횟수와 시기, 자문회의와 공청회 요구, 과업 기간 |
| 제안서 | 수행 방법, 추진일정, 투입 인력, 제안서에서 약속한 조사 규모와 회의 횟수 |
| 착수보고서 | 발주처와 확정한 일정, 협의 결과, 제안서 대비 변경 사항 |
| 계약 및 행정 서류 | 계약 기간, 계약 금액, 참여 인력과 참여율, 인건비 산정 M/M |

- 제안서에서 약속한 조사 규모와 회의 횟수는 계약 내용으로 보고 작업 행에 반영한다.
- 자료끼리 내용이 다르면 항목마다 아래 자료를 기준으로 삼고, 어긋난 내용은 오버뷰의 특기사항에 기록한다.
- (기간, 금액, 인력의 기준) 계약 및 행정 서류를 따른다.
- (과업 범위와 산출물의 기준) 과업지시서를 따른다.
- (방법과 일정의 기준) 착수보고서를 따르고, 착수보고서가 없으면 제안서를 따른다.

## 작업 순서

1. 자료를 읽고 프로젝트명, 기간, 발주처, 보고 일정, 납품 산출물, 투입 인력을 정리한다.
2. 자료로 확인되지 않은 필수 항목만 한 번에 질문한다. 필수 항목은 계약 종료일, 보고회 일정, 투입 인력이다. 질문마다 적용할 기본값을 함께 밝히고, 답이 없으면 기본값으로 진행한 뒤 `[확인 필요]`로 표시한다.
3. `references/skeletons.md`에서 과업 유형에 맞는 단계 골격을 고르고 과업지시서 항목을 행으로 옮긴다. 설문이 있으면 `references/survey.md`도 읽는다.
4. `assets/plan_example.json` 형식으로 plan.json을 작성한다. 필드 설명은 `references/output.md`에 있다.
5. `python scripts/plan.py check plan.json`을 실행한다. 경고가 1-2건이면 고친 뒤 한 번 더 실행한다. 3건 이상 남으면 초안과 남은 경고 목록을 함께 제시한다.
6. `python scripts/plan.py md plan.json -o overview.md`로 오버뷰를 만든다. CSV, XLSX, PDF는 사용자가 요청할 때 만든다.

같은 프로젝트의 두 번째 요청부터는 plan.json을 고쳐 다시 내보낸다. 응답에는 바뀐 행, 일정 여유 일수의 변화, 남은 경고만 적는다.

## 작업 행 작성

### 행의 구분

모든 행은 아래 구분 중 하나를 가진다. 구분을 가르는 질문은 "이 행이 늦어지면 우리 팀 책임인가"이다.

| 구분 | 뜻 | 예 |
|---|---|---|
| 작업 (work) | 우리 팀이 수행하고 끝을 통제하는 일 | 설문지 작성, 현황 분석, 보고서 초안 |
| 대기 (wait) | 발주처나 외부 기관이 끝을 정하는 시간 | 발주처 검토, 자료 회신, 설문 회수, 참석자 섭외 |
| 점검 (check) | 날짜가 정해진 보고와 회의 | 착수보고회, 중간보고회, 자문회의, 공청회 |
| 여유 (buffer) | 지연을 흡수하려고 비워 둔 기간 | 마지막 작업과 계약 종료일 사이 |

대기를 작업 행 안에 섞으면 대기가 길어져도 행의 기간이 그대로라서 지연이 보이지 않는다. 대기 행에 남긴 날짜는 발주처 사정에 따른 지연을 설명하는 근거도 된다.

### 행 1개의 크기

- 행 1개는 담당 1명이 끝낼 수 있고 완료를 확인할 수 있는 단위다.
- 작업 행의 기간은 진도 점검 주기 안에서 끝나는 크기로 잡는다. `plan.py`는 28일을 넘는 작업 행에 경고를 낸다. 긴 작업은 중간 산출물을 기준으로 나눈다.
- 매월 반복되는 관리 업무는 행 1개로 두고 `allow_long`을 켠다.
- 단계는 2단(단계와 작업)으로 쓰고, 행 번호는 표의 순번을 쓴다.
- 가까운 달의 작업은 자세히 적고 먼 달의 작업은 묶어서 적는다. 묶은 행은 해당 시점이 오면 나눈다.

### 완료 기준

산출물(완료 기준) 칸에는 "무엇이 어떤 조건을 채우고 누가 확인하는가"를 한 줄로 적는다.

- 예) 기존 계획 대조표의 승계 판정 공란 0건, PM 승인
- 예) 유효 응답이 목표 표본의 80% 이상, PM 승인
- 조건 수치는 과업지시서와 제안서의 값을 쓴다. 문서에 값이 없으면 `[확인 필요]`로 적는다.

### 빠뜨리기 쉬운 행

- (사업관리 단계) 착수 준비, 착수보고, 진도 및 위험 관리, 중간보고, 최종보고, 종료 정리를 첫 단계로 둔다. 이 행들이 없으면 보고와 검수 기간이 일정에서 사라져 계획이 실제보다 짧게 나온다.
- (외부 행사) 자문회의는 요청(작업), 개최(점검), 의견 반영(작업) 3행으로 나눈다. 공청회는 준비(대기 포함), 개최, 결과 정리, 반영 4행으로 나눈다.
- (행사 간격) 첫 자문회의는 주요 조사와 분석이 끝난 직후에 둔다. 자문회의 간격은 4주 이상, 마지막 자문회의는 최종보고 4주 이상 전, 공청회는 최종보고 6주 이상 전에 둔다. 반영할 기간이 없는 행사는 형식으로 끝난다.
- (발주처 검토) 주요 보고서마다 초안 작성, 내부 검토, 제출, 발주처 검토 대기, 의견 반영 순서로 행을 둔다.
- (자료 수집) 수집 계획, 협조 요청, 회신 대기, 정제, 확정으로 나눈다.
- (단계별 정리) 각 단계 끝에 그 단계 산출물을 문서로 확정하는 행을 둔다. 마지막 보고서 행은 편집과 통합만 맡는다. 마지막 보고서 행이 전체 기간의 15%를 넘으면 앞 단계의 정리 행이 빠진 상태다.
- (계약 산출물) 발표자료, 요약본, 데이터베이스, 원자료처럼 계약서에 적힌 산출물은 별도 행으로 둔다. 계약 산출물 목록과 행을 1:1로 대조한다.

### 과업 범위 대조

- 과업지시서의 모든 과업 항목과 계약 산출물은 1개 이상의 행에 대응해야 한다.
- 같은 일이 두 행에 들어가지 않게 한다.
- 과업 범위 밖의 일은 특기사항에 적는다.

### 기간 산정

- 작업 기간은 순수 작업일을 담당자의 참여율로 나눈 값이다. 참여율 50% 인력의 5일 분량 작업은 약 10일이 걸린다.
- 참여율을 모르면 전담 0.8, 과업 2개 병행 0.4, 과업 3개 병행 0.2를 기본값으로 쓴다. 전담 인력도 회의와 행정에 시간을 쓰고, 여러 과업을 오가면 전환에 드는 시간이 더 늘어난다.
- 대기 기간은 기관의 실제 처리 기준을 먼저 쓴다. 기준이 없으면 발주처 검토 1-2주, 기관 자료 회신 2-4주, 자문 회신 1-3주, 섭외 2-3주를 가정하고 비고에 가정이라고 적는다.
- 연구윤리 심의, 통계 작성 승인, 인허가, 공인시험처럼 기관 절차가 있는 행은 착수 직후 해당 기관의 처리 기간을 확인한다.

### 비고의 표준 문구

비고에는 아래 문구를 먼저 쓰고 대응을 함께 적는다.

- (결과 불확실) 설문 회수, 실험 성공처럼 결과를 보장할 수 없는 행이다. 미달 시 수행할 보완 행을 함께 둔다.
- (특정 인력 의존) 특정 전문가나 장비가 없으면 멈추는 행이다. 대체 인력이나 대체 자료를 적는다.
- (납기 직결) 늦어지면 최종 납기가 바로 밀리는 행이다. 월간 점검에서 먼저 확인한다.

## 일정 여유

사람은 작업 기간을 낙관적으로 잡는 경향이 있다. 작업마다 여유를 조금씩 숨기면 그 여유는 늦은 착수나 남은 시간 채우기로 작업 안에서 먼저 사라진다. 그래서 여유를 한곳에 모아 표에 드러내고 소진량을 관리한다.

- (위치) 마지막 작업 행과 계약 종료일 사이에 구분이 "여유"인 행 1개를 둔다. 마지막 작업 행의 종료일이 팀의 내부 목표일이 된다.
- (크기) 과거 유사 과업의 지연 실적이 있으면 그 평균 지연율을 쓴다. 실적이 없으면 전체 기간의 15% 이상을 확보한다. `plan.py`가 비율을 계산하고 기준에 못 미치면 경고한다.
- (작업 기간) 개별 작업 기간은 현실적인 추정치로 적는다. 결과가 불확실한 행은 기본 기간을 유지하고, 미달 시 수행할 보완 행을 따로 둔다. 보완 행의 기간은 기본 행의 30-50%이며, 비율을 고르는 기준은 `references/survey.md`와 `references/skeletons.md`의 해당 항목에 있다.
- (확보가 어려울 때) 15%를 채우지 못하면 선후 관계가 약한 작업 겹치기, 인력 보강, 범위나 납기 협의 중에서 고른다. 선택지별 영향은 `references/recovery.md`에 있다.
- (소진 관리) 최초 계획의 마지막 작업 종료일을 plan.json의 `baseline_last_end`에 기록한다. 매월 진척률과 여유 소진율을 비교하고, 소진율이 진척률보다 크면 `references/recovery.md`의 경로를 검토한다.

## M/M

1 M/M은 1명이 한 달 동안 이 과업에 전념한 분량이다. 참여율 50%로 6개월 참여하면 3.0 M/M이다.

- 투입인력 표는 사람과 월로 이루어진 표다. 월별 값은 그 달 작업 행의 부하에 맞춰 배분한다.
- 한 사람의 월 값은 1.0 이하이고, 사람별 합계는 계약 서류의 M/M과 같아야 한다. `plan.py`가 두 조건을 검산한다.
- 다른 과업의 참여율을 알면 합산이 100%를 넘지 않는지 함께 확인한다.
- 사용자가 M/M 관리가 필요 없다고 하면 `options.mm`을 false로 둔다.

## RACI (선택)

사용자가 요청할 때만 `options.raci`를 true로 두고 작업 행마다 사람별 역할을 적는다.

| 기호 | 역할 |
|---|---|
| R | 작업을 수행하는 사람. 여러 명 가능 |
| A | 결과를 최종 책임지는 사람. 작업마다 정확히 1명 |
| C | 작업 전에 의견을 주는 사람 |
| I | 결과를 공유받는 사람 |

## 오버뷰

`plan.py md`가 아래 순서로 오버뷰를 조립한다. 모델은 plan.json의 `overview` 필드를 채우고, WBS와 점검 일정과 상세 표는 코드가 작업 행에서 만든다.

| 섹션 | 채우는 방법 |
|---|---|
| 기본개요 | 프로젝트명, 기간, 투입 인력은 자동으로 들어간다. 발주처와 계약 형태는 `summary`에 적는다 |
| Why(수혜자 & 니즈 및 문제) | 과업 결과로 혜택을 받는 대상과 과업이 해결할 문제를 자료 근거로 적는다 |
| 프로젝트 목표 | 과업지시서의 과업 목적에서 도출한다. 종료 시점에 달성 여부를 판단할 수 있는 문장으로 적는다 |
| WBS | 자동으로 들어간다. 일정 여유 1줄과 단계별 작업 요약으로 구성된다 |
| 가설 & 솔루션 | 가설은 과업 결과를 좌우하지만 아직 확인되지 않은 판단이다. 솔루션은 가설을 확인하거나 결과에 반영하는 작업이며 WBS 행 이름과 맞춘다 |
| 성공판단기준 | 3줄 이내로 적는다. 종료 시점에 예 또는 아니오로 판정할 수 있는 문장이어야 한다 |
| 보고/자문회의 등 프로젝트 점검 일정 | 구분이 점검인 행에서 자동으로 만든다 |
| 특기사항 | 위험 요인, 범위 변경 가능성, 외부 환경 변화, 자료 간 충돌, `[확인 필요]` 목록을 적는다 |
| WBS 상세, 투입인력 | 전체 행 표와 사람별 월 M/M 표가 자동으로 들어간다 |

- 오버뷰 본문은 보고서 관행에 맞춰 개조식 명사형 종결로 쓰고, 한 줄에는 한 가지 내용만 담는다.
- 오버뷰 본문에서 대등한 명사 2개는 "와", "과" 대신 "및"으로 잇는다. "예산과 인력 확보"는 "예산 및 인력 확보"로 쓴다. 두 명사 사이의 관계(사이, 간, 격차, 차이, 일치, 불일치, 연계, 연동, 정렬, 비교, 구분, 분리, 협력)나 동작의 상대를 나타내는 "와", "과"는 그대로 둔다(예: "현행과 기준의 격차", "유관기관과 공유"). BSC의 "학습과 성장" 같은 관용 명칭의 "와", "과"도 그대로 둔다.
- 오버뷰의 날짜와 수치는 plan.json과 같아야 한다. 문장에 수치를 새로 넣을 때도 plan.json 값을 가져온다.

## 산출 명령

```bash
python scripts/plan.py check plan.json            # 검산만 수행
python scripts/plan.py md   plan.json -o overview.md
python scripts/plan.py csv  plan.json -o wbs.csv   # M/M을 켜면 wbs_mm.csv도 생성
python scripts/plan.py xlsx plan.json -o wbs.xlsx
python scripts/md2pdf.py overview.md -o overview.pdf
```

- `check`, `md`, `csv`에는 추가 패키지가 필요 없다. `xlsx`에는 openpyxl, PDF에는 fpdf2와 markdown-it-py, 문서 변환에는 markitdown이 필요하다. HWPX 변환에는 python-hwpx를 선택적으로 쓴다.
- XLSX는 WBS 시트 1개로 구성하고, M/M을 켜면 투입인력 시트 1개를 더한다. 글자색은 검정, 테두리는 얇은 실선이고 머리글에만 회색 바탕을 쓴다. 간트 머리글은 가로로 쓴다. 위 줄은 월마다 병합한 흰 바탕 칸에 "2026년 3월"처럼 월을 적고, 아래 줄에는 각 주 월요일의 날짜를 적는다. 간트 칸은 수식이라 날짜를 고치면 표시도 따라 바뀐다.
- CSV는 한글이 깨지지 않도록 BOM이 붙은 UTF-8로 저장한다. 다른 PM 도구로 옮길 때 쓴다.
- PDF 스크립트는 설치된 한글 글꼴을 자동으로 찾는다. 글꼴을 찾지 못하면 `--font 글꼴경로`를 지정한다.
- 파일 전달 기능이 있는 환경에서는 만든 파일을 전달하고, 없으면 파일 경로를 안내한다.

## 일정 지연과 위기

사용자가 "일정이 밀렸다", "납기가 위험하다"라고 하거나 여유 소진율이 진척률을 넘으면 `references/recovery.md`를 읽고 경로를 제시한다. 먼저 plan.json을 최신 상태로 고치고 `plan.py check`로 남은 여유를 계산한 뒤 선택지를 비교한다.

## 기존 WBS 검토

사용자가 이미 만든 WBS나 일정표의 검토를 요청하면 `references/review.md`의 순서로 점검한다. 일정 자체를 틀리게 만드는 항목을 먼저 보고 완성도 항목은 그 뒤에 본다.

## 제출 전 점검

- 과업지시서 항목과 계약 산출물이 모두 행에 대응하는가?
- 대기 시간이 작업 행과 분리되어 있는가?
- `plan.py check`의 경고를 처리했거나 남은 경고를 사용자에게 알렸는가?
- 일정 여유 행이 있고 비율이 기준 이상인가?
- `[확인 필요]` 항목을 특기사항에 모았는가?
- 오버뷰 문장의 날짜와 수치가 plan.json과 일치하는가?
