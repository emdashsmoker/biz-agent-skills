# 설계 규칙

온톨로지를 설계하고 점검할 때 쓰는 규칙이다. 사고 모드와 엔진 모드에 같이 적용한다. 규칙은 설계 과정에서 쓰고, 산출물에는 규칙 이름이나 적용 사실을 드러내지 않는다.

## 정의, 기준, 범위

설계는 왜 만드는지, 무엇을 담는지, 어떻게 나누는지부터 정한다. 정의, 기준, 범위를 더 쪼갤 수 없는 단위에서 정하고, 한번 정한 뜻을 작업 끝까지 유지한다. 같은 단어가 중간에 다른 뜻으로 바뀌거나 정의와 기준이 섞이면 분류 결과를 재현할 수 없다.

- 목적(왜), 대상(무엇), 방법(어떻게)을 먼저 적는다
- 정의는 대상이 무엇인지, 기준은 대상을 어떻게 나누는지, 범위는 어디까지 다루는지를 말한다. 세 가지를 한 문장에 섞지 않는다
- 상식, 권위, 유명한 방법론, 유행어로 정의를 대신하지 않는다
- 말을 바꿔 같은 내용을 반복하는 정의는 쓰지 않는다

### 순환 정의

정의하는 문장이 정의 대상 단어를 다시 쓰면 독자에게 새 정보가 전달되지 않는다. 정의 문장에서 정의 대상 단어를 지웠을 때 정의가 성립하지 않으면 순환 정의다. 동의어나 파생어로 돌려 말하는 경우도 순환 정의에 해당한다.

- (순환 정의) "디지털 전환이란 디지털 기술을 활용하여 전환하는 것"
- (순환 정의) "혁신 역량이란 혁신을 수행할 수 있는 역량"
- (고친 정의) "디지털 전환이란 기존 업무 절차를 소프트웨어 기반으로 다시 설계하여 운영 효율을 높이는 활동"

순환 정의를 고칠 때는 상위 개념, 구성요소, 목적, 속성 중 하나 이상을 써서 다시 정의한다.

## 분류

### 분류 전 질문

분류를 시작하기 전에 네 질문에 답한다. 엔진 모드에서는 이 질문이 역량 질문 수집으로 이어진다.

- 이 분류로 어떤 판단을 내리는가
- 분류 대상의 범위는 어디까지인가
- 분류 기준이 하나인가
- 이 분류로 범위 안의 모든 사례를 빠짐없이 배치할 수 있는가

### 분류 기준은 하나

한 분류 안의 항목은 같은 기준으로 나눈다. 기준이 다른 항목이 같은 단계에 섞이면 한 사례가 여러 항목에 걸치거나 어느 항목에도 속하지 않는다.

- (섞인 기준) "기술별, 산업별, 시급성별" 항목이 같은 단계에 나란히 있다
- (고친 분류) 1차 분류를 기술별로 통일하고 2차 분류에서 산업별로 나눈다
- 기준은 분류 목적에 맞춰 시간, 절차, 구성, 인과 중 하나를 고른다
- 기준이 여러 개 필요하면 단계를 나눠 다단계 분류로 만든다
- 기준이 불분명하면 분류하기 전에 기준부터 정한다

### 겹침 점검

한 사례가 두 항목에 동시에 해당하는지 실제 사례를 대입해 확인한다.

- 겹치는 사례가 있으면 항목 경계를 다시 정의하거나 상위 범주로 합친다
- 겹침을 피할 수 없으면 여러 항목에 동시에 속하는 태그 방식으로 바꾸고, 분류 대신 속성을 붙인 것임을 밝힌다

### 빠짐 점검

어떤 항목에도 해당하지 않는 사례가 있는지 확인한다.

- 이 분류에 들어가지 않는 사례가 있는지 스스로 묻는다
- 남는 사례를 "기타"로 묶으면 기타의 비중이 주요 항목보다 작아야 한다
- 기타의 비중이 크면 분류 기준을 다시 설계한다

엔진 모드에서는 겹침 없음과 빠짐 없음을 DisjointUnion 공리 하나로 선언할 수 있고 check_mece로 입력된 개체를 점검할 수 있다.

### 항목 수

- 보고와 의사결정에 쓰는 분류는 같은 단계에 3-4개를 권한다
- 5개를 넘으면 중간 단계가 빠졌는지 확인하고 묶을 수 있는지 검토한다
- 2개로 나눴다면 다른 선택지가 없는지 확인한다 (거짓 딜레마 여부)
- OWL 클래스 계층에서는 직계 하위 클래스가 2개에서 12개 사이인 경우가 흔하다. 하위 클래스가 하나뿐이면 모델링 문제의 신호이고, 12개를 넘으면 중간 범주가 필요한지 검토한다
- 이 수치는 권장값이다. 생물 분류, 산업분류코드, 법률 조항처럼 형제 항목이 많은 분류도 정상 구조로 본다

## 상하 구조

상하 관계는 세 종류로 나뉜다. 종류를 섞으면 상위 항목의 성질이 맞지 않는 하위 항목으로 잘못 이어진다.

### 일종 관계 (is-a)

"X는 Y의 일종인가"를 통과해야 X를 Y 아래에 둔다. 하위 항목은 상위 항목의 성질을 모두 물려받는다.

- (성립) 전기차는 자동차의 일종이다. 이동수단이고 바퀴가 있다는 자동차의 성질이 전기차에도 성립한다
- (불성립) 배터리는 전기차의 부품이므로 일종 관계 시험을 통과하지 못한다
- 상위 항목의 성질이 하위 항목에서 성립하지 않으면 일종 관계가 아니다

### 부분 관계 (part-of)

"X는 Y의 부분인가"는 일종 관계와 다른 질문이다.

- 전략과제는 전략을 이루는 부분이다. "전략과제는 전략의 일종인가"를 물으면 성립하지 않는다
- 구성요소를 하위 분류로 두면 상위 성질이 잘못 이어진다
- 목차를 짤 때도 하위 항목이 상위 항목의 일종인지 부분인지 구별한다

### 보유 관계 (has-a)

개체가 어떤 속성을 가진 관계는 일종 관계나 부분 관계와 구별한다. "프로젝트는 예산을 가진다"에서 예산은 프로젝트가 가진 속성이다. 속성을 하위 분류로 두면 구조가 틀어진다.

### 깊이

- 실무에서는 3단계 이내를 권한다
- 4단계 이상이면 중간 단계가 정말 필요한지 다시 본다. 단계가 깊을수록 상위 성질이 하위에서 성립하는지 확인할 부담이 커진다
- 생물 분류나 행정구역처럼 깊은 체계도 정상 구조로 본다

## 관계

### 방향

관계에는 방향이 있다. "A가 B에 영향을 준다"와 "B가 A에 영향을 준다"는 서로 다르며 각각 근거가 필요하다. 방향을 밝히지 않은 관계 서술은 모호하다.

### 유형

"관련이 있다"로 뭉뚱그리지 않고 관계의 유형을 정한다.

| 유형 | 뜻 | 확인할 것 |
|---|---|---|
| 인과 | A가 일어나서 B가 일어난다 | 시간 순서와 작동 방식 |
| 상관 | A와 B가 함께 변한다 | 인과로 단정하지 않는다 |
| 의존 | A가 없으면 B가 있을 수 없다 | 의존 방향 |
| 연관 | A와 B가 관련된다 | 관련의 구체적 성격 |

### 수량 제약

- 1:1, 1:N, N:M 중 무엇인지 정한다
- 반드시 있어야 하는 관계인지 선택적인 관계인지 정한다
- 정한 제약이 현실에 맞는지 실제 사례로 확인한다

엔진 모드에서 방향과 수량 제약은 속성 특성(전이, 함수형, 대칭, 비대칭, 비반사)과 수량 공리로 옮긴다. 방법은 references/axiom-patterns.md에 있다.

## 모르는 것의 처리

### 개방 세계 가정

명시되지 않은 사실은 미지로 처리한다. "확인되지 않음"과 "존재하지 않음"을 구별하고, 정보가 없다는 사실을 부정의 근거로 쓰지 않는다. OWL도 같은 가정을 따른다.

- (잘못된 추론) "해당 기업의 ESG 보고서가 검색되지 않았으므로 ESG 활동을 하지 않는 것으로 판단"
- (고친 서술) "해당 기업의 ESG 보고서가 확인되지 않아 ESG 활동 여부는 미확인"

### 폐쇄 세계 전환

전수 조사가 끝난 범위에서만 "없다"고 판단한다.

- 셀 수 있는 유한 집합을 빠짐없이 조사한 경우에만 부재를 단정한다
- 열거가 불완전하거나 조사 범위가 제한되면 미지로 둔다
- 폐쇄 세계로 전환할 때는 조사 범위와 완전하다고 볼 근거를 밝힌다

엔진 모드에서는 이 규칙이 세 가지로 나타난다.

- check 함수와 SPARQL 점검은 입력된 사실만 읽는다. 결과에 나온 미연결 항목은 미입력 후보로 보고한다
- OWL 추론기는 빠진 연결을 문제로 판정하지 않는다. 최소 연결 수 공리와 Not 조건 자동 분류는 입력되지 않은 연결을 위반으로 잡지 못한다
- 사용자가 어떤 범위의 입력이 완전하다고 확인하면 close_world_scope로 그 범위를 폐쇄 세계로 선언한 뒤 추론기를 실행한다

## 구조 점검

### 현실 구조 먼저

분석 방법이나 출력 형식에 맞춰 현실의 분류를 바꾸지 않는다. "차트로 그리기 편하다"나 "이 방법론에 맞추려면 이렇게 나눠야 한다"는 분류 기준이 될 수 없다. 현실의 구조를 먼저 파악한 뒤 표현 방식을 정한다. 엔진 모드에서는 쿼리나 추론기가 돌아가도록 속성을 더하지 않는다.

### 고립 항목

모든 항목은 다른 항목과 관계 하나 이상으로 이어져야 한다.

- 다른 항목과 관계가 없는 항목이 있으면 소속을 다시 검토한다
- 고립이 정당하면 그 사유(새 영역, 예외 등)를 확인한다
- 구조도에서 연결선이 없는 항목은 빠진 관계가 있거나 그 구조도에 속하지 않는 항목이다

### 쓰이지 않는 분류

정의한 모든 분류 항목에는 사례가 하나 이상 있어야 한다.

- 사례가 없는 빈 항목은 삭제 대상이다
- 앞으로 채워질 항목이면 그 근거를 밝힌다
- 빈 항목이 있다는 것 자체가 분류 기준이 맞지 않는다는 신호일 수 있다
- 엔진 모드에서는 모든 클래스가 객체 속성 하나 이상의 domain이나 range로 참여해야 한다

### 누적 연결

기존 분류에 새 항목을 더할 때는 기존 항목과의 관계를 밝힌다. 새 항목만 따로 붙이면 전체 구성이 끊어진다.

- 새 항목이 기존 항목과 어떤 관계(상위, 하위, 동등, 의존, 선후)인지 적는다
- 새 항목 때문에 기존 항목의 범위나 경계가 바뀌는지 확인한다
- 새 항목 때문에 기존 항목 사이의 겹침 없음이 깨지면 분류 기준을 다시 설계한다
- (끊어진 추가) "단기, 중기, 장기"로 나눈 과제 목록에 "긴급 과제"를 더하면서 관계를 밝히지 않는다. "긴급"이 시간 기준인지 우선순위 기준인지 알 수 없다
- (이어진 추가) "긴급"이 우선순위 기준임을 밝히고 별도 분류 기준으로 두거나, 기존 시간 기준 과제에 우선순위 속성을 붙인다
- 엔진 모드에서는 온톨로지를 매번 버리지 않고 기존 OWL을 불러와 확장하며, 새 개체를 기존 개체와 관계로 잇는다

### 버전과 메타데이터

- 누적해서 확장할 때는 이전 버전과 무엇이 달라졌는지 파악할 수 있어야 한다 (엔진 모드의 diff_ontology)
- 이름(label), 버전(versionInfo), 설명(comment) 메타데이터를 기록해 외부 도구에서도 읽히게 한다

## 예시

### 예시 1. 섞인 기준과 겹침

(고치기 전)

```markdown
## 공공기관 정보화 사업의 문제점
- 예산 편성의 비효율
- 전문 인력 부족
- 부서 간 칸막이
- 레거시 시스템 노후화
- 정보보호 미흡
- 성과 평가 체계 부재
- 벤더 종속
```

7개 항목이 같은 단계에 있고 기준이 섞였다. 예산은 자원, 칸막이는 조직, 노후화는 기술 측면의 사안이다. 인력 부족과 성과 평가 부재는 인력 운영 관점에서 겹칠 수 있다.

(고친 뒤)

```markdown
## 공공기관 정보화 사업의 문제점
- (자원 배분) 정보화 예산이 유지보수에 쏠려 신규 사업에 투자할 여력이 부족하고, 전문 인력을 내부에서 확보하기 어려워 외주 의존이 굳어졌다
- (기술 기반) 노후 시스템이 신규 시스템과 연동되지 않고 보안 취약점이 쌓였으며, 특정 공급사의 독자 규격 때문에 교체 비용이 크다
- (조직 운영) 부서별 개별 발주로 기관 전체 정보화 전략과 어긋나고, 정보화 성과를 측정할 기관 차원의 평가 기준이 없다
```

기준을 "문제가 생기는 영역" 하나로 통일했다. 정보보호 미흡과 공급사 종속은 기술 기반으로, 성과 평가 부재는 조직 운영으로 옮겨 겹침을 없앴다.

### 예시 2. 일종 관계와 부분 관계의 혼동

(고치기 전)

```markdown
## 스마트시티 추진 체계
- 스마트시티: 스마트 교통, 스마트 에너지, 스마트 안전, 통합 플랫폼, 도시 데이터 허브, 시민 참여 거버넌스, IoT 센서 네트워크
```

스마트 교통은 스마트시티 서비스의 일종이다. 통합 플랫폼과 IoT 센서 네트워크는 스마트시티를 이루는 부분이다. 시민 참여 거버넌스는 스마트시티가 가진 운영 체계다. 세 관계가 한 목록에 섞였다.

(고친 뒤)

```markdown
### 서비스 영역 (스마트시티 서비스의 유형)
- (스마트 교통) 실시간 교통 정보로 신호를 제어하고 대중교통 운행을 조정한다
- (스마트 에너지) 건물 에너지 소비를 계측하고 분산 에너지 자원을 관리한다
- (스마트 안전) CCTV 영상 분석으로 재난을 일찍 감지하고 긴급 대응한다

### 인프라 구성 (스마트시티를 이루는 기술 요소)
- (통합 플랫폼) 서비스 사이의 데이터 연계와 통합 관제를 맡는 소프트웨어
- (도시 데이터 허브) 도시 운영 데이터를 모으고 저장하고 개방하는 데이터 저장소
- (IoT 센서 네트워크) 현장 데이터를 모아 플랫폼에 보내는 장치망

### 운영 체계 (스마트시티 운영을 위한 의사결정 구조)
- (시민 참여 거버넌스) 서비스 기획과 평가 단계에 시민 의견을 반영하는 절차
```

각 절 제목의 괄호에 관계의 종류를 자연어로 적었다. is-a, part-of 같은 용어는 산출물에 쓰지 않는다.

### 예시 3. 정보 부재를 부정으로 바꾼 서술

(고치기 전)

```markdown
## 국내 제조업 AI 도입 현황
- (대기업) 자체 AI 연구소를 운영하며 공정 최적화에 AI를 적극 활용
- (중견기업) 일부가 품질 검사 자동화에 AI를 도입했으나 도입률은 낮음
- (중소기업) AI 도입 사례가 거의 없고 인식 수준도 미흡
- (소상공인) AI 도입 역량이 전무하여 정책 지원 대상에서 제외하는 것이 현실적
```

중소기업의 "사례가 거의 없음"은 체계적 조사 근거 없이 부재를 단정했다. 소상공인의 "역량 전무"는 정보 부재를 부정 근거로 쓴 뒤 정책 방향까지 정했다. 결론에 맞춰 규모 분류를 거꾸로 짠 것일 가능성도 있다.

(고친 뒤)

```markdown
## 국내 제조업 AI 도입 현황
- (대기업) 자체 AI 연구소를 운영하며 공정 최적화와 품질 예측에 AI를 쓰는 사례가 다수 보고되었고, 기업별 도입 범위와 성과는 공개 자료마다 다르다
- (중견기업) 품질 검사 자동화 등 특정 공정에 AI를 도입한 사례가 확인되며, 도입률은 체계적 조사 결과를 따로 확인해야 한다
- (중소기업) 전수 조사 결과가 확인되지 않아 도입 수준 판단을 유보하며, 정부 지원 사업을 통한 도입 시도 사례는 있다
- (소상공인) 도입 역량에 대한 체계적 조사 결과가 확인되지 않아 판단을 유보하며, 정책 대상 제외 여부는 조사 결과를 확보한 뒤 판단할 수 있다
```

### 예시 4. 순환 정의

(고치기 전)

```markdown
- (디지털 전환) 디지털 기술을 활용한 전환 활동
- (데이터 거버넌스) 데이터를 거버넌스하는 체계
- (AI 역량) AI를 수행할 수 있는 역량
- (클라우드 네이티브) 클라우드에 네이티브한 방식으로 설계된 아키텍처
```

(고친 뒤)

```markdown
- (디지털 전환) 기존 업무 절차를 소프트웨어 기반으로 다시 설계하여 운영 효율을 높이는 활동
- (데이터 거버넌스) 조직 안 데이터의 품질, 접근 권한, 생애주기를 관리하는 정책과 절차
- (AI 역량) 업무 목적에 맞는 AI 모델을 고르고 운영 환경에 적용할 수 있는 조직의 기술 준비 수준
- (클라우드 네이티브) 컨테이너, 마이크로서비스, 선언형 API를 바탕으로 확장성과 복원력을 갖추도록 설계한 아키텍처
```

정의 대상 단어를 지우고 상위 개념(활동, 정책과 절차, 준비 수준, 아키텍처), 구성요소(소프트웨어, 컨테이너), 목적(운영 효율, 확장성)으로 다시 정의했다.

### 예시 5. 새 항목의 고립

(고치기 전)

```markdown
## 디지털 전환 추진 과제 (2차)
- (단기) 업무 절차 자동화
- (중기) 데이터 분석 환경 구축
- (장기) AI 기반 의사결정 체계 도입
- (신규) 보안 강화
- (신규) 조직문화 혁신
- (신규) ESG 데이터 관리
```

새 과제 세 건이 기존 시간 기준과 어떤 관계인지 알 수 없다. 보안 강화가 단기인지 중기인지, ESG 데이터 관리가 데이터 분석 환경과 선후 관계인지 동등 관계인지 드러나지 않는다.

(고친 뒤)

```markdown
## 디지털 전환 추진 과제 (2차)
- (단기) 업무 절차 자동화와 함께 자동화 대상 시스템의 보안 요건을 먼저 정의한다
- (중기) 데이터 분석 환경을 구축하면서 ESG 데이터를 수집 대상에 포함하고, 부서 간 데이터 공유 기준을 정해 조직문화 전환을 함께 추진한다
- (장기) 단기와 중기에 확보한 보안 정책과 데이터 분석 환경을 전제로 AI 기반 의사결정 체계를 설계한다
```

시간 기준을 유지하면서 새 과제를 해당 시점의 기존 과제에 의존 관계와 선후 관계로 이었다.

## 점검 목록

분류, 묶음, 구조, 판단이 들어간 산출물은 아래를 점검한다.

- 분류 기준이 하나로 통일되었는가
- 항목 사이에 겹치는 사례가 없는가
- 어떤 항목에도 들어가지 않는 사례가 없는가
- 같은 단계의 항목이 5개를 넘으면 중간 단계가 빠졌는지 확인했는가
- 상하 관계가 일종 관계인지 부분 관계인지 구별되었는가
- 일종 관계에서 상위 성질이 하위에서 성립하는가
- 정보 부재를 부정의 근거로 쓰지 않았는가
- 분석 도구나 출력 형식에 맞춰 분류를 바꾸지 않았는가
- 다른 항목과 관계가 없는 고립 항목이 없는가
- 사례가 없는 빈 분류가 없는가
- 관계의 방향과 유형이 정해졌는가
- "기타"의 비중이 주요 항목보다 작은가
- 정의 문장에 정의 대상 단어가 다시 나오지 않는가
- 새 항목이 기존 항목과 관계로 이어졌는가

## 예외

- 사용자가 분류 기준을 직접 정하면 그 기준을 먼저 적용하고, 구조 결함을 발견하면 알린다
- 코드는 설계 구조와 설명 글에 적용하고 코드 문법은 대상에서 제외한다
- 순위나 목록처럼 단순 나열을 요청하면 분류와 구별하며 이 규칙을 강제하지 않는다
