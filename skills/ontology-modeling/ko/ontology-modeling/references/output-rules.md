# 보고 규칙

보고서는 독자에게 필요한 정보 자체로 채운다. 글의 존재, 작성자의 존재, 작성 과정이 독자에게 보이지 않게 쓴다. 이 규칙은 문장 길이, 종결 형태, 문체, 거시 구조, 마크다운 형식, 분량, 어휘 선호에는 관여하지 않는다.

## 메타 서술

메타 서술은 독자의 정보 요구를 채우는 본문 대신 글 자체, 작성 과정, 작성자의 내부 상태, 사용자와의 상호작용, 사용 도구처럼 본문 바깥을 서술하는 문장이다. 작성자가 자기 행위를 보고하거나, 정당화하거나, 예고하거나, 돌아보는 문장이 여기에 해당한다.

### 판별 테스트

모든 문장은 쓰기 전에 네 가지 테스트를 통과해야 한다. 하나라도 걸리면 그 문장을 지우거나 본문 내용으로 바꾼다.

- (주어 테스트) 문장의 실제 주어가 글 자체("본 보고서는", "본 절에서는"), 작성자("분석한 결과"), 작성 행위("살펴보면", "정리하면"), 사용자 요청("요청하신"), 사용 도구나 방법론이면 메타 서술이다. 주어가 생략되었으면 복원해서 판단한다
- (삭제 테스트) 그 문장을 지워도 독자가 받는 정보가 줄지 않으면 메타 서술이다
- (수혜자 테스트) 그 문장의 수혜자가 독자 대신 작성자(자기 정당화, 자기 보호, 자기 과시)이면 메타 서술이다
- (응대 기능 테스트) 그 문장이 정보 전달 없이 응대 의례(인사, 칭찬, 확인, 안내, 유도)만 하면 메타 서술이다

주어 테스트가 가장 기계적으로 적용되므로 먼저 적용한다. 주어 테스트를 통과해도 나머지 테스트에 걸리면 메타 서술이다. 네 테스트를 모두 통과한 문장만 쓴다.

### 메타 서술이 생기는 이유

아래 동기는 모두 독자의 정보 요구와 무관하다. 이 동기가 느껴지는 문장을 먼저 의심한다.

- (분량 채우기) 본문 내용이 부족할 때 메타 서술로 분량을 채운다
- (구조 미루기) 내용을 직접 구조화하는 대신 "먼저 A를 보고 다음으로 B를" 식으로 예고만 한다
- (책임 분산) "완벽하지 않을 수 있으나"로 품질 책임을 미리 피한다
- (호감 확보) "도움이 되셨길"로 독자와의 관계를 관리한다
- (권위 연출) "철저히 분석한 결과"로 작업 품질을 스스로 선언한다
- (요청 확인) "요청하신 대로"로 지시를 정확히 따랐음을 증명한다
- (내부 정보 노출) 독자가 존재조차 모르는 작성자의 시스템, 제약, 지침, 도구, 작업 과정을 드러내 혼란을 준다

### 우회 형태

직접적인 메타 서술을 막으면 우회 형태가 생긴다. 판별 테스트는 기능을 보므로 우회 형태에도 그대로 적용한다.

- (주어 숨기기) "분석 결과를 정리하면", "파악된 현황은", "도출된 결론은"처럼 주어를 생략하거나 수동태로 바꾼다. 주어를 복원했을 때 작성자이면 메타 서술이다
- (내용 섞기) "다양한 관점에서 검토한 결과 A가 적합하다"처럼 메타 서술에 본문을 조금 섞는다. 메타 부분만 지우고 "A가 적합하다"만 남긴다
- (겸양 위장) "부족하지만 정리해 보면", "제한된 정보이지만"처럼 겸손을 가장한다. 겸양의 수혜자가 작성자이면 메타 서술이다
- (질문 위장) "그렇다면 어떻게 접근해야 할까?", "무엇이 핵심일까?"처럼 수사 의문문으로 바꾼다. 질문을 지우고 답만 쓴다
- (접속사 위장) "앞서 살펴본 바와 같이 A는 B다", "이상의 분석에 기초하여 D를 제안한다"처럼 접속 표현에 붙인다. 접속 부분만 지운다

## 원칙명과 자기 정당화

설계 규칙과 논증 규칙은 작업 과정에서 지키는 기준이다. 산출물에는 그 결과만 보이게 한다.

- 방법론과 원칙의 이름을 직접 쓰지 않는다 (So What, Why So, MECE, 오류 명칭, 편향 명칭, Disjoint Classes, Open World Assumption, Connected Graph 등)
- 이름을 생략하고 정의를 풀어 쓰는 우회도 하지 않는다 (예: "각 항목은 하나의 기준에서 작동하고 항목 사이에 중복이 없다")
- 자기 분류, 추론, 구조가 원칙을 충족한다는 자평을 쓰지 않는다 (예: "본 분류는 누락 없이 전체를 포괄한다", "각 항목은 상호 배타적이다")
- 기본 원리에서 따져 보았다는 식으로 사고 방식의 적용 사실을 알리지 않는다
- "X가 아니라 Y", "X가 아닌 Y가 아닌 Z" 같은 대비 구문으로 쓰지 않고 Y를 직접 쓴다
- 사용자가 요청하지 않은 자기 점검 절(분석 한계, 검토 시 유의사항, 방법론)을 더하지 않는다
- 사용자가 요청한 범위를 넘는 작업을 스스로 늘리지 않는다
- 이 규칙과 무관한 외부 기준의 인용은 그대로 쓴다 (예: 회계 기준에 따라 작성, 개정 지침에 따라 운영)
- 분석 대상에 대한 논리 평가는 사용자가 요청하면 쓰고, 자기 산출물에 대한 논리 자평은 사용자가 요청할 때만 쓴다

## 반례와 역규칙

반례 탐색은 겹침, 빠짐, 일반화를 점검하는 과정에서 한다. 보고서에 반례를 늘어놓으면 결론이 흐려지고 독자가 확인할 일만 늘어난다.

- 보고서에는 발견 사항에 해당하는 반례(예: 두 분류에 동시에 속한 개체, 규칙과 충돌한 개체)와 사용자가 요청한 반례만 쓴다
- 사용자가 요청하지 않은 역규칙, 역논리, 역설, 반례를 판단 근거 없이 덧붙이지 않는다
- 반례를 쓸 때는 원자료나 코드 결과로 실제 존재를 확인한 것만 쓴다

| 분석 용어 그대로 | 사실 서술로 |
|---|---|
| 커버리지 미달 3건 탐지 | 제시된 추진전략 중 사업목표와의 연결이 확인되지 않는 항목이 3건 있음 |
| 인과 체인 단절 발견 | 주요 위험요인의 영향이 실행계획 단계까지 반영되지 않음 |
| 파이프라인 무결성 위반 | 기획 단계의 산출물이 실행 단계에서 쓰이지 않는 구간이 있음 |
| 정합성 점검 실패 | 전략 A가 참조하는 기회요인 B가 외부환경 분석에서 도출되지 않은 항목임 |

## 프로세스 출력 형식

사용자가 절차나 작업 계획을 산출물로 요청하면 SKILL.md의 진행 원칙(필수성, 실행 가능성, 비례성)을 통과한 단계만 아래 형식으로 쓴다. 사용자가 다른 형식을 정하면 그 형식을 따른다.

```
## Module N. 모듈명
* 목적 : 1줄

| Task | Input | 내용 | Output |
|------|-------|------|--------|
| N-1. Task명 | 입력 자료 | 수행 행동 | 산출물 |
| N-2. Task명 | 입력 자료 | 수행 행동 | 산출물 |
```

- 모듈 수는 세 조건을 충족하는 범위에서 정한다
- 내용 칸에는 수행 행동만 쓴다
- 프로세스의 의의, 배경, 기대효과는 쓰지 않는다. "이 프로세스는 OO을 목표로 합니다", "본 단계에서는 OO을 수행합니다", "이를 통해 OO을 달성할 수 있습니다", "OO하는 것이 중요합니다", "다음과 같은 프로세스를 제안합니다", "효율적인 진행을 위해"는 모두 메타 서술이다

## 예시

### 예시 1. 보고서 서두

(고치기 전)

```markdown
## 개요
- 본 보고서는 중소기업의 클라우드 전환 현황을 분석하고 정책적 시사점을 도출하는 것을 목적으로 함
- 먼저 현황을 살펴보고 다음으로 문제점을 분석한 후 마지막으로 개선 방향을 제시
- 클라우드 컴퓨팅이란 인터넷으로 컴퓨팅 자원을 제공하는 기술로서 IaaS, PaaS, SaaS로 구분됨
- 이러한 맥락에서 클라우드 전환은 매우 중요한 의미를 가짐
- 주신 자료를 철저히 검토하고 다양한 관점에서 분석한 결과를 아래와 같이 정리하였음
```

(고친 뒤)

```markdown
## 중소기업 클라우드 전환 현황
- 중소기업의 클라우드 전환 필요성 인식은 넓어졌으나 실제 전환율은 낮은 수준에 머물러 있다

- 전환한 기업도 단순 인프라 이전에 머무는 경우가 많아 업무 방식 개선까지 이어진 사례는 드물다
- 전환 이후 업무 절차를 다시 설계하지 않으면 비용 절감 효과도 작다
```

## 적용 방식

- (작성 모드) 새 글을 쓸 때 판별 테스트를 미리 적용해 메타 서술이 나오지 않게 한다. 결과물에 이 규칙의 적용 사실을 드러내지 않는다
- (교정 모드) 기존 글에서 메타 서술을 찾아 지우고 본문 내용만 남긴다. 교정한 유형을 간단히 요약한 뒤 교정 결과를 낸다
- 판별 원리, 유형 목록, 판별 테스트를 산출물에 드러내지 않는다
- 다른 문체 지침과 함께 쓸 때 그 지침이 허용하는 표현이라도 판별 테스트에 걸리면 이 규칙을 따른다

## 예외

- 사용자가 메타 서술을 명시적으로 요청하면 쓴다 (예: "보고서 목적을 서두에 적어 줘")
- 학술 논문의 연구 목적, 연구 방법 절처럼 장르 관례상 필요한 메타 서술은 관례를 따른다
- 사용자가 한계, 유의사항, 방법론 설명을 요청하면 쓴다

## 산출 전 점검

- 글 자체, 작성자, 작성 행위, 사용자 요청, 사용 도구가 주어인 문장이 없는가
- 지워도 정보가 줄지 않는 문장이 없는가
- 수혜자가 작성자인 문장이 없는가
- 정보 없이 응대 의례만 하는 문장이 없는가
- 주어 숨기기, 내용 섞기, 겸양 위장 같은 우회 형태가 없는가
- 원칙명 노출, 자기 정당화, 대비 구문, 요청받지 않은 반례가 없는가
- 첫 문장이 인사, 요청 반복, 과정 예고 대신 본문 내용으로 시작하는가
- 마지막 문장이 인사, 추가 질문 권유, 면책 대신 본문 내용으로 끝나는가
