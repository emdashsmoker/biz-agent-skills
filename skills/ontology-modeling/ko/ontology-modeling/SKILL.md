# 온톨로지 모델링

분석 대상의 개념, 분류, 관계, 사실을 겹침과 빠짐 없이 정리하고, 그 결과물이 답해야 할 질문에 실제로 답하는지 확인한다. LLM은 자연어 해석과 설계를 맡고, 규칙 점검과 추론은 Python 코드가 맡는다. 해석이 들어간 결정은 사용자와 합의한 뒤 반영한다.

작업 방식은 두 가지다. 사고 모드는 코드 없이 정의 목록, 분류표, 관계 서술을 작성하고 글이나 기획안의 논리를 살핀다. 엔진 모드는 OWL 파일을 만든 뒤 SPARQL 질의와 OWL 추론기로 확인한다. 두 모드는 같은 설계 규칙과 보고 규칙을 따른다.

## 용어

아래 용어는 이 스킬과 참조 파일 전체에서 같은 뜻으로 쓴다.

| 용어 | 뜻 |
|---|---|
| 온톨로지 | 분석 대상의 개념, 분류, 관계, 사실을 정리한 구조. 사고 모드에서는 글 속 정의와 분류표로, 엔진 모드에서는 OWL 파일로 표현한다 |
| 클래스 | 같은 성질을 공유하는 개체의 묶음 (예: 전략, 목표) |
| 개체 | 클래스에 속하는 개별 대상 (예: 특정 전략 하나) |
| 객체 속성 | 개체와 개체를 잇는 관계 (예: 전략이 목표를 달성한다) |
| 데이터 속성 | 개체에 붙는 값 (예: 예산 금액) |
| TBox | 클래스와 속성의 정의 (스키마) |
| ABox | 개체와 개체 사이의 연결, 개체의 값 (사실) |
| 공리 | 추론기가 사용하는 제약 선언 (예: 두 클래스는 겹치지 않는다) |
| 역량 질문(CQ) | 온톨로지가 답할 수 있어야 하는 구체적 질문 |
| 사실 속성 | 원출처를 보면 누구나 동의할 수 있는 값 (이름, 수치, 소속, 날짜 등) |
| 판정 속성 | 해석을 거쳐 붙인 값 (예: A는 B에 해당한다) |
| 미입력 후보 | 입력된 사실 안에서 연결이 확인되지 않은 항목. 실제 존재 여부는 미지로 둔다 |
| 위반 | 명시한 규칙이나 공리와 입력된 사실이 충돌하는 항목 |

## 진행 원칙

단계가 늘어날수록 사용자가 확인할 일과 작업 비용이 함께 늘어난다. 그래서 모든 단계는 아래 세 조건을 모두 충족할 때만 수행하고, 하나라도 충족하지 못하면 삭제하거나 다른 단계에 합친다.

- (필수성) 이 단계가 없으면 산출물 품질이 실제로 떨어진다
- (실행 가능성) 사용자가 지금 가진 자원으로 실행할 수 있다. 제약이 불분명하면 먼저 확인한다
- (비례성) 이 단계에 드는 노력이 얻는 가치보다 작다

세 조건은 다음 방식으로 적용한다.

- 사용자가 이미 정한 문제, 방향, 경로, 역량 질문은 다시 묻지 않는다. 같은 대화에서 이미 합의한 내용도 다시 정하지 않는다
- 한 번의 행동으로 끝나는 작업을 여러 단계로 나누지 않는다
- 사용자에게 확인할 질문은 한 번의 질의로 묶는다
- 법률, 규정, 안전처럼 민감도가 높은 단계는 세 조건과 관계없이 유지한다
- 엔진 모드의 합의 지점(TBox 설계안, ABox 입력 계획, 판정 속성 입력, SWRL 규칙 적용)도 유지한다. 이 지점을 건너뛰면 LLM의 해석이 사실처럼 저장되기 때문이다
- 사용자가 상세 프로세스나 전체 단계를 명시적으로 요청하면 이 원칙을 풀고, 사용자가 제약 조건을 밝히면 그 조건으로 실행 가능성을 판단한다

## 작업 순서

작업은 방식 결정, 설계, 구축, 점검, 보고 순서로 진행한다. 각 단계에서 필요한 참조 파일만 읽는다.

| 단계 | 하는 일 | 사고 모드 | 엔진 모드 | 참조 파일 |
|---|---|---|---|---|
| 0. 방식 결정 | 모드와 경로를 정하고 역량 질문을 모은다 | 분류 전 질문에 답한다 | 경로 선택, 역량 질문 수집 | 이 문서 |
| 1. 설계 | 목적, 정의, 기준, 범위, 분류, 관계를 설계한다 | 적용 | 적용 | modeling-rules.md |
| 2. 구축 | 설계한 구조를 작성한다 | 정의 목록, 분류표, 관계 서술 | TBox, ABox, 공리 구축 | tbox-templates.md, axiom-patterns.md |
| 3. 점검 | 구조와 논증을 점검한다 | 구조 점검, 논증 점검 | 구조 점검, 논증 점검, check 함수, SPARQL, 추론기 | reasoning-rules.md, check-functions.md, sparql-patterns.md |
| 4. 보고 | 결과를 독자에게 전달한다 | 적용 | 적용, 파일 저장, Mermaid 다이어그램 | output-rules.md |

## 0단계. 방식 결정

### 모드 판단

같은 대화에서 이미 모드와 경로를 합의했다면 이 단계를 건너뛰고 설계나 구축으로 간다.

아래 여섯 가지 중 하나 이상에 해당하면 엔진 모드의 가치가 크다.

- (지식 구조화) 여러 개체 사이의 관계를 정형화해 한눈에 파악해야 한다
- (관계 탐색) 원인과 결과의 연쇄, 경로 추적, 역추적, 영향 범위 산출이 필요하다
- (패턴 발견) 많은 개체에서 같은 대상 참조, 미연결, 순환 같은 구조 패턴을 찾아야 한다
- (자동 분류) 개체의 속성값 조합으로 소속 유형을 판별해야 한다
- (구조 점검) 교차 참조, 허용 조합 규칙, 포괄 여부, 순서 단절을 전수 조사해야 한다
- (누적 지식) 복잡한 도메인 지식을 여러 턴에 걸쳐 쌓고 다시 써야 한다

아래에 해당하면 사고 모드가 효율적일 가능성이 높다.

- 개체 사이에 관계가 없는 독립 항목의 나열이다
- 자연어 해석만으로 충분한 정성 판단이다
- 관계 구조가 단순하다 (클래스 5개 미만이면서 속성 3개 미만)

요청이 OWL 파일, TBox, SPARQL, 추론기를 명시하면 엔진 모드로 진행한다. 요청이 글이나 기획안의 분류와 논증 점검이면 사고 모드로 진행한다. 엔진 모드의 신호가 없는데 사용자가 온톨로지 구축을 원하면 거절하지 않고 두 선택지를 제시한다. 선택지는 구축 없이 직접 분석하는 방식과 온톨로지를 구축한 뒤 추론하는 방식이며, 예상 소요와 분석 범위의 차이를 함께 알린다.

사고 모드에서는 분류를 시작하기 전에 네 가지 질문에 답한다. 이 분류로 어떤 판단을 내리는가, 대상 범위는 어디까지인가, 분류 기준이 하나인가, 범위 안의 모든 사례를 빠짐없이 배치할 수 있는가. 요청에서 답이 드러나지 않을 때만 사용자에게 묻는다.

### 엔진 모드 경로

| 경로 | 구축 | 분석 | 분석 시점 | 맞는 상황 |
|:---:|:---:|:---:|---|---|
| A | O | X | 없음 | 지식 구조화만 필요하다 |
| B | O | O | ABox 구축과 같은 턴 (원턴을 고르면 전체를 한 턴에) | 결과까지 빠르게 확인하고 싶다 |
| C | O | O | ABox 구축 후 별도 턴 | 구축 결과를 충분히 검토한 뒤 분석하고 싶다 |
| D | X | O | 구축 없이 바로 | 기존 OWL 파일에 질의만 한다 |

- (경로 A) 1턴에 TBox를 만들고 Mermaid 클래스 다이어그램과 OWL 파일을 제시한 뒤 구조 검토를 요청한다. 2턴에 ABox를 만들고 Mermaid 개체 그래프를 제시해 승인받은 뒤 OWL을 저장하고 끝낸다. SPARQL 질의 제안, suggest_sparql_queries, suggest_axioms를 포함한 모든 분석을 생략한다
- (경로 B) TBox와 ABox를 나눌지 사용자에게 묻는다. 나누면 TBox 승인 뒤 ABox 구축과 분석을 같은 턴에 수행한다. 원턴은 사용자가 TBox 사전 확인 없이 빠른 결과를 원한다고 밝힌 경우에만 허용하며, 이때도 설계 단계의 현실 구조 우선 원칙은 그대로 적용한다
- (경로 C) 1턴 TBox, 2턴 ABox, 3턴 분석으로 진행한다. 구축 턴에서는 모든 분석을 생략한다. 판정 속성이 많거나 만들어진 온톨로지를 본 뒤 분석 범위를 정하고 싶을 때 권한다
- (경로 D) 기존 OWL을 불러온 뒤 구축을 건너뛰고 점검 단계로 간다

요청에서 경로가 드러나면 묻지 않고 그 경로로 진행하며, 고른 경로를 한 줄로 알린다. 드러나지 않으면 위 표를 보여 주고 묻는다. 각 경로가 무엇을 하고 무엇을 생략하는지 사용자가 이해한 상태에서 고르게 한다.

### 추론 방향과 역량 질문

경로 A가 아니면 경로 질의와 같은 메시지에서 세 가지를 함께 묻는다.

- (활용 목적) 지식 구조화, 관계 탐색, 패턴 발견, 자동 분류, 구조 점검 중 무엇인가
- (기대 산출) 지식 그래프, 경로 탐색 결과, 위반 목록, 자동 분류 목록 중 무엇인가
- (범위) 전수 분석인가, 특정 부분 집중인가

역량 질문은 모든 경로에서 수집한다. 경로 A도 TBox 설계 근거를 남기고 나중에 다시 쓰기 위해 수집한다. 역량 질문은 TBox에서 필요한 개념이 빠지지 않게 하는 기준으로 쓴다. 역량 질문 없이 구축하면 어떤 클래스를 왜 포함했는지 설명할 수 없다.

- 먼저 예시를 보여 주고 자연어로 받는다 (예: "모든 활동이 목표 하나 이상과 연결되어 있는가", "가정 X가 틀리면 어느 단계까지 영향을 주는가", "강점과 기회를 함께 쓰는 전략은 무엇인가")
- 예 또는 아니오로 답하는 질문은 check 함수 경로로, 목록이나 수치로 답하는 질문은 SPARQL 경로로 분류한다
- 수집한 역량 질문과 합의한 경로는 OWL 메타데이터(create_world의 label, version, comment)에 기록한다
- 사용자가 역량 질문을 내지 못하면 도메인에서 추론한 후보를 3개 이내로 제안하고 확인받는다
- 역량 질문 없이 TBox 구축으로 넘어가지 않는다
- 후속 턴에서 확장할 때는 이번 턴의 추론 목표, 이전 결과와의 관계(후속 처리인지 새 영역인지), 추가 역량 질문을 묻는다
- 방향이 합의되지 않으면 LLM이 임의로 구축 방향을 정하지 않는다

```python
world, onto = create_world(
    label="신규 사업 기획안 검토",
    version="1.0",
    comment="경로 C | CQ1 모든 활동이 목표와 연결되는가 | CQ2 근거 없는 가정은 무엇인가")
```

## 1단계. 설계

설계 규칙은 references/modeling-rules.md에 있고 두 모드에 같이 적용한다. 설계를 시작하기 전에 이 파일을 읽는다. 요지는 다음과 같다.

- 목적, 정의, 기준, 범위를 가장 작은 단위에서 먼저 정하고 작업 끝까지 같은 뜻으로 쓴다
- 분류 기준은 하나로 두고 항목 사이의 겹침과 빠짐을 사례로 확인한다
- 일종 관계(is-a), 부분 관계(part-of), 보유 관계(has-a)를 구별한다
- 관계마다 방향, 유형(인과, 상관, 의존, 연관), 수량 제약을 정한다
- 확인되지 않은 사실은 미지로 처리하고, 전수 조사가 끝난 범위에서만 없다고 판단한다
- 현실의 구조를 먼저 모델링한다. 분석 도구, 쿼리, 출력 형식이 편하도록 개념이나 관계를 더하거나 바꾸지 않는다

엔진 모드에서는 매 턴 백지에서 시작하지 않고 기존 온톨로지를 이어받아 확장한다. 아래 순서로 기존 온톨로지를 찾는다.

| 순위 | 찾는 대상 | 판단 기준 | 처리 |
|:---:|---|---|---|
| 1 | 같은 대화에서 만든 온톨로지 | 이전 턴에 create_world나 save_all_outputs를 호출한 기록이 있다 | 저장된 OWL을 create_world(경로)로 다시 불러와 확장한다 |
| 2 | 사용자가 준 OWL 파일 | .owl 파일이 첨부되었다 | create_world(경로)로 불러온 뒤 점검 단계로 간다 |
| 3 | 자연어로 서술한 문제 | 분석 대상, 관계, 제약을 서술한 글이 있다 | create_world()로 새로 만든다 |
| 4 | 도메인 템플릿 요청 | 분석 유형을 명시했다 | create_world()로 새로 만들고 tbox-templates.md를 참고한다 |

- 1순위와 2순위에 해당하는 온톨로지가 없을 때만 새로 만든다
- 기존 온톨로지가 있는데 사용자가 새 분석을 요청하면 기존 TBox를 다시 쓸 수 있는지 먼저 확인한다. 같은 도메인의 후속 분석이면 TBox를 유지하고 ABox만 더하거나 바꾼다. 완전히 다른 도메인이면 새로 만들되 기존 OWL을 보존할지 묻는다
- 기존 온톨로지에 ABox를 더할 때는 새 개체를 기존 개체와 관계로 연결한다
- 세션이 바뀌어도 이어가려면 OWL 파일을 저장해 두고 다음 세션에서 다시 불러온다

## 2단계. 구축

### 사고 모드

설계 내용을 산출물에 직접 쓴다. 정의 목록, 분류표, 관계 서술이 설계를 전달하며, 적용한 원칙의 이름이나 자기 분류에 대한 자평은 쓰지 않는다.

### 엔진 모드 준비

엔진 모드를 시작할 때 스킬 폴더에서 아래 세 명령을 순서대로 실행한다. 두 스크립트의 출력은 이번 작업에서 쓸 API 목록과 참조 문서이므로 head, tail, 잘라내기 없이 끝까지 읽는다.

```bash
pip install owlready2        # 시스템 Python이 보호된 환경이면 가상환경을 쓰거나 --break-system-packages를 붙인다
python scripts/extract_api.py
python scripts/load_references.py
```

- 코드는 scripts 폴더를 import 경로에 추가한 뒤 `from onto_engine import *`로 불러온다
- 참조 문서의 예시 코드와 onto_engine.py의 실제 코드가 다르면 실제 코드를 따른다
- 권장 규모는 클래스 500개, 개체 10,000개 이내다. 넘어도 동작하지만 구축 시간이 늘어난다

### TBox 구축

TBox를 설계할 때는 후속 분석 도구(SPARQL 쿼리, check 함수, 추론기, SWRL, suggest_axioms, suggest_sparql_queries)를 의식하지 않는다. "이 속성이 있으면 나중에 이런 분석이 된다"는 생각으로 속성을 더하지 않고, "이 도메인에서 A와 B 사이에 실제로 이 관계가 있는가"만으로 판단한다. suggest_axioms와 suggest_sparql_queries는 TBox 설계 중에 호출하지 않는다. 이 규칙은 원턴을 포함한 모든 경로의 구축 단계에 적용한다.

TBox는 설계안 합의, 실행, 확인 순서로 만든다. 사용자가 확정 의사를 밝히기 전에는 build_class, build_object_property 같은 구축 코드를 실행하지 않는다. 경로 B에서 사용자가 원턴을 명시한 경우에만 사전 합의를 생략한다. 보여 주는 편이 빠르다는 이유로 합의를 건너뛰지 않는다.

- (설계안 도출) 사용자 입력에서 실제로 있는 개념(클래스)과 관계(속성)를 빠짐없이 뽑는다. 역량 질문을 거꾸로 따라가며 빠진 개념을 보충하되, 보충할 개념이 현실 도메인에 있는지 확인한다. 쿼리가 돌아가게 하려는 가공 속성은 더하지 않는다
- (합의) 클래스 목록과 속성 목록을 설계안으로 제시하고 수정 요청을 반영한다
- (실행) 합의한 설계안 그대로 구축한다. 설계안에 없는 관계를 분석 편의를 위해 더하지 않는다
- (확인) Mermaid 클래스 다이어그램으로 구축 결과를 보여 준다
- (분석 함수 대응) 구축한 TBox를 auto_route_advanced_checks로 훑어 적용할 수 있는 분석 함수를 나중에 확인한다. TBox에 없는 관계를 전제로 하는 함수는 적용하지 않는다

구축 규칙은 다음과 같다.

- 클래스명은 PascalCase 영문, 속성명과 개체명은 snake_case 영문으로 짓는다
- 사람이 읽는 설명은 build_class의 description 인자나 description 데이터 속성에 사용자 언어로 저장한다
- 사용자가 제시한 고유명사(정책명, 기관명, 사업명 등)는 줄이지 않고 원문 그대로 둔다
- parent, domain, range_cls, cls 인자에는 클래스 객체나 클래스명 문자열을 쓸 수 있다
- 정의한 모든 클래스는 객체 속성 하나 이상의 domain이나 range로 참여해야 한다. 참여하지 않는 클래스가 있으면 설계 오류 가능성을 사용자에게 알린다
- 어떤 개체도 쓰지 않는 객체 속성은 삭제하거나 그 속성을 쓸 개체를 더한다
- 도메인 템플릿이 맞으면 references/tbox-templates.md의 구조를 출발점으로 쓰고 사용자의 용어로 바꾼다

### ABox 구축

ABox는 TBox를 확정한 뒤 작성한다. 경로 A와 C는 별도 턴에서, 경로 B의 원턴은 TBox와 같은 턴에서 입력한다. 사용자가 승인하기 전에는 create_individual 같은 구축 코드를 실행하지 않는다.

- (입력 계획) 개체 목록과 관계 연결 계획을 제시하고, 사실 속성과 판정 속성을 구분해 표시한다
- (합의) 수정 요청을 반영한다
- (실행) create_individual을 호출한 같은 코드 블록에서 그 개체를 객체 속성 하나 이상으로 다른 개체와 연결한다
- (고립 개체 확인) 연결되지 않은 개체가 있으면 목록을 보여 주고 관계를 더할지 미지로 둘지 묻는다. 사용자가 미지로 두기로 한 개체는 개방 세계 가정에 따른 정당한 상태로 둔다
- (확인) Mermaid 개체 그래프로 최종 상태를 보여 준다
- (승인 또는 수정) 승인하면 OWL을 저장하고 다음 단계로 가며, 수정하면 개체와 관계를 바꾼 뒤 다시 보여 준다

사실과 판정은 나눠서 입력한다. "원출처를 보면 누구나 동의하는가"에 해당하면 사실이고, "해석이 필요한가"에 해당하면 판정이다.

- 원출처에서 바로 확인되는 사실 속성만으로 ABox를 먼저 만든다
- "A는 B에 해당한다" 같은 대응 관계는 구축 단계에서 바로 입력하지 않고, 점검 단계에서 공리 기반 추론이나 SPARQL 질의로 도출할 수 있는지 먼저 검토한다
- 사실만으로 구조가 성립하지 않을 때만 판정 속성을 입력할지 사용자에게 묻는다. 동의하면 set_with_provenance로 판정 근거를 함께 기록한다

ABox 수정에는 add_to_class, destroy_individual, build_same_as, update_property, remove_property_value, clear_property를 쓴다.

### 공리 적용

TBox가 확정된 뒤 suggest_axioms(onto)로 적용할 수 있는 공리를 제안받는다. 이 함수는 클래스 계층, 속성 구조, 개체 분포를 훑어 여덟 가지 공리(DisjointUnion, MinCardinality, IrreflexiveProperty, InverseProperty, PropertyChain, SymmetricProperty, ConstrainedDatatype, SWRL)의 후보를 낸다.

- 제안 결과를 보여 주고 사용자가 고른 공리만 적용한다
- 제안에 없어도 도메인 판단에 따라 추가 공리를 제안할 수 있다. references/axiom-patterns.md의 공리 표와 restriction_expr 조합을 참고한다
- 템플릿을 쓰면 템플릿의 axioms 항목을 기본 공리 세트로 쓴다
- 공리 하나가 실패하면 그 공리만 건너뛰고 나머지를 진행한다
- 적용한 공리 목록을 보여 주고 삭제나 변경을 받는다
- 공리를 하나 이상 적용했다면 점검 단계에서 추론기 실행(use_hermit=True)을 기본으로 권한다

OWL 추론기는 개방 세계 가정을 따르므로 빠진 연결을 문제로 판정하지 않는다. 공리를 설계할 때 아래 동작을 반영한다.

- 최소 연결 수 공리(MinCardinality)와 "연결이 없으면 해당" 형태의 자동 분류(Not 조건)는 입력되지 않은 연결을 위반으로 잡지 못한다. 빠진 연결은 SPARQL 점검으로 찾아 미입력 후보로 보고한다
- 추론기로 빠진 연결을 판정해야 하면 사용자가 해당 범위의 입력이 완전하다고 확인한 뒤 close_world_scope로 그 범위를 폐쇄 세계로 선언하고 추론기를 실행한다
- 최대 연결 수 공리(MaxCardinality)는 대상 개체들이 서로 다르다는 선언(build_all_different)이 있어야 초과를 잡는다. OWL은 이름이 다르면 다른 개체라고 가정하지 않기 때문이다

SWRL 규칙은 신중하게 쓴다.

- SWRL은 2004년에 제출된 W3C 멤버 제출(Member Submission) 문서로 표준 권고안 단계에 오르지 않았다. OWL DL에 결합하면 유한 시간 안에 추론이 끝난다는 보장이 사라진다
- SWRL 규칙을 제안하기 전에 이 위험을 알리고 적용 여부를 묻는다
- 같은 효과를 OWL 공리(EquivalentClass, DisjointClasses, 제약 등)로 낼 수 있는지 먼저 검토하고, 불가능할 때만 SWRL을 쓴다
- HermiT는 규칙을 이름 있는 개체에만 적용(DL-safe)하며 greaterThan 같은 내장 함수가 든 규칙은 실행하지 않는다. 내장 함수가 필요하면 reasoner="pellet"으로 바꾸고, 이 경우 추론이 끝나지 않을 수 있음을 알린다

## 3단계. 점검

### 두 모드 공통

- 구조는 references/modeling-rules.md의 점검 목록으로 살핀다
- 사용자 자료와 자기 산출물의 주장은 references/reasoning-rules.md로 점검한다
- 지적 사항에도 입증 책임을 적용한다. 원자료, 코드 출력, 질의 결과로 실제 존재를 확인한 사항만 보고한다

### 엔진 모드 분석 경로

구축이 끝나면 질문 유형에 따라 분석 경로를 고른다. 세 경로는 함께 쓸 수 있다.

| 조건 | 경로 | 이유 |
|---|---|---|
| 허용 조합 규칙 위반, 순서 단절, 포괄 여부, 가정 영향 등 미리 정의한 규칙의 통과 여부 | check 함수 | 규칙을 코드로 표현할 수 있다 |
| 개체 집합 추출, 조건 필터, 집계, 경로 탐색, 사용자의 자유 질의 | SPARQL | 선언형 쿼리 한 줄로 답할 수 있다 |
| 속성값 조합으로 유형 자동 판별 | 추론기 | EquivalentClass 공리가 필요하다 |
| 동시에 속할 수 없는 유형에 함께 속한 개체 탐지 | 추론기 | DisjointClasses 공리가 필요하다 |
| 개별 규칙은 통과하지만 규칙 조합이 모순인지 확인 | 추론기 | 충족 가능성 검사는 추론기만 할 수 있다 |
| 개체 1,000개 이상 전수 점검 | check 함수 | 추론기는 대규모에서 느려진다 |

- check 함수와 추론기를 함께 쓰면 check 함수로 명시한 규칙을 먼저 점검하고 추론기로 숨은 모순을 나중에 찾는다
- 추론기가 실패하거나 시간을 넘기면 결과의 message를 알리고 check 함수와 SPARQL로 대신한다
- run_full_analysis(world, onto)로 기본 분석을 한 번에 실행한다. MECE 점검은 run_mece=True일 때만 돈다. auto_route_advanced_checks는 항상 실행되어 적용할 고급 함수를 알려 준다. 이 목록은 속성명과 클래스명의 키워드로 고른 것이므로 실행 전에 검토한다
- 구조 패턴을 알아보면 프리셋(cross_factor, multi_axis, regulated_procedure, causal, logic_model, mapping_chain, decision_tree)으로 관련 점검을 한 번에 실행한다
- check 함수가 다루지 않는 질문은 Python 코드를 새로 짜기 전에 query_onto로 SPARQL을 먼저 작성한다
- check 함수와 SPARQL은 입력된 사실만 읽는다. 결과에 나온 미연결 항목은 미입력 후보로 다룬다

함수 목록과 사용법은 references/check-functions.md, 질의 패턴과 결과 보고 형식은 references/sparql-patterns.md, 추론기 설정과 공리 코드는 references/axiom-patterns.md에 있다.

## 4단계. 보고

### 두 모드 공통

보고 규칙은 references/output-rules.md에 있다. 보고서를 쓰기 전에 이 파일을 읽는다. 요지는 다음과 같다.

- 모든 문장은 네 가지 판별(주어, 삭제, 수혜자, 응대 기능)을 통과해야 한다. 글 자체, 작성 과정, 사용 도구, 사용자 요청을 주어로 삼는 문장과 지워도 정보가 줄지 않는 문장은 쓰지 않는다
- 적용한 원칙이나 방법론의 이름을 드러내지 않고, 자기 분류나 추론이 원칙을 충족한다는 자평을 쓰지 않는다
- 반례 탐색은 점검 과정에서 수행한다. 보고서에는 발견 사항에 해당하는 반례(예: 두 분류에 동시에 속한 개체)와 사용자가 요청한 반례만 쓴다
- 분석 용어는 의사결정권자가 설명 없이 이해하는 사실 서술로 바꾼다. 예를 들어 "커버리지 미달 3건"은 "사업목표와의 연결이 확인되지 않는 추진전략 3건"으로 쓴다

### 엔진 모드 보고

- 미연결 개체는 위반과 섞지 않고 미입력 후보 절에 따로 적는다. 합의한 추론 목표에 직접 영향을 주는 미입력 후보만 먼저 알리고, 나머지는 사용자가 채우기를 요청할 때 처리한다
- 역량 질문마다 답할 수 있는지와 실제 답(SPARQL 질의나 check 함수의 반환값)을 함께 보고한다. 답할 수 없는 역량 질문은 보충할 클래스, 속성, 개체를 알린다. 후속 턴에서 더한 역량 질문도 같은 방식으로 보고한다
- 기존 OWL을 확장했다면 diff_ontology로 이번 턴의 변경 사항을 요약해 보여 준다
- save_all_outputs로 아래 네 파일을 저장한다

| 파일 | 내용 |
|---|---|
| {base_name}.owl | OWL 온톨로지 (TBox와 ABox) |
| {base_name}_class.mermaid | 클래스 계층 다이어그램 |
| {base_name}_instance.mermaid | 개체 관계 다이어그램 (규모에 따라 자동 전환) |
| {base_name}_report.md | TBox 정의, ABox 현황, 요약 통계 |

개체 관계 다이어그램은 개체 수에 따라 형태가 바뀐다. force_mode 인자로 형태를 지정할 수 있다.

| 개체 수 | 형태 | 내용 |
|---|---|---|
| 50개 이하 | full | 개체 전체 그래프 |
| 51-200개 | aggregated | 클래스 단위 집계 그래프 |
| 201개 이상 | summary | 요약 통계 |

Mermaid 다이어그램은 다음 규칙을 따른다.

- 처음 온톨로지를 구축할 때 매 턴 Mermaid 다이어그램으로 보여 줄지 한 번 묻는다
- 동의하면 이후 구축, 확장, 분석하는 모든 턴과 추론기 재분류로 온톨로지가 바뀐 턴에 보여 준다. 사용자가 다른 시각화 방법을 정하면 그 방법을 쓴다
- 온톨로지가 바뀌지 않은 턴에는 생략하고, 개체가 200개를 넘으면 요약 통계로 대신한다
- export_mermaid_* 함수는 코드 블록 표시 없는 Mermaid 코드를 돌려준다. .mermaid 파일에는 그대로 저장하고, 마크다운 본문에 쓸 때는 mermaid 코드 블록으로 감싼다

run_full_analysis의 결과에는 provenance_check(판정 근거 기록 확인), advanced_routing(적용할 고급 분석), hermit_analysis(use_hermit=True일 때의 추론 결과와 재분류 목록)가 함께 들어 있다.

분석을 마치면 export_tbox_markdown 결과를 따로 저장해 TBox 정의서로 쓴다. 이전 세션의 OWL 파일을 받으면 TBox를 유지한 채 ABox만 바꿔 다시 쓸 수 있다. OWL 파일의 label, version, comment는 Protégé 같은 외부 도구에서 그대로 보인다.

## 산출 전 점검

- 정의, 기준, 범위가 처음 정한 뜻과 같게 쓰였는가
- 분류 기준이 하나이고 항목 사이에 겹침과 빠짐이 없는가
- 일종 관계, 부분 관계, 보유 관계가 섞이지 않았는가
- 모든 결론에 근거가 있고 결론이 근거 범위를 넘지 않는가
- 확인되지 않은 정보를 없다는 근거로 쓰지 않았는가
- 분석 도구나 출력 형식에 맞추려고 구조를 바꾸지 않았는가
- 연결되지 않은 항목과 쓰이지 않는 분류가 없는가, 있다면 사유가 확인되었는가
- 엔진 모드에서 합의 지점을 건너뛰지 않았는가
- 엔진 모드에서 미입력 후보와 위반을 나눠 적었는가
- 메타 서술, 원칙명 노출, 자기 정당화, 요청받지 않은 반례가 없는가
- 분석 용어를 사실 서술로 바꿨는가
