# 오프라인 의존성 스킬 빌더

일부 스킬은 실행할 때 pip, npm, GitHub 릴리스, 모델 허브 같은 외부 경로에서 파일을 받아야 작동한다. 조직 설정이나 플랫폼 정책으로 컨테이너의 외부 통신이 막히면 이런 스킬은 설치 단계에서 멈춘다. 이 스킬은 멈추는 스킬에 필요한 파일을 미리 담은 의존성 스킬을 만든다. 사용자가 두 스킬을 함께 로드하면 원래 스킬이 외부 통신 없이 작동한다.

## 용어

아래 용어는 이 문서와 참조 파일 전체에서 같은 뜻으로 쓴다.

- (부모 스킬) 외부 네트워크에서 파일을 받아야 작동하는 기존 스킬
- (의존성 스킬) 부모 스킬에 필요한 파일을 담아 부모 스킬과 함께 로드하는 스킬
- (의존성) 부모 스킬이 작동하려면 실행 환경에 있어야 하지만 부모 스킬 폴더에는 없는 파일과 프로그램
- (페이로드) 의존성 스킬에 담긴 의존성 파일 묶음
- (목록 파일) 페이로드 항목의 버전, 출처, 라이선스와 조립 때의 가정을 기록한 MANIFEST.md
- (빌드 환경) 의존성 스킬을 조립하는 곳
- (실행 환경) 의존성 스킬이 로드되어 부모 스킬과 함께 쓰이는 곳
- (활성화) 실행 환경에서 페이로드를 풀고 경로를 설정해 부모 스킬이 쓸 수 있게 만드는 과정

의존성은 라이브러리에 한정되지 않는다. 언어 런타임, 실행 파일, 폰트, 모델 가중치, 첫 실행 때 내려받는 데이터 파일, 템플릿, 오피스 프로그램 확장 기능도 모두 의존성이다.

빌드 환경과 실행 환경은 같을 때도 있고 다를 때도 있다. 네트워크가 열린 PC나 에이전트에서 조립해 claude.ai나 ChatGPT에 올리는 경우가 흔하다. 네트워크가 막힌 세션 안에서 사용자가 첨부한 파일로 조립하는 경우도 있다.

## 판단 원칙

의존성의 형태와 설치 방식은 소프트웨어마다 다르다. 신생 라이브러리는 버전마다 명령 이름과 배포 방식을 바꾸기도 한다. 이 문서의 절차는 기본 흐름으로 쓰고, 절차에 맞지 않는 의존성을 만나면 아래 목표에서 출발해 방법을 직접 설계한다.

> 실행 환경에서 외부 통신 없이 부모 스킬의 주요 기능이 끝까지 작동하고, 그 결과물이 정상이다.

판단의 근거는 문서보다 직접 실행해 본 결과에 둔다. 플랫폼 문서가 허용한다고 적은 도메인이 실제로는 막혀 있기도 하다. 설치 명령이 성공한 라이브러리가 첫 사용 때 네트워크를 찾다가 실패하기도 한다. 직접 확인할 수 없는 사항은 가정으로 기록하고 다음 단계로 진행한다.

사용자에게 묻는 질문은 답에 따라 결과물이 달라지는 사항으로 좁힌다. 실행 플랫폼, 큰 파일을 세션마다 첨부할 의향, 부모 스킬 코드 수정 여부가 여기에 해당한다. 나머지 사항은 합리적인 기본값으로 진행하고 최종 보고에 적는다.

## 새 의존성 스킬 만들기

### 1. 의존성 목록 작성

부모 스킬의 SKILL.md, 스크립트, 참조 문서를 모두 읽고 의존성을 찾는다. 설치 명령에는 의존성의 일부만 드러나므로 아래 단서를 함께 살핀다.

- 설치 명령, import 문, require 문
- 스크립트가 호출하는 외부 프로그램
- 코드 안의 URL, 모델 저장소 이름, 캐시 경로
- 문서가 이름으로 지정하는 폰트, 템플릿, 확장 기능
- 환경 변수와 스킬 폴더 밖의 파일 경로

의존성마다 부모 스킬의 어느 기능이 그 의존성을 쓰는지 기록한다. 주요 기능에 필요한 의존성과 선택 기능에만 쓰이는 의존성을 나눈다. 큰 라이브러리는 부모 스킬이 실제로 쓰는 구성 요소를 따로 적는다. 여러 추론 엔진이나 여러 모델을 함께 배포하는 라이브러리에서 부모 스킬이 그중 하나만 쓰는 경우가 흔하다. 이 기록은 용량 설계에서 제외할 항목을 고르는 근거가 된다.

부모 스킬이 이미 외부 통신 없이 작동하면 의존성 스킬이 필요 없다고 알리고 작업을 마친다.

### 2. 실행 환경 파악

페이로드는 실행 환경에 맞는 파일이어야 작동한다. 실행 환경에서 아래 항목을 확인한다. 확인 명령은 references/platforms.md에 있다.

- 운영체제, CPU 아키텍처, C 라이브러리 종류와 버전
- Python, Node.js, Java 버전과 이미 설치된 패키지
- 쓰기 가능한 경로, 디스크 여유, 메모리
- 현재 사용자의 root 여부
- 출처별 실제 접속 가능 여부

실행 환경에 직접 접근할 수 없으면 사용자에게 실행 플랫폼을 묻는다. 답을 받을 수 없으면 references/platforms.md의 기본 가정을 쓰고 그 가정을 목록 파일에 적는다. 조건을 모를 때는 여러 조건에 맞는 파일을 함께 담는 방법도 있다. Python 버전별 휠을 함께 담으면 버전을 몰라도 설치된다. 이 방법은 용량을 늘리므로 용량 설계와 함께 판단한다.

실행 환경에 이미 있는 의존성은 페이로드에서 제외한다. 사전 설치 패키지는 플랫폼 업데이트로 바뀔 수 있으므로 사전 설치에 기대는 항목을 목록 파일에 적는다.

### 3. 획득 경로 선택

의존성 파일을 얻는 경로는 아래와 같다. 앞쪽 경로일수록 사용자 부담이 작다.

- (빌드 환경 네트워크) 패키지 관리자, git, 공식 다운로드 주소에서 직접 받는다
- (세션 다운로드 도구) 셸의 외부 통신이 막혀도 대화에 등장한 URL의 파일을 컨테이너로 받아 주는 도구를 제공하는 플랫폼이 있다. 현재 세션의 도구 목록에서 찾는다. 이런 도구는 대화에 먼저 나온 URL만 받기도 하므로 웹 검색으로 공식 주소를 먼저 찾는다
- (사용자 첨부) 사용자가 파일을 받아 대화에 첨부한다
- (사용자 환경 조립) 사용자가 네트워크가 열린 자기 환경에서 이 스킬로 의존성 스킬을 조립해 업로드한다

한 소프트웨어를 얻는 길은 대개 여러 개다. 릴리스 바이너리 주소가 막혀도 git 저장소는 열려 있을 수 있다. 같은 기능을 다른 패키지 저장소나 WASM 패키지로 배포하는 프로젝트도 있다. 한 경로가 막히면 다른 경로를 찾아 시도하고, 시도한 경로와 결과를 기록한다.

사용자에게 파일을 받아 달라고 안내할 때는 아래 기준을 따른다.

- 웹 검색으로 공식 다운로드 주소를 찾아 알려 준다. 공식 주소는 프로젝트 자체 사이트, 패키지 저장소의 패키지 페이지, 패키지 저장소가 원본으로 가리키는 저장소를 뜻한다. 포크, 미러, 재배포 사이트는 공식 주소에서 제외한다
- 웹 검색 도구가 없으면 모델 지식으로 주소를 안내하고, 주소가 바뀌었을 수 있다고 함께 알린다
- 운영체제, 아키텍처, Python 버전, C 라이브러리 종류처럼 파일 선택에 필요한 조건을 구체적으로 적는다
- 받은 파일은 이름을 바꾸거나 압축을 풀지 않고 그대로 첨부해 달라고 요청한다
- 첨부 한도보다 큰 파일은 나누어 올리는 방법을 함께 안내한다

첨부 파일을 받으면 파일 이름의 플랫폼 표기와 실제 내용이 실행 환경 조건과 맞는지 살핀 뒤 조립에 쓴다.

### 4. 용량 설계

플랫폼마다 스킬 업로드 한도가 있다. 이 문서 작성 시점의 공식 문서 기준으로 Claude API의 한도는 모든 파일의 압축 해제 합계 30MB이다. OpenAI API의 한도는 압축 해제 합계 25MB와 파일 500개이다. claude.ai에서는 파일이 200개를 넘는 zip의 설치가 거부된 사례가 보고되었다. 여러 플랫폼에서 쓸 의존성 스킬은 압축 해제 합계 25MB 이하와 파일 200개 이하를 기본 목표로 둔다. 현재 공식 수치를 확인할 수 있으면 그 수치를 우선한다.

한도는 스킬 폴더 안의 파일 크기로 계산된다. 폴더 안에 둔 압축 파일은 압축된 크기로 계산되므로 압축률이 높을수록 더 많이 담긴다. 조립이 끝나면 폴더 전체 크기와 파일 수를 실제로 측정한다.

한도를 넘으면 아래 방법을 차례로 검토한다. 여러 방법을 함께 써도 된다.

- (사전 설치 활용) 실행 환경에 이미 있는 의존성을 제외한다
- (부분 포함) 부모 스킬이 쓰는 구성 요소만 담는다. 라이브러리가 시작할 때 목록을 읽는 폴더는 빈 폴더로 남긴다
- (재압축) xz처럼 압축률이 높은 형식으로 다시 묶고, 파일이 많은 폴더는 아카이브 하나로 묶는다. 실행 환경의 Python 표준 라이브러리로 풀 수 있는 zip, tar.gz, tar.xz를 쓴다
- (분할) 의존성 스킬을 여러 개로 나눈다. 여러 부모 스킬이 함께 쓰는 런타임은 별도 의존성 스킬 하나로 만들어 공유한다
- (하이브리드) 한도를 넘는 큰 파일만 스킬 밖에서 공급한다
- (대체 제안) 더 작은 라이브러리나 모델로 바꾸는 방법을 사용자에게 제안한다. 부모 스킬 코드 수정이 따르므로 결정은 사용자에게 맡긴다

부분 포함은 라이브러리 내부 구조에 기대는 방법이다. 구성 요소를 제외했으면 검증 단계에서 부모 스킬의 주요 기능을 실행해 작동을 확인한다. 공유 런타임을 줄였으면 그 런타임을 쓰는 모든 부모 스킬로 확인한다. 한 소비자에게 충분한 축소가 다른 소비자를 멈추게 하기도 한다.

하이브리드 구성은 아래처럼 만든다.

- 사용자가 세션마다 큰 파일을 첨부한다. 첨부 한도보다 크면 여러 조각으로 나누어 올리고 실행 환경에서 합친다. 합친 파일의 크기가 원본 크기와 같은지 비교한다
- 쿠버네티스 같은 에이전트 실행 환경에서는 볼륨 마운트, 미리 채운 캐시 폴더, 조직 내부 패키지 미러로 공급한다
- 플랫폼이 특정 도메인만 허용하는 설정을 제공하면 필요한 도메인 목록을 정리해 사용자가 관리자에게 요청하도록 돕는다

모델 가중치가 GB 단위이거나 런타임 자체가 수백 MB이면 대개 하이브리드 구성만 가능하다. 어느 방법으로도 한도를 맞출 수 없으면 필요한 크기, 플랫폼 한도, 가능한 대안을 사용자에게 그대로 알린다.

### 5. 의존성 스킬 조립

의존성 스킬의 폴더 구성과 SKILL.md 양식과 목록 파일 양식은 references/child-skill-template.md를 따른다. 생태계별로 실행 환경에 맞는 파일을 받는 방법과 활성화 방법은 references/ecosystems.md에 있다.

빌드 환경에서 파일을 받을 때는 실행 환경 조건을 명시한다. 패키지 관리자는 조건이 없으면 빌드 환경 기준으로 파일을 고른다. 윈도우 PC에서 받은 네이티브 패키지는 리눅스 컨테이너에서 로드되지 않는다.

의존성 스킬의 SKILL.md에는 활성화 절차를 담는다. 활성화 절차는 아래 성질을 갖춘다.

- 의존성이 이미 쓸 수 있는 상태인지 먼저 확인하고, 없을 때만 페이로드를 푼다
- 페이로드는 쓰기 가능한 작업 경로에 푼다. 스킬 폴더는 읽기 전용일 수 있다
- 실행 파일은 작업 경로로 복사한 뒤 실행 권한을 준다. 업로드와 동기화 과정에서 실행 권한이 사라지기도 한다
- 경로와 환경 변수를 설정하고, 부모 스킬이 알아야 할 경로를 출력한다
- 환경 변수는 작업 경로의 파일에도 저장한다. 명령마다 새 셸이 열리는 실행 환경에서는 명령 앞에서 이 파일을 불러온다
- 간단한 작동 확인을 실행한다
- 여러 번 실행해도 같은 결과가 나온다

활성화 절차가 길면 Python 표준 라이브러리만 쓰는 스크립트로 만들어 의존성 스킬에 담아도 된다.

부모 스킬과 연결하는 방법도 SKILL.md에 적는다. 부모 스킬의 설치 단계를 건너뛰고 활성화 결과를 쓰도록 안내한다. 부모 스킬이 파일 경로를 고정해 두었으면 옵션이나 환경 변수로 연결한다. 부모 스킬 코드 수정이 필요하면 수정 내용을 사용자에게 보여 주고 승인을 받는다.

목록 파일에는 담은 항목마다 버전, 출처 주소, 라이선스, 대상 플랫폼 조건, 받은 날짜, 크기를 적는다. 제외한 구성 요소와 이유, 실행 환경에 대한 가정도 함께 적는다. 목록 파일은 갱신과 공유 전 점검의 근거가 된다.

### 6. 검증

검증은 실행 환경과 최대한 비슷한 조건에서 부모 스킬의 주요 기능을 끝까지 실행하는 일이다.

빌드 환경에서는 외부 통신이 없는 상태를 만든다. 리눅스에서는 네트워크 네임스페이스나 프록시 설정 해제로 만들 수 있다. 두 방법을 모두 쓸 수 없으면 패키지 관리자의 오프라인 옵션(pip --no-index, npm --offline)으로 설치 단계를 격리하고, 첫 사용 다운로드 여부는 실행 환경에서 확인한다. 이미 설치된 사본이 결과를 가리지 않도록 새 가상 환경과 새 작업 경로를 쓴다. 실행 환경과 같은 언어 버전을 쓰고, 실행 환경에 없는 시스템 폰트나 런타임은 보이지 않게 가린다.

성공 여부는 결과물 내용으로 판단한다. 종료 코드가 0이고 파일이 생겨도 결과물이 비어 있을 수 있다. 문서 렌더러는 폰트가 없으면 글자만 빠진 PDF를 만들고 정상 종료하기도 한다. PDF는 텍스트를 추출하고 페이지를 이미지로 렌더링해 글자가 보이는지 본다. 추론이나 변환 결과는 기대값과 비교한다.

첫 사용 때 데이터를 내려받는 라이브러리는 설치에 성공한 뒤에도 실패한다. 외부 통신이 없는 상태에서 실제 기능을 한 번 호출해 본다.

실행 환경에서 처음 활성화할 때 같은 확인을 한 번 더 한다. 빌드 환경에서 확인하지 못한 항목은 목록 파일과 최종 보고에 미검증으로 적는다.

### 7. 최종 보고

작업을 마치면 사용자에게 아래 내용을 알린다.

- 만든 의존성 스킬과 함께 로드할 부모 스킬
- 담은 항목, 제외한 항목과 이유, 전체 크기와 파일 수
- 검증 결과와 미검증 항목
- 가정한 실행 환경 조건
- 사용자가 할 일 (업로드, 세션별 첨부, 관리자 설정 요청)

의존성 스킬은 폴더째 zip으로 묶어 전달한다. zip을 열면 스킬 이름과 같은 폴더가 나오고 그 안에 SKILL.md가 있어야 한다.

## 기존 의존성 스킬 갱신

갱신 요청을 받으면 목록 파일의 버전과 최신 버전을 비교한다. 빌드 환경에 네트워크가 있으면 패키지 저장소와 git 태그를 조회한다. 네트워크가 없으면 웹 검색으로 공식 페이지의 최신 버전을 찾는다.

갱신은 이유가 있을 때 진행한다. 보안 수정, 부모 스킬이 요구하는 새 기능, 현재 겪는 결함의 수정이 갱신 이유에 해당한다. 이유가 없으면 비교 결과만 알린다.

신생 라이브러리는 버전이 바뀌면 명령 이름, 옵션, API가 함께 바뀌기도 한다. 갱신한 뒤에는 검증 단계를 다시 수행하고, 통과하기 전까지 이전 판 페이로드를 보관한다. 부모 스킬 코드가 새 버전과 맞지 않으면 필요한 수정을 사용자에게 알린다. 마지막으로 목록 파일을 고친다.

## 공유 전 점검

의존성 스킬을 다른 사람과 공유하거나 공개할 계획이면 아래 사항을 점검한다.

- 항목마다 라이선스를 확인해 재배포 가능 여부와 조건을 목록 파일에 적는다. 재배포를 금지하는 폰트와 상용 소프트웨어, 소스 공개 의무가 따르는 라이선스는 사용자에게 먼저 알린다
- 라이선스 전문을 함께 배포해야 하는 항목은 라이선스 파일을 페이로드에 함께 담는다
- 서명 이미지, 조직 서식, 인증서, API 키처럼 특정 개인이나 조직에 속한 파일은 페이로드 밖에 두고, 실행 때 사용자가 첨부하도록 안내한다
- 목록 파일과 SKILL.md에 개인 경로, 조직 내부 도메인, 계정 이름이 남아 있는지 살핀다
