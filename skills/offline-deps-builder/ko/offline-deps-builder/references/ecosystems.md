# 생태계별 획득과 활성화

각 절은 실행 환경에 맞는 파일을 받는 방법, 페이로드로 묶는 방법, 실행 환경에서 활성화하는 방법, 자주 막히는 지점을 담는다. 명령은 예시이다. 도구 버전에 따라 옵션 이름이 바뀔 수 있으므로 막히면 해당 도구의 --help로 현재 옵션을 확인한다.

## Python 패키지

pip는 조건을 주지 않으면 빌드 환경의 Python 버전과 운영체제에 맞는 파일을 고른다. 실행 환경 조건을 지정해 받는다.

```
pip download <패키지> -d wheels --only-binary=:all: \
  --python-version 3.12 --implementation cp \
  --platform manylinux2014_x86_64
```

--platform은 여러 번 줄 수 있다. manylinux 태그의 숫자는 필요한 최소 glibc 버전을 뜻하므로 실행 환경 glibc보다 높은 태그는 주지 않는다.

휠 없이 소스 배포판만 있는 패키지는 `pip wheel <패키지> -w wheels`로 미리 휠을 만든다. 빌드는 실행 환경과 같은 Python 버전과 운영체제에서 한다. 오프라인에서 소스 배포판을 설치하면 빌드 도구를 받으려다 실패한다. C 확장을 빌드한 휠은 빌드한 시스템의 glibc 이상에서만 작동하므로 glibc가 실행 환경과 같거나 더 오래된 시스템에서 빌드한다.

활성화는 `pip install --no-index --find-links <휠 폴더> <패키지>`로 한다. pip가 없거나 설치가 막힌 환경에서는 휠을 작업 경로에 풀고 그 경로를 PYTHONPATH에 추가한다. 콘솔 명령과 설치 후처리가 필요 없는 패키지는 이 방법으로 작동한다. 큰 휠은 풀어서 tar.xz로 다시 묶으면 휠보다 작아지고, 활성화 때 풀어서 PYTHONPATH로 쓴다.

자주 막히는 지점은 아래와 같다.

- (선언되지 않은 의존성) 메타데이터에 없는 패키지를 import하는 라이브러리가 있다. 설치 뒤 부모 스킬의 import와 주요 호출을 실제로 실행해 누락을 찾는다
- (첫 사용 다운로드) 토크나이저 데이터, 말뭉치, 모델 가중치를 첫 호출 때 받는 라이브러리가 있다. 빌드 환경에서 한 번 실행해 캐시를 채우고, 캐시 폴더를 페이로드에 담은 뒤 라이브러리의 캐시 경로 환경 변수로 지정한다. tiktoken의 TIKTOKEN_CACHE_DIR이 그런 예이다
- (GPU판 기본값) 딥러닝 프레임워크는 기본 저장소에서 GPU판과 수 GB의 GPU 라이브러리가 함께 선택되기도 한다. CPU 실행 환경이면 CPU판 전용 저장소를 지정하고, 다른 패키지를 이어서 받을 때도 CPU판이 유지되는지 받은 파일 목록을 본다
- (Python 버전) cp312처럼 버전이 표기된 휠은 다른 버전에서 설치되지 않는다. abi3 표기 휠은 표기된 버전 이상에서 두루 쓰인다. `pip debug --verbose`는 실행 환경이 받아들이는 휠 태그 목록을 보여 준다

## Node.js 패키지

네이티브 바이너리를 담은 패키지는 설치할 때 운영체제와 CPU에 맞는 하위 패키지를 고른다. 빌드 환경에서 실행 환경 조건을 지정해 설치한다.

```
npm install <패키지> --os=linux --cpu=x64 --libc=glibc
```

설치 과정에서 바이너리나 브라우저를 추가로 내려받는 패키지도 있다. 빌드 환경에서 설치를 끝낸 node_modules를 그대로 묶는다. node_modules는 파일이 수백 개에서 수천 개이므로 tar.xz 하나로 묶는다.

활성화 때는 작업 경로에 node_modules를 푼다. require로 불러오는 CommonJS 스크립트는 NODE_PATH에 node_modules 경로를 지정하면 된다. import로 불러오는 ES 모듈은 NODE_PATH를 따르지 않고 스크립트가 있는 폴더와 상위 폴더에서 node_modules를 찾는다. 스킬 폴더가 읽기 전용이면 부모 스킬의 스크립트를 작업 경로로 복사해 node_modules 옆에서 실행한다.

브라우저용으로 만든 패키지는 브라우저가 제공하는 함수를 전역 함수로 요구하기도 한다. 캔버스의 글자 폭 측정 함수가 흔한 예이다. Node에서 쓰려면 그 함수를 직접 제공해야 하고, 결과물 품질이 브라우저와 달라질 수 있다. WASM 패키지는 운영체제와 CPU를 가리지 않으므로 네이티브 바이너리 호환 문제가 생길 때 대안이 된다.

## 실행 파일

공식 릴리스 자산 가운데 실행 환경의 운영체제와 아키텍처에 맞는 파일을 고른다. 파일 이름 규칙은 프로젝트마다 다르므로 릴리스 API나 릴리스 페이지의 자산 목록을 보고 고른다.

릴리스를 받을 수 없으면 소스 빌드를 검토한다. 저장소의 빌드 설정, CI 설정, 개발 문서를 읽고 그 시점의 방법을 따른다. 필요한 실행 파일 대상만 빌드한다. 저장소 크기와 빌드 시간이 GB 단위와 수십 분 단위에 이르기도 하므로 디스크 여유를 먼저 본다. 저장소가 툴체인 버전을 고정해 두었으면 빌드 환경에서 그 버전을 받을 수 있어야 한다.

동적 링크 실행 파일은 빌드한 시스템의 glibc보다 오래된 glibc에서 실행되지 않는다. 아래 명령으로 요구 버전을 보고 실행 환경 glibc와 비교한다.

```
objdump -T <실행 파일> | grep -o 'GLIBC_[0-9.]*' | sort -Vu | tail -1
```

실행 환경 glibc를 모르면 정적 링크 빌드나 오래된 glibc에서 빌드한 공식 배포판을 고른다.

실행 파일은 strip으로 디버그 정보를 지운 뒤 xz로 압축해 담는다. 활성화 때는 작업 경로에 풀고 실행 권한을 준 뒤 PATH에 추가한다. 함께 필요한 공유 라이브러리는 LD_LIBRARY_PATH로 지정한다.

신생 도구는 버전마다 명령 이름과 옵션이 바뀐다. 활성화한 뒤 `--help`로 현재 명령 체계를 보고 부모 스킬의 호출 방식과 대조한다. 이름이 달라졌으면 같은 기능의 명령을 찾아 부모 스킬과 연결한다.

## Java

JAR 라이브러리는 Maven Central 같은 저장소에서 전이 의존성까지 모은다. 빌드 환경에 Maven이 있으면 `mvn dependency:copy-dependencies`로 한 번에 모은다. claude.ai의 패키지 관리자 허용 목록에는 Maven 저장소가 없으므로 Java 라이브러리는 의존성 스킬로 공급하는 경우가 많다.

부모 스킬용으로 작성한 Java 코드는 실행 환경 런타임 버전에 맞춰 `javac --release <버전>`으로 컴파일해 담는다. 최소 런타임에는 컴파일러가 없어서 소스 파일을 바로 실행하지 못한다.

실행 환경에 Java가 없으면 런타임도 담는다.

- 필요한 모듈은 `jdeps --print-module-deps --ignore-missing-deps <JAR 목록>`으로 구한다
- `jlink --add-modules <모듈 목록> --strip-debug --no-man-pages --no-header-files --output <폴더>`로 최소 런타임을 만든다
- jlink의 원본 JDK는 오래된 glibc에서도 도는 배포판(예: Eclipse Temurin)을 쓴다. 리눅스 배포판이 패키징한 JDK는 그 배포판의 glibc를 요구한다
- jlink 내부 압축을 끄고 만든 뒤 전체를 xz로 묶으면 더 작아진다
- 여러 부모 스킬이 쓰는 런타임은 모든 소비자의 모듈 합집합으로 만든다. 네이티브 라이브러리를 추가로 줄였으면 모든 소비자로 검증한다

활성화 때는 런타임을 작업 경로에 풀고 java 실행 파일에 실행 권한을 준다. 경로는 PATH나 JAVA_HOME으로 알리거나, Java를 호출하는 라이브러리의 설정 변수로 연결한다.

로케일이 없는 컨테이너에서는 Java 출력의 한글처럼 ASCII 밖의 문자가 물음표로 바뀐다. LANG=C.UTF-8을 지정한다.

## 오피스 프로그램 확장 기능

LibreOffice 확장(.oxt)은 공식 확장 사이트나 프로젝트 릴리스에서 받는다.

- root 사용자에게는 사용자 단위 설치가 거부된다. root이면 `unopkg add --shared <파일>`로 설치하며, LibreOffice 설치 폴더에 쓰기 권한이 필요하다
- root가 아니면 전용 프로필 경로 `-env:UserInstallation=file:///<경로>`를 unopkg와 soffice에 똑같이 준다
- Java로 작성된 확장은 LibreOffice가 쓸 Java 런타임이 필요하다. 시스템 Java가 없으면 담아 온 런타임을 `UNO_JAVA_JFW_JREHOME=file:///<런타임 경로>`로 지정한다
- 한글처럼 ASCII 밖의 문자가 들어간 파일명은 UTF-8 로케일(LANG=C.UTF-8)에서 열린다

## 운영체제 패키지

deb와 rpm 패키지는 실행 환경과 같은 배포판, 같은 버전일 때 쓴다. root 권한 없이 쓰려면 패키지를 작업 경로에 풀고(`dpkg-deb -x <파일> <폴더>`) PATH와 LD_LIBRARY_PATH를 지정한다. 필요한 공유 라이브러리가 실행 환경에 있는지 `ldd <실행 파일>`로 본다. 배포판이 다르거나 알 수 없으면 언어별 패키지나 정적 빌드 같은 다른 경로를 먼저 찾는다.

## 폰트

재배포를 허용하는 라이선스(SIL Open Font License 등)의 폰트만 담는다. 문서가 상용 폰트를 지정하면 비슷한 무료 폰트를 담고 대체 폰트로 연결한다.

- 도구가 폰트 경로 옵션을 제공하면 그 옵션으로 지정한다
- 옵션이 없으면 `$HOME/.local/share/fonts`에 복사하고 `fc-cache`를 실행한다. HOME에 쓸 수 없으면 폰트 폴더와 쓰기 가능한 캐시 폴더를 추가한 fontconfig 설정 파일을 만들고 FONTCONFIG_FILE로 지정한다
- 명조와 고딕처럼 문서가 여러 계열을 쓰면 계열마다 폰트를 담는다. 용량이 부족하면 한 폰트를 여러 계열의 대체 폰트로 지정한다. 대체 지정이 없으면 해당 계열의 글자가 누락된 결과물이 나온다

## 모델 가중치와 데이터

부모 스킬이 첫 실행 때 받는 모델과 데이터의 저장소 이름과 캐시 경로를 코드에서 찾는다.

담을 수 있는 크기면 빌드 환경에서 로컬 폴더로 받아 담는다. 활성화 때 로컬 경로를 부모 스킬에 연결하고 오프라인 모드 환경 변수를 지정한다. Hugging Face 계열 라이브러리는 HF_HUB_OFFLINE=1을 쓴다.

GB 단위 모델은 하이브리드 구성으로 공급한다. 모델을 돌리는 딥러닝 프레임워크 자체도 수백 MB에 이르므로 함께 계산한다.

오래된 모델 저장소는 새 라이브러리 버전에서 로드되지 않기도 한다. 검증을 통과한 라이브러리 버전을 모델과 함께 목록 파일에 적는다.
