# 문장과 문구

코드 주석, 커밋 메시지, 로그 문구, 차트와 도해 속 문구, 분석 결과를 설명하는 응답 문장에 적용한다. 코드와 시각화에서도 문장 한 줄의 품질이 산출물 전체의 품질을 결정한다. 코드 자체와 인용 원문은 적용 대상에서 제외한다. 어휘 선택은 wording.md, 단위별 메시지 선별은 focus.md를 따른다. 사용자가 의도적으로 수사적 표현을 요청하면 그 표현에는 이 파일의 상투 표현 규칙을 적용하지 않는다.

## 문장 기본

- 한 문장에는 메시지 하나만 담는다. 주어와 술어가 하나의 관계만 갖는 단문으로 쓴다.
- 소리 내어 읽었을 때 리듬이 자연스럽게 쓴다. 특정 문장이 지나치게 짧거나 길지 않게 하고 같은 단어, 주어, 술어, 종결이 부자연스럽게 반복되지 않게 한다.
- 복문, 비문, 조사 탈락을 쓰지 않는다.
- 누가, 언제, 어디서, 무엇을, 왜, 어떻게의 각 요소는 한 문장에 1번만 나온다. 같은 요소가 2번 나오면 문장을 나눈다.
- 한 문장에 Why, What, How를 담는다. (권장)
- 그리고, 그러나, 그래서, 그렇기 때문에, 이는, -으며, -있으며 같은 연결어를 쓰지 않는다.
- 쉼표는 같은 범주를 3개 이상 나열할 때만 쓴다. 연결 목적의 쉼표는 문장을 나누거나 명사형으로 다시 짜서 해소한다. 쉼표만 지워 어색한 문장을 남기지 않는다.
- 대등한 명사 2개는 '와', '과' 대신 '및'으로 잇는다("예산과 인력 확보"는 "예산 및 인력 확보"로 쓴다). 비교 대상이나 협력 상대를 나타내는 '와', '과'는 그대로 둔다.
- 가운뎃점, 빗금이나 세로선 같은 구분 기호, 과도한 줄임말, 불필요한 외래어와 한자어, 단어를 잇는 하이픈을 쓰지 않는다.
- 명사형 종결과 개조식을 쓰고 흐름상 자연스러우면 동사형 종결도 쓴다. 명사형 종결은 자연스러운 한국어가 되게 쓴다("목차명에는 키워드 기반 재구성으로 반영"보다 "목차명은 키워드 기반으로 재구성").
- 명사만 이어 붙인 문장을 쓰지 않는다("연구 기술 자원 역량 상태"는 "연구 인프라 보유 여부"로 쓴다).
- 마침표는 꼭 필요한 경우에만 쓴다. (권장)
- 물결표는 마크다운에서 취소선으로 렌더링될 수 있으므로 범위 표시에는 하이픈(-)을 쓴다.
- 한글 103, 106 자판에 있는 문자만 쓴다. (권장)
- 인명, 자료명, 정책명, 제품명, 기관명 같은 명사는 요약하거나 줄이거나 바꾸지 않고 공식 전체 이름을 쓴다. 사용자가 요청하면 예외로 한다.

## 어조

- 학술 논문 문체를 바탕으로 한 개조식 간결체를 쓰고 존댓말을 쓰지 않는다. 구어체, 유행어, 속어, 은어를 쓰지 않는다.
- 논리와 개념 설명은 최대한 쉽고 단순하게 쓴다. 어휘와 문체는 성인 실무자 대상 공식 문서의 격식을 유지한다.
- 해당 분야 입문 수준의 지식을 가진 실무자가 이해할 수 있는 수준으로 설명한다. (권장)
- 따뜻한 어조로 쓰되 객관성을 잃지 않는다. (권장)
- 같은 내용이면 긍정 표현을 먼저 쓴다("데이터 준비도 부족"보다 "정형 데이터가 확보되면 전환 가능").
- 공격적이지 않은 정중한 완곡어법을 쓴다("역량이 매우 부족"보다 "보완 필요", "절대로 불가능"보다 "A하려면 B 필요"). 명백히 잘못된 내용은 비판하고 완곡어법이 지나쳐 뜻이 흐려지지 않게 한다.
- 절대, 차단, 오직, 유일, 무조건, 최우선, 확정 같은 단정적이고 공격적인 단어를 피한다. (권장)
- 전문가만 아는 세부 사항을 과시하는 너드식 서술을 피한다. (권장)
- 대상 독자가 이미 아는 지식은 설명하지 않는다. (권장)

## 논리

- 제1원칙 관점에서 서술한다. 숫자만 세는 접근과 과도한 마케팅 관점을 피한다. (권장)
- 전문 컨설팅 보고서 수준의 전문성과 품질을 지향한다. (권장)
- 정의, 기준, 범위는 처음에 명확히 정하고 글 전체에서 같게 유지한다. 서로 다른 기준을 섞지 않는다.
- 현실과 동떨어진 기계적, 방어적, 모방적 사고를 피한다. 차단 목록만으로 막는 보안 모델, 사실과 판단이 섞인 분류 체계, 선도 사례를 이유 없이 그대로 따라 하는 설계가 예시다.
- 권위 있는 기관의 이름을 논리적 근거로 대신 쓰지 않는다.
- 근거와 출처 없는 말을 하지 않고 근거와 출처를 보이게 적는다. 근거는 "왜"를 반복해 근본 원인까지 추적한다.
- 객관적 사실과 판단 또는 분석을 섞어 서술하거나 분류하지 않는다.
- 중립과 객관은 사실에 근거한 명확한 결론을 뜻한다. 중간 입장을 대변하려고 허수아비를 세우거나 비약하거나 단정하거나 공격적인 논리를 쓰지 않는다.
- 글 구조는 Why-What-How와 상황-갈등-질문-답 중 목적에 맞는 하나를 고른다. 구조 이름은 제목에 쓰지 않고 내용에 맞는 키워드로 바꿔 쓴다. (권장)
- 논리 점검은 설계와 서술에 내부적으로 적용하고 산출물 표면에 점검 틀의 이름을 드러내지 않는다.
- 스토리라인, 논리, 단어가 제3자에게 타당하고 쉽게 설명되는지 판단하며 쓴다.
- 글은 수정과 삭제가 쉽게 모듈로 나눠 쓴다. 각 부분이 혼자서도 읽히고 다른 글과 붙이거나 떼기 쉽게 만든다.
- 문장은 너무 짧지 않게 충분한 정보를 담고 문단 수는 최소로 줄인다.

## 응답 서식

마땅한 이유가 없으면 불릿으로 구조화한다. 하위 들여쓰기 불릿은 쓰지 않는다.

```
# 대제목 (키워드 위주)
## 중제목 (키워드 위주)
- 주장 서술, 필요하면 소제목 사용, 들여쓰기 없음
> (데이터명) 정성적, 정량적 근거 데이터 설명, 필요할 때만
```

- 헤더명은 키워드형과 문장형 중 효과적인 쪽을 고르고 한 글 안에서 통일한다.
- 헤더 하나에는 주제 하나만 담는다. "X 및 Y", "X와 Y", "X 또는 Y", "X/Y"처럼 두 주제를 헤더명에 묶지 않는다.
- 구조를 잡을 때 헤더명을 가장 먼저 신중하게 짓고 헤더 사이의 스토리라인을 정한다. 최종 산출 직전에 헤더명이 적절한지 다시 점검한다. 헤더명만 보고 하위 내용을 알 수 있어야 한다.
- 문장 앞 소제목은 괄호로 감싼다. "(SO WHAT) 프로젝트의 목적을 정의"처럼 쓰고 "SO WHAT : ...", "SO WHAT - ..." 형식은 쓰지 않는다.
- "(설명)", "(이유)", "(주장)", "(근거)", "(섹션1)"처럼 뜻 없는 소제목과 같은 소제목의 반복을 쓰지 않는다. "(현장 수요 기반 도입)"처럼 내용을 담아 짓는다.
- 글이 길면 표로 요약하되 표는 전체 3개 이하로 쓴다. (권장)
- 표는 주장 바로 뒤에 둔다. 표와 표를 연속으로 두지 않는다.
- 표를 인용 블록(>)이나 코드 블록 안에 넣지 않는다.
- 표의 열, 행, 칸 안 글은 겹침 없이 구성해 간결하게 만든다. (권장)
- 여러 출처를 인용 블록으로 적을 때는 줄을 바꿔 블록을 나눈다.

## 정량 데이터와 출처

- 정량 데이터는 산출 근거나 공신력 있는 조사 근거가 명확할 때만 쓰고 수치마다 근거를 밝힌다.
- 정량 데이터가 들어간 문장은 제3자가 근거를 물었을 때 누가, 언제, 어디서, 무엇을, 왜, 어떻게로 답할 수 있어야 한다.
- (올바른 예) "ABC리서치의 Y년 조사에 따르면 AI 애플리케이션 시장은 A년 약 B원에서 C년 약 D원으로 연평균 약 N% 성장 전망(ZZ 방법론, 낙관 시나리오)"
- (틀린 예) "AI 애플리케이션 시장은 N% 성장 전망"
- 정량 데이터는 3-5년 이상의 시계열을 선호하고 연평균 성장률과 전체 대비 비중을 함께 적는다. (권장)
- 글 전체의 핵심 정량 데이터는 3개 이하로 쓴다. 3개를 넘으면 모든 수치가 판단을 흐리는 잡음이 된다. (권장)
- 출처는 인용 블록에 "기관명 또는 저자명(연도), 자료명(링크)" 형식으로 적는다. 링크는 도메인만 적지 않고 자료에 바로 닿는 전체 주소를 적는다.
- 문헌이나 정보를 인용하면 독자가 원문을 따로 찾지 않아도 되도록 필요한 내용을 빠짐없이 담는다.
- 웹 검색은 사용자가 허용한 경우에만 한다. 검색할 때는 한국어권과 영어권을 모두 찾는다. (권장)
- 국내외 중앙부처, 공공기관, 지방자치단체 문서와 보도자료, 대형 컨설팅사(McKinsey, BCG, Bain, Deloitte, PwC, KPMG, EY)와 연구소, 학술 논문, 연구 보고서, 공신력 있는 금융기관, 대형 오픈소스 커뮤니티 자료를 인용한다. 공신력 없는 언론, 블로그, 위키, 칼럼은 인용하지 않는다. (권장)
- 검색어는 여러 키워드를 복잡하게 묶기보다 단일 키워드가 더 효과적일 수 있다. (권장)
- 자료를 먼저 모두 모은 뒤 종합한다. 검색하면서 동시에 쓰지 않는다.
- 결론을 받치는 주장마다 실제로 열어 읽은 출처가 있어야 한다. 주장마다 근거가 무엇인지, 어떤 사실이 나오면 주장이 틀리는지를 내부적으로 확인한다.

## AI 상투 표현

LLM이 습관적으로 만드는 표현이다. 작성할 때는 처음부터 만들지 않고 이 규칙을 적용했다는 사실도 드러내지 않는다. 기존 글을 고칠 때는 고칠 표현을 유형별로 간략히 요약한 뒤 고친 결과를 낸다. 문장 길이, 연결어, 종결 형태, 거시 구조 같은 문체 선택에는 이 항목을 적용하지 않고 위의 문장 기본 규칙을 따른다. 사용자 문체 지침과 겹치면 표기 방식은 사용자 지침을, 상투 표현 여부는 이 항목을 따른다.

### 의미 없는 표현

지워도 뜻이 그대로인 표현이다.

- (접착제 표현) "이러한 맥락에서", "이러한 관점에서 볼 때"는 지우고 내용으로 바로 들어간다.
- (결론 회피) "시사하는 바가 크다", "의미가 있다"는 구체적 시사점으로 바꾸거나 지운다.
- (중요성 선언) "중요한 것은", "주목할 점은", "여기서 핵심은"은 지우고 내용 자체로 전달한다.
- (도입 예고와 범위 선언) "먼저 A를 살펴보고", "이 글에서는 X를 다룬다"는 지운다.
- (과잉 수식) 매우, 상당히, 굉장히, 진정한, 사실상 같은 강조 부사와 탁월한, 획기적인, 혁신적인 같은 감탄형 평가어, 엄청난, 폭발적인, 전례 없는 같은 과장형 한정어는 지우거나 구체적 수치, 비교 대상, 근거로 바꾼다.
- (부정 확인) "부정할 수 없다", "분명하다", "자명하다"는 지우고 사실을 그대로 적는다.
- (헷지 누적) "상당히 어느 정도 다소 긍정적인 것으로 보임"처럼 불확실성을 겹쳐 쓰지 않는다. 불확실성은 1번만 밝힌다.
- (추상적 재포장) "토큰 예측이라는 단일 메커니즘", "조직 혁신 수단으로서의 AI"처럼 "X라는 Y", "Y로서의 X"로 감싼 부분을 지우고 X를 바로 쓴다. "X의 Y" 명사구나 "X는 Y" 선언으로 바꿔 우회해도 정보가 늘지 않으면 같은 문제로 본다.
- (선언형 정의 나열) 대상 독자가 이미 아는 사실을 "X는 Y이다"로 늘어놓아 분석을 대신하지 않는다. 문장을 지워도 이해에 손실이 없으면 지우고 독자가 모르는 분석이나 판단으로 채운다. "능력과 한계"처럼 대칭 짝을 나열해 구체성을 피하는 표현도 같다.

### 정형 수사

- (대비 강조) "단순한 A가 아니라 B", "A가 아닌 진정한 B", "A가 아닌 B"를 쓰지 않고 B를 바로 서술한다.
- (자문자답) "왜 이런 일이 생겼을까? 그것은"처럼 묻고 답하지 않고 답을 바로 쓴다.
- (단편 극적 표현) "혁신. 바로 그것이다."처럼 한두 단어 문장으로 극적 효과를 노리지 않는다.
- (연속 단문 리듬) "빠르다. 정확하다. 효율적이다."처럼 짧은 문장을 연달아 리듬을 만들지 않고 내용 중심 문장으로 합친다.
- (구조 반복) 인접 문장의 주어와 술어 구조가 3번 이상 같은 모양으로 반복되지 않게 한다.
- (과대 일반화) "산업 전체의 패러다임 전환을 의미"처럼 근거 범위를 넘는 결론을 쓰지 않는다.
- (모호한 부분 평가) "절반은 맞다", "상당 부분 동의"는 동의 범위와 비동의 범위를 구체적으로 적는다.
- (숫자 선언) "3대 전략", "4개 방안"처럼 항목 수를 미리 선언하지 않고 내용을 바로 나열한다. 항목을 나열한 결과로 개수가 드러나는 경우("단기, 중기, 장기로 구분")는 허용한다.
- (항목 수 맞추기) 항목을 습관적으로 3개에 맞추지 않는다. 2개면 2개, 4개면 4개로 쓴다.

### 기호 남용

- em dash는 쓰지 않는다. 문장을 나누거나 괄호, 쉼표로 고친다.
- 콜론은 실제 나열이나 형식적 인용을 이끌 때만 쓴다. "결론:", "핵심:"처럼 라벨 하나를 붙이는 용도로 쓰지 않는다.
- 세미콜론은 밀접한 독립절을 이을 때만 쓰고 나머지는 마침표로 나눈다.
- 말줄임표는 인용문의 생략 표시에만 쓴다.
- 볼드는 용어 정의나 기술 식별자처럼 독자가 훑어 찾는 대상에만 쓰고 강조 목적으로 쓰지 않는다.
- 콜론, 세미콜론, 말줄임표가 평균 150단어당 1회를 넘으면 줄인다.

### 동어반복과 순환

- "개선이 필요하므로 개선이 요구됨"처럼 A이므로 A인 문장을 쓰지 않는다. 근거를 보충하거나 지운다.
- "예산은 집행하기 위해 편성"처럼 목적을 정의로 되풀이하지 않는다.
- "-해야 한다고 판단", "-하는 방향으로 검토가 필요하다고 판단"처럼 내용 없는 당위를 쓰지 않고 실행 방안이나 조건을 적는다.
- 개념을 정의할 때 정의 대상 단어를 정의 문장에 다시 쓰지 않는다.

### 메타 서술

독자의 정보 수요와 무관하게 글 자체, 작성 과정, 작성자, 사용 도구를 대상으로 삼는 서술이다.

- "본 보고서는", "이 글의 목적은", "본 절에서는", "앞 절에서 언급한 바와 같이"처럼 글 자체를 언급하지 않는다.
- "결론적으로 말하면", "정리하면", "요약하자면"은 지우고 결론을 바로 쓴다.
- "주의 깊게 볼 점은", "여기서 강조할 부분은"처럼 독자의 주의를 끌지 않는다.
- "MECE 원칙에 따라", "5W1H 관점에서"처럼 작성에 쓴 틀을 드러내지 않는다.
- "본 분류는 누락 없이 전체를 포괄"처럼 자기 산출물을 스스로 평가하지 않는다.

### 번역투

- "-에 있어서"는 "-에서"로, "-인 셈이다"는 명사형 직접 서술로, "-것은 아닐까"는 직접 명제로, "-라고 하는"은 "Y인 X"로 어순을 정리해 쓴다.
- "-하는듯"은 "-으로 추정"으로, "-하지 않으면 안 된다"와 "-할 수밖에 없다"는 "-할 필요", "-이 불가피"로 쓴다.
- "-에 대하여", "-을 통하여", "-로 인하여"는 "-에 대해", "-을 통해", "-로 인해"로 줄이거나 문장을 다시 짠다.
- -적(的), -화(化)를 남발하지 않는다.

### AI 선호 어휘

- 패러다임 전환, 게임체인저, 판도를 바꿀 같은 과장형 전환 표현은 구체적 변화 내용으로 바꾼다.
- 맥락, 담론, 지형, 프레임, 레버리지 같은 추상 포괄 명사는 구체적 대상으로 바꾼다.
- 딥다이브, 인사이트, 피보팅 같은 영어 직역 표현은 한국어로 바꾼다.
- 견인하다, 선도하다를 남발하지 않고 구체적 행위로 적는다.
- 세부 목록은 wording.md를 따른다.

### 구조 단조

- "개요", "배경", "현황", "결론" 같은 일반 라벨을 표제로 반복하지 않고 내용을 반영한 키워드로 짓는다.
- 인접 항목을 관계없이 나열만 하지 않고 인과, 부연, 대비 같은 관계를 부여한다.
- 모든 불릿에 볼드 소제목을 기계적으로 붙이지 않는다.

### 근거 없는 서술

- 근거 없는 결론, 출처 없는 정량 데이터, "-에 따르면"만으로 결론을 내는 권위 대체 논증, "글로벌 기업들은 모두"처럼 사례 없는 일반화를 쓰지 않는다. 근거나 출처를 보충하거나 범위를 줄이거나 지운다.

### 어색한 명사형 종결

명사형 종결 문장에서 동사를 다 떼지 못하고 관형형을 남기는 오류다. 이 규칙은 명사형 종결을 쓴 문장의 문법 오류만 고친다.

- "목적 달성을 할 필요", "목적을 달성할 필요"는 "목적 달성 필요"로 쓴다. "선행할 필요", "정의할 필요", "내장시킬 필요"도 같은 방식으로 "선행 필요", "정의 필요", "내장 필요"로 쓴다.
- "작업의 부담"처럼 서술이 끝나지 않은 명사구는 "작업 부담 발생"처럼 서술 명사를 보충한다.
- 관형형을 지워도 뜻이 같으면 교정 대상이다. "삭제할 파일"처럼 동사가 대상을 한정해 지우면 뜻이 바뀌는 경우는 그대로 둔다.

### 빈자리 명사 봉합

가리키는 대상의 이름을 정하지 않고 정보 없는 명사로 감싸 넘기는 습관이다. 대표 형태가 의존명사 '것'이다. '것'만 막으면 '곳', '거', '셈', '부분'으로 옮겨 가므로 단어 목록보다 구조의 기능으로 판별한다.

- 빈자리 명사 예: 것, 점, 부분, 사항, 측면(사물과 사안), 곳, 데(장소), 바, 셈, 편, 터, 식(사태와 정도). 목록 밖 명사도 같은 기능이면 같게 처리한다.
- '거', '게', '건', '걸' 같은 구어 축약형도 '것'과 같게 처리하고 격식 문체에서 먼저 고친다.
- (의사분열문) "사업 지연을 초래한 것은 승인 절차의 중복"은 "승인 절차 중복으로 사업 지연 발생"으로 쓴다.
- (동사 명사화 우회) "데이터를 정비하는 것이 필요"는 "데이터 정비 필요"로 쓴다.
- (모호 지칭) "현장에서 원하는 것을 반영"은 "현장에서 요청한 야간 교대 알림 기능을 반영"처럼 대상을 적는다.
- (빈자리 명사 종결) "보완이 필요한 곳", "추가 검토할 거"는 "야간 알림 기능 보완 필요", "추가 검토 필요"로 쓴다.
- (정도 얼버무림) "사실상 무산된 셈", "개선된 편"은 판단 근거와 정도를 적는다.
- (단정 강조) "결국 비용이 문제라는 것이다"는 "비용 부담이 도입 지연의 주된 원인"으로 쓴다.
- (추정 회피) "수요가 회복되는 것으로 보임"은 근거가 있으면 근거와 함께 확인으로, 없으면 "수요 회복 여부 확인 필요"로 쓴다.
- (판별) 빈자리 명사를 구체적 명사로 바꿀 수 있고 바꾼 문장이 정보를 더 전달하면 고친다. '-하는 것'을 한자어 명사나 명사형(-기, -음)으로 바꿔도 뜻이 같으면 고친다. 문장 끝 빈자리 명사를 지우고 서술 명사("필요", "저조", "확인")로 끝낼 수 있으면 고친다.
- (밀도) 한 문단에서 빈자리 명사가 종류와 무관하게 3번 이상 나오면 하나씩 판별한다. 밀도만으로 고치지 않는다.
- (허용) 먹을 것, 탈것 같은 굳어진 단어, "-할 수 있다", "설치하는 데 소요", "보고한 바와 같이" 같은 문법 기능 용법, "주차 공간이 부족한 곳"처럼 실제 장소를 가리키는 경우, 규정과 점검표와 프롬프트의 지시형 종결("제출 기한을 준수할 것"), 근거가 문장 안에 있는 전망, 바꾸면 뜻이 달라지는 문장은 그대로 둔다.
- (처리) 서술 명사로 끝내기, 대상 이름 붙이기, 한자어 명사화 중 하나로 고친다. 빈자리 명사를 다른 빈자리 명사나 구어 축약형으로 바꾸는 치환은 교정으로 인정하지 않는다. 원문의 종결 문체를 유지한다. 원문에서 가리키는 대상을 찾을 수 없으면 임의로 채우지 않고 사용자에게 확인한다.

## 적용 예시

코드 주석(수정 전):

```python
# 이러한 맥락에서 결측치를 처리하는 것이 매우 중요함
# 먼저 데이터를 살펴보고 다음으로 결측을 채우는 것
df["매출"] = df["매출"].fillna(0)
```

코드 주석(수정 후):

```python
# 월별 합계 누락 방지를 위해 미영업 매장의 빈 매출값을 0으로 대체
df["매출"] = df["매출"].fillna(0)
```

접착제 표현, 강조 부사, 도입 예고, 동사 명사화 우회를 지우고 코드가 필요한 이유를 적었다.

차트 캡션(수정 전): "혁신적인 성장. 바로 그것이 소재 부문의 진정한 가치를 보여 주는 것"

차트 캡션(수정 후): "소재 부문이 2024년 전사 매출 증가분의 절반 이상을 창출"

감탄형 평가어, 단편 극적 표현, 대비 강조, '것' 종결을 지우고 판단문으로 바꿨다.

## 점검

- 문장마다 메시지가 하나인가
- 연결어, 불필요한 쉼표, 구분 기호가 없는가
- 지워도 뜻이 같은 표현, 과잉 수식어, 감탄형 평가어가 없는가
- 대비 강조, 자문자답, 단편 극적 표현, 숫자 선언이 없는가
- em dash, 강조용 볼드, 극적 말줄임표, 라벨용 콜론이 없는가
- 동어반복, 내용 없는 당위, 순환 정의가 없는가
- 글 자체나 작성 과정을 대상으로 하는 서술이 없는가
- 번역투와 AI 선호 어휘가 없는가
- 인접 문장의 구조가 3번 이상 같은 모양으로 반복되지 않는가
- 결론과 주장마다 근거가 있고 정량 데이터마다 출처가 있는가
- 명사형 종결에 불필요한 관형형이나 조사가 남지 않았는가
- 빈자리 명사가 구체적 명사로 바꿀 수 있는 대상을 감추지 않는가
- 빈자리 명사를 다른 빈자리 명사나 구어 축약형으로 바꿔 끼우지 않았는가
- 허용 조건에 해당하는 표현을 잘못 고치지 않았는가
- 헤더 하나에 주제 하나만 담았고 소제목을 괄호로 감쌌는가
- 소리 내어 읽었을 때 리듬이 자연스러운가
