# 분류와 계층 설계

분류, 그룹핑, 구조화, 판단이 들어가는 모든 사고에 적용하는 규칙이다. 함수 분리, 조건 분기, 예외 분류, 열거형 설계, 클래스 상속, 데이터 모델, 차트 범주, 화면 분할, 목차, 문장 속 나열이 모두 대상이다. 온톨로지 설계 원칙을 사고 규율로 옮겨 쓰며 OWL 모델 구축이나 추론기 실행은 다루지 않는다.

## 원칙

| 원칙 | 원래 정의 | 사고에 적용하는 방식 |
|------|-----------|---------------------|
| 상호배제 | 분류 항목 사이의 교집합이 공집합 | 한 사례가 두 항목에 동시에 들어가면 분류 기준을 다시 설계 |
| 전체포괄 | 분류 항목의 합집합이 논의 대상 전체를 덮음 | 어느 항목에도 들어가지 않는 사례가 있으면 분류가 불완전 |
| 단일 분류 기준 | 하나의 분류 체계는 한 차원의 기준으로 구성 | 차원이 다른 항목을 한 분류에 섞지 않음 |
| 일종 관계(is-a) | 하위 개념이 상위 개념의 모든 속성을 물려받음 | "X는 Y의 일종인가"를 통과해야 상하위로 배치 |
| 부분 관계(part-of) | 부분은 전체를 구성하는 요소 | "X는 Y의 일종인가"와 "X는 Y의 부분인가"를 구분 |
| 배타 범주 선언 | 동시에 해당할 수 없는 유형을 명시 | 함께 성립할 수 없는 범주 쌍을 찾아 겹침 여부 점검 |
| 열린 세계 가정 | 적히지 않은 사실은 미지로 취급 | 정보가 없다는 사실을 부정의 근거로 쓰지 않음 |
| 닫힌 세계 전환 조건 | 열거가 끝난 집합에만 닫힌 세계 적용 | 전수 조사가 끝난 범위에서만 "없음"을 단정 |
| 도구 편향 배제 | 도구에 맞춰 현실을 재단하지 않음 | 분석 방법이나 출력 형식에 맞춰 분류를 왜곡하지 않음 |
| 연결 그래프 | 모든 개체가 최소 1개 관계로 연결 | 고립된 항목은 관계를 찾거나 소속을 다시 검토 |
| 사용 어휘 | 정의한 개념은 최소 1번 사용 | 사례가 없는 분류 항목은 삭제 대상 |
| 비순환 정의 | 정의문에 정의 대상 자체가 들어가지 않음 | 정의할 때 정의 대상 단어를 정의 문장에 다시 쓰지 않음 |
| 누적 연결 | 확장할 때 새 개체를 기존 개체와 관계로 연결 | 새 분류 항목을 넣을 때 기존 항목과의 관계를 명시 |
| 역량 질문 | 구축 전에 구조가 답해야 할 질문을 수집 | 분류 전에 "이 분류로 어떤 판단을 내릴 수 있는가"를 먼저 확인 |

## 적용 방식

- 이 원칙은 추론 과정 안에서 작동한다. 산출물에는 분류 결과만 보이고 원칙 이름이나 적용 사실은 드러내지 않는다.
- 사용자가 분석 대상의 분류 구조를 검토해 달라고 하면 그 검토는 그대로 수행한다.
- 자기 분류가 원칙을 충족한다고 스스로 평가하는 문장을 쓰지 않는다.

## 분류 규칙

### 분류 기준 하나로

- 한 분류 체계 안의 분류 기준은 한 차원으로 통일한다. "기술별, 산업별, 시급성별" 항목을 같은 계층에 섞지 않는다. 1차 분류를 "기술별"로 통일한 뒤 2차 분류에서 "산업별"로 나눈다.
- 분류 기준이 복합적이면 기준을 분리해 여러 단계로 분류한다.
- 분류 기준이 불명확하면 분류하기 전에 기준을 먼저 정한다.

### 겹침 점검

- 한 사례가 두 항목에 동시에 들어가는지 반례를 찾아 점검한다.
- 교집합이 생기면 항목 경계를 다시 정하거나 상위 범주로 합친다.
- 교집합을 피할 수 없으면 여러 곳에 속할 수 있는 태그 방식으로 바꾸고 이것이 속성 부여라고 밝힌다.

### 누락 점검

- 어느 항목에도 들어가지 않는 사례가 있으면 분류가 불완전하다. "이 분류에 들어가지 않는 사례가 있는가"를 스스로 묻는다.
- 남는 항목을 "기타"로 처리하면 기타의 비중은 주요 항목보다 작아야 한다. 기타가 지나치게 크면 분류 기준 자체를 다시 설계한다.

### 항목 수

- 의사결정과 소통을 위한 분류는 같은 계층에 3-4개를 권장한다.
- 5개를 넘으면 중간 계층이 빠졌는지 점검하고 묶을 수 있는지 검토한다.
- 2개면 이분법이 타당한지 따로 확인한다(거짓 딜레마 여부).
- 생물 분류, 산업분류코드, 법률 조항 체계처럼 같은 계층이 5개를 넘기 쉬운 체계는 구조 결함으로 보지 않는다.

### 분류 전 질문

- 이 분류로 어떤 판단을 내리려 하는가
- 이 분류의 대상 범위는 어디까지인가
- 분류 기준이 한 차원인가
- 범위 안의 모든 사례를 빠짐없이 배치할 수 있는가

### 순환 정의 막기

- 정의 문장에서 정의 대상 단어를 지웠을 때 정의가 성립하지 않으면 순환 정의다. 동의어나 파생어로 돌려 쓰는 경우도 같다.
- "디지털 전환이란 디지털 기술을 활용해 전환하는 활동"은 순환 정의다. "기존 업무 프로세스를 소프트웨어 중심으로 재설계해 운영 효율을 높이는 활동"처럼 정의 대상 단어 없이 속성과 행위로 쓴다.
- 정의가 순환하면 상위 개념, 구성 요소, 목적, 속성 중 하나 이상을 써서 다시 정의한다.

## 계층 규칙

- (일종 관계) "전기차는 자동차의 일종이다"처럼 상위 개념의 속성(이동 수단, 바퀴 보유)이 하위 개념에서도 성립해야 상하위로 배치한다. "배터리는 전기차의 일종이다"는 성립하지 않는다. 배터리는 전기차의 부품이다.
- 일종 관계가 성립하지 않는 항목을 일종 관계로 배치하면 속성 상속 오류가 이어서 생긴다.
- (부분 관계) 전략과제는 전략을 구성하는 부분이므로 전략의 하위 분류로 두지 않는다. 구성 요소를 하위 분류로 잘못 두면 속성 상속 오류가 생긴다. 목차에서도 하위 항목이 상위 항목의 일종인지 부분인지 구분한다.
- (속성 관계) "프로젝트는 예산을 가진다"에서 예산은 프로젝트가 가진 속성이다. 속성을 하위 분류로 두지 않는다.
- 코드에서는 일종 관계를 상속으로, 부분 관계와 속성 관계를 구성(composition)이나 필드로 옮긴다.
- 실용적인 계층 깊이는 3단계 이내를 권장한다. 4단계 이상이면 중간 계층이 필요한지 다시 본다. 생물 분류나 행정구역처럼 깊은 계층이 자연스러운 체계는 결함으로 보지 않는다.

## 판단 규칙

- (정보 부재) "확인되지 않음"과 "존재하지 않음"을 구분한다. "ESG 보고서가 검색되지 않았으므로 ESG 활동을 하지 않는다"고 쓰지 않고 "ESG 보고서가 확인되지 않아 ESG 활동 여부는 미확인"으로 쓴다.
- (없음 단정) 열거할 수 있는 유한 집합을 모두 조사한 경우에만 부재를 단정하고 조사 범위와 완전성 근거를 함께 적는다. 열거가 불완전하면 미지로 둔다.
- (도구 편향) "차트로 그리기 편하다", "이 틀에 넣으려면 이렇게 나눠야 한다"는 분류 기준이 되지 못한다. 현실의 구조를 먼저 파악한 뒤 표현 방식을 정한다.
- (고립 항목) 다른 항목과 관계가 없는 항목은 소속을 다시 본다. 고립이 정당하면 신규 영역, 예외처럼 사유를 확인한다. 구조도에서 연결선이 없는 항목은 관계가 누락되었거나 그 구조에 속하지 않는 항목이다.
- (빈 범주) 정의만 하고 사례가 없는 범주는 지운다. 앞으로 채워질 가능성이 있으면 근거를 적는다. 빈 범주는 분류 기준이 부적절하다는 신호일 수 있다.
- (누적 연결) 기존 분류에 새 항목을 넣을 때 기존 항목과의 관계(상위, 하위, 병렬, 의존, 선후)를 밝힌다. 새 항목이 기존 항목의 경계를 바꾸는지 점검한다. 새 항목 때문에 겹침이 생기면 분류 기준을 다시 설계한다.

## 관계 규칙

- (방향) "A가 B에 영향을 준다"와 "B가 A에 영향을 준다"는 다른 관계다. 양방향이면 방향마다 근거를 따로 댄다.
- (유형) 인과(A가 일어나 B가 일어남, 시간 선후와 작동 방식 확인), 상관(A와 B가 함께 변함, 인과로 단정하지 않음), 의존(A가 없으면 B가 존재할 수 없음, 의존 방향 확인), 연관(A와 B가 관련됨, 관련의 구체적 성격 명시)을 구분한다. "관련이 있다"로 뭉뚱그리지 않는다.
- (수량 제약) 1:1, 1:N, N:M 중 무엇인지, 필수 관계인지 선택 관계인지 밝히고 현실과 맞는지 반례로 확인한다.

## 적용 예시

차트 범주(수정 전): 정보화 사업 문제점 차트에 "예산 편성 비효율, 전문 인력 부족, 부서 간 칸막이, 레거시 시스템 노후화, 정보보호 미흡, 성과 평가 체계 부재, 벤더 종속" 7개 막대를 나란히 그렸다. 자원, 조직, 기술 차원이 한 계층에 섞였다.

차트 범주(수정 후): 기준을 "문제가 생기는 영역"으로 통일해 자원 배분(예산 편성, 인력), 기술 기반(노후화, 정보보호, 벤더 종속), 조직 운영(부서 간 칸막이, 성과 평가)의 3개 범주로 묶는다.

데이터 모델(수정 전): `SmartCity` 클래스 아래 `Transport`, `Energy`, `Safety`, `IntegratedPlatform`, `IoTSensorNetwork`, `CitizenGovernance`를 모두 하위 클래스로 두었다.

데이터 모델(수정 후): 교통, 에너지, 안전은 서비스의 일종이므로 `Service`의 하위 클래스로 둔다. 통합 플랫폼과 센서 네트워크는 도시를 구성하는 부분이므로 `SmartCity`의 구성 필드로 둔다. 시민 참여 거버넌스는 도시가 가진 운영 체계이므로 속성 필드로 둔다.

열거형 확장(수정 전): `Term = {SHORT, MID, LONG}`에 `URGENT`를 추가했다. 긴급도는 기간과 다른 차원이라 한 열거형 안에서 겹침이 생긴다.

열거형 확장(수정 후): `Priority = {URGENT, NORMAL}`을 별도 열거형으로 만들고 과제 데이터에 기간과 우선순위를 각각 필드로 둔다.

## 점검

- 분류 기준이 한 차원으로 통일되었는가
- 분류 항목 사이에 교집합이 없는가(반례 탐색)
- 분류 항목의 합이 논의 대상 전체를 덮는가(누락 탐색)
- 같은 계층 항목이 5개를 넘으면 중간 계층을 점검했는가
- 상하위 관계가 일종 관계인지 부분 관계인지 구분되었는가
- 일종 관계에서 상위 속성이 하위에서도 성립하는가
- 정보 부재를 부정의 근거로 쓰지 않았는가
- 분석 도구나 출력 형식에 맞춰 분류를 왜곡하지 않았는가
- 다른 항목과 관계없는 고립 항목이 없는가
- 사례가 없는 빈 범주가 없는가
- 관계의 방향과 유형이 특정되었는가
- "기타"의 비중이 주요 항목보다 작은가
- 정의 대상 단어가 정의 문장에 다시 나오지 않는가
- 새 항목을 기존 항목과 관계로 연결했는가

## 예외

- 사용자가 분류 기준을 지정하면 그 기준을 먼저 적용하고 구조 결함을 발견하면 알린다.
- 항목 수와 계층 깊이의 권장값은 문서 독자를 위한 기준이다. 코드는 도메인 명세가 정한 항목 수와 깊이를 따른다.
- 순위나 단순 목록 요청은 분류와 구분해 이 규칙을 강제하지 않는다.
