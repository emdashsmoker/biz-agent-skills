# 코드 작성

코드는 작성 시간보다 디버깅 시간이 길다. 그래서 읽고 고치기 쉬운 구조를 기본으로 삼는다. 원칙은 특정 언어에 묶이지 않으며 예시는 Python을 기준으로 적었다.

## 설계

- 클린 코드 원칙을 지키고 코드를 쉽고 단순하고 간결하게 쓴다.
- 함수 하나는 책임 하나만 맡는다.
- 설정값은 파일 상단이나 별도 설정 파일로 분리한다. 값을 코드 중간에 하드코딩하지 않는다.
- 모든 상수에 역할이 드러나는 이름을 붙여 매직 넘버를 없앤다.
- 변수와 함수 이름은 역할이 드러나게 짓는다.
- 모듈 사이 결합을 낮춰 모듈별로 따로 테스트할 수 있게 만든다.
- 널리 쓰이는 패키지를 보수적으로 고르고 불필요한 의존성을 늘리지 않는다.
- 한국어처럼 ASCII 밖의 문자를 다루는 경우 유니코드 호환성을 항상 고려한다. 파일 입출력의 인코딩을 명시하고 시각화에는 해당 문자를 담은 글꼴을 지정한다.
- 언어와 상황에 맞춰 디버깅하기 쉬운 구조로 설계한다.
- 모든 설계 결정에는 결론과 근거가 짝으로 있어야 한다. 기술을 고른 근거는 주석이나 README에 남기고 근거 없는 기술 선택을 하지 않는다.

## 구조 나누기

코드 구조도 겹침 없이 나누고 빠짐없이 덮는다. 분류 기준의 상세는 structure.md를 따른다.

- 함수를 나눌 때 각 함수가 맡는 영역이 겹치지 않고 합쳐서 전체를 덮게 한다.
- if-elif-else 분기는 모든 경우를 빠짐없이 처리하고 분기 기준은 한 차원으로 유지한다.
- 예상 가능한 예외는 유형별로 겹치지 않게 나눠 처리한다.
- 모듈 사이 책임 경계를 명확히 하고 같은 기능을 여러 곳에 두지 않는다.
- 상태값과 유형값은 열거형(Enum)으로 정의해 누락을 막는다.

## 주석과 기록

- 주석은 Why(이 코드가 필요한 이유)를 중심으로 쓴다.
- What(이 코드가 하는 일) 주석은 코드만 보고 알기 어려운 경우에 보충한다. (권장)
- How(구현 방식의 선택 근거) 주석은 대안이 있는 경우 선택 이유를 남긴다. (권장)
- 미완성이나 임시 처리 지점은 TODO, FIXME, HACK 표시로 남긴다. (권장)
- 커밋 메시지에는 변경의 이유와 범위를 서술한다.
- 주석, 커밋 메시지, 로그 문장은 text.md와 wording.md를 따른다.

## 작업 방식

- 코드를 쓰기 전에 관련된 코드 영역 전체를 읽는다.
- 테스트는 구현 전이나 구현과 함께 작성한다.
- 큰 변경은 변경 계획을 먼저 세운 뒤 실행한다.
- 검증은 테스트 실행으로 한다. 정상 경로와 오류 경로를 모두 실행한다.
- 파일 안의 문자열을 일괄 치환할 때는 단어 경계를 지정한다(예: `\bword\b`). 경계 없이 치환하면 `edge`를 바꾸다가 `Ledger` 같은 이웃 단어까지 깨진다. 치환 후에는 붙어 버리거나 깨진 합성어가 없는지 grep으로 확인한다.

## 실행 환경

환경 관리 규칙은 사용자의 컴퓨터(로컬 환경)에서 작업할 때 적용한다. 가상환경을 만들 수 없는 일회성 실행 환경에서는 그 환경이 허용하는 설치 방식을 따른다. 언어, 셸, 패키지 관리 도구는 사용자와 프로젝트가 이미 쓰는 도구를 따른다.

- 사용자가 언어를 지정하면 그 언어를 쓴다. 지정하지 않았으면 프로젝트가 이미 쓰는 언어를 따른다. 기존 코드가 없으면 작업에 맞는 언어를 제안하고 고른 이유를 밝힌다.
- 결과를 화면에 바로 렌더링하는 환경에서는 작업 특성에 따라 분석용 언어와 HTML, CSS, JavaScript 중 효과적인 쪽을 고른다. (권장)
- 셸 명령은 사용자의 운영체제와 프로젝트가 쓰는 셸(bash, zsh, PowerShell 등)의 문법으로 작성한다. 어느 셸인지 불명확하면 사용자에게 확인한다.
- 세션을 시작하면 기존 가상환경 목록을 조회하고 재사용할지 새로 만들지 사용자에게 묻는다.
- 기본(base) 환경이나 시스템 인터프리터를 건드리지 않고 프로젝트 전용 환경을 만든다.
- 패키지 관리 도구는 프로젝트가 이미 쓰는 도구(conda, venv와 pip, uv, Poetry 등)를 따르고 패키지는 프로젝트 전용 환경 안에서만 설치한다. 정해진 도구가 없으면 언어의 표준 도구(Python은 venv와 pip)를 쓰고 사용자에게 알린다.
- conda를 쓰는 경우 Anaconda의 defaults 채널은 일정 규모 이상의 조직에 유료 약관이 적용된다. 이 채널을 쓰려면 소속 조직에 약관이 적용되는지 먼저 확인한다. conda-forge 채널은 누구나 무료로 쓸 수 있다.
- 도구 실행 권한을 묻는 환경에서는 프로젝트를 시작할 때 프로젝트 폴더 범위의 일괄 권한(셸, 웹 도구, 패키지 관리 도구 등) 허용 여부를 사용자에게 묻는다.
- 전역 권한과 전역 설정은 바꾸지 않는다. 전역 변경이 필요하면 사용자 허락을 먼저 받는다.
- sudo, UAC 같은 권한 상승을 쓰지 않고 작업에 필요한 최소 권한만 쓴다.

## 보안

- API 키, 토큰, 비밀번호를 코드, 로그, 표준 출력에 노출하지 않는다.
- 자격 증명 파일(`.env`, `*.pem`, `*.key`, `*_secret*`, `.credentials.json`)을 읽거나 노출하지 않는다.
- 환경변수 전체를 출력하지 않는다. 개별 변수 확인은 허용한다.
- Git 커밋에 민감 정보가 들어가지 않게 하고 커밋 전에 다시 확인한다.
- `.gitignore`에 민감 파일 패턴이 들어 있는지 확인한다.
- 사용자 입력은 반드시 검증한다.
- 외부 입력을 셸 명령에 직접 넘기지 않아 명령어 주입을 막는다.
- 파라미터화된 쿼리로 SQL 주입을 막는다.
- 경로에 `..`가 들어가면 검증해 경로 조작을 막는다.
- 임시 파일은 작업이 끝나면 정리한다.
- 사용자의 명시적 요청이 없으면 `--force` 푸시를 하지 않는다.

## 다른 언어로 확장

위 원칙은 C, C++, Rust, Go 같은 시스템 언어와 보안, 인프라 작업에도 같이 적용한다. 언어마다 도구와 관용 구조가 다르므로 아래처럼 옮긴다.

- 설정 분리, 상수 이름, 단일 책임, 예외 유형 분리는 그 언어의 관용 구조(상수 선언, 설정 구조체, 결과 타입 등)로 구현한다.
- 포매터, 린터, 테스트 실행기는 그 언어의 표준 도구를 쓴다. (권장)

## 점검

- 하드코딩한 값을 설정으로 분리했는가
- 매직 넘버에 이름을 붙였는가
- 디버깅하기 쉬운 구조인가
- 함수가 책임 하나만 맡는가
- 요청 범위 밖의 코드를 바꾸지 않았는가
