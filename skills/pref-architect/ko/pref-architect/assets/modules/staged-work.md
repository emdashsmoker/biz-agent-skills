# staged-work

큰 작업에서 초반의 잘못된 가정이 끝에 가서야 드러나는 일을 막기 위한 절차다. 이 절차는 작업 방식을 정할 뿐 모델의 추론 능력 자체를 높이지는 않는다. 능력을 넘는 작업이면 그럴듯한 결과를 만들지 않고 한계를 사용자에게 알린다.

## 쓰지 않는 경우

접근 방법이 하나로 분명하고 한 번에 끝나는 작업에는 이 절차를 쓰지 않고 바로 처리한다. 단순한 작업에 단계를 세우면 답이 절차에 묻힌다. 이 절차는 한 번에 처리하면 무언가를 놓칠 가능성이 있는 작업에만 쓴다.

## 1. 단계 계획

작업을 시작하기 전에 전체 단계를 적는다. 단계마다 번호와 예상 산출물을 붙인다.

```
1단계 [이름], 예상 산출물 [내용]
2단계 [이름], 예상 산출물 [내용]
```

- 단계 하나는 확인할 수 있는 산출물 하나를 만든다. 확인할 산출물이 없는 단계는 다음 단계와 합친다.
- 진행 중에 알게 된 사실이 계획을 틀리게 만들면 계획을 고친다. 계획은 작업 중에 바뀔 수 있다.

## 2. 단계별 검증

단계마다 실패할 수 있는 확인 조건을 정한다. 확인 조건은 외부 산출물로 판정한다.

- 테스트를 실행하여 통과한다.
- 파일이나 출력이 예상한 형태로 실제 존재한다.
- 출처를 실제로 열어 읽었다.
- 산출물을 요청 명세와 비교했다.

"검토해 보니 맞아 보인다"는 확인 조건이 아니다. 검증을 건너뛰려는 모델은 자기 판단도 쉽게 통과시킨다. 실패할 수 있는 확인 조건이 없는 단계는 그 사실을 적고 산출물에 미검증이라고 표시한다. 그래야 다음 단계에서 빈틈이 보인다.

뒤 단계에서 고친 내용이 앞 단계의 산출물을 무효로 만들면 앞 단계의 확인을 다시 실행한 뒤 계속한다. 오류는 앞 단계에서 잡을수록 고치는 비용이 적다.

작업 종류별 확인 조건의 예는 아래와 같다.

| 작업 종류 | 진행 방식 | 확인 조건 |
|---|---|---|
| 소프트웨어 개발 | 관련 코드를 먼저 읽고 테스트를 구현과 함께 쓴다. 큰 변경은 변경 계획을 먼저 세운다 | 테스트가 실행되고 오류 경로까지 확인된다 |
| 조사와 지식 작업 | 출처를 모은 뒤 종합한다. 주장마다 근거와 반증 조건을 따진다. 확인된 사실과 추론을 구분하고 추론은 표시한다 | 결론을 받치는 주장이 모두 실제로 읽은 출처로 이어진다 |
| 데이터 분석 | 데이터 형태를 먼저 파악한다. 계산 전에 가설을 적는다. 결측, 중복, 이상치를 먼저 본다 | 데이터 품질 확인 코드가 실제 데이터에서 통과한다 |
| 여러 세션에 걸친 작업 | 결정, 이유, 실패한 시도를 작업 기록에 남긴다. 이어서 작업할 때 기록부터 읽는다. 완료 조건을 먼저 정한다 | 완료 조건이 글로 적혀 있고 확인할 수 있다 |

## 3. 전달 전 자기 검토

결과를 전달하기 전에 회의적인 검토자의 눈으로 다시 읽는다. 실제 약점을 찾으면 고치거나 사용자에게 알린다. 제대로 확인했는데 약점이 없으면 없다고 쓴다. 절차를 채우려고 약점을 만들어 내지 않는다.

문제를 알리기 전에 문제가 실제로 있는지 확인한다. 검색, 비교, 실행, 원문 대조로 확인한다. 증거를 못 찾았다는 이유만으로 경고를 내지 않는다. 확인하지 않은 경고는 없는 문제를 만들어 사용자의 시간을 쓴다.

## 운영 규칙

- (경고 누적) 진행 중에 멈출 정도는 아닌 작은 우려가 생기면 개수를 센다. 3개가 쌓이면 멈추고 모두 한꺼번에 사용자에게 알린 뒤 진행한다. 작은 우려가 같은 방향으로 쌓이면 하나의 큰 문제일 가능성이 높다.
- (안전한 일괄 치환) 파일에서 문자열을 일괄 치환할 때는 단어 경계를 지정한다. 경계 없이 치환하면 다른 단어의 일부까지 바뀐다. 치환 후에는 붙어 버리거나 깨진 단어가 없는지 검색으로 확인한다.
- (토큰 절약과 함께 쓸 때) token-lean이 함께 불러와져도 단계 계획과 검증 기록은 줄이지 않는다. 이 기록이 있어야 사용자가 작업을 추적할 수 있다.
