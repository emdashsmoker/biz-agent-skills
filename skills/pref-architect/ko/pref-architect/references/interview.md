# 인터뷰 문항

인터뷰의 목적은 상시 지침과 모듈 설정 절에 들어갈 값을 정하는 데 있다. 문항마다 기본값과 답이 바꾸는 위치를 적어 두었다. 답이 바꾸는 위치가 없는 문항은 묻지 않는다.

## 진행 방식

- 한 번에 최대 4문항을 묻는다. 묻는 수가 많으면 사용자가 답을 대충 고르게 된다.
- 문항마다 기본값을 보여 주고 기본값을 첫 번째 선택지로 둔다.
- A묶음(환경)은 항상 묻는다. B묶음의 첫 질문에서 "나머지 문항을 모두 기본값으로 진행" 선택지를 준다. 사용자가 이 선택지를 고르면 B묶음부터 F묶음까지 기본값으로 채운다.
- 기존 자산이 있으면 기존 자산에서 읽어 낸 값을 기본값 자리에 채우고 "기존 설정"이라고 표시한다.
- 앞선 답으로 필요 없어진 문항은 건너뛴다. 예를 들어 code-standard를 설치하지 않으면 E묶음을 묻지 않는다.
- 사용자가 선택지 밖의 답을 적으면 그 답을 그대로 설정값으로 쓴다. 답이 다른 설정과 충돌하면 충돌 내용을 알려 주고 다시 묻는다.
- 인터뷰 답은 대화 안에서 한 표로 모아 두고 설계안 승인 단계에서 그대로 보여 준다.

## A. 환경

| 번호 | 질문 | 선택지 | 기본값 | 답이 바꾸는 위치 |
|---|---|---|---|---|
| A1 | 상시 지침을 어디에 둘 예정인가 (복수 선택) | claude.ai 유저 프리퍼런스, Claude Code의 CLAUDE.md, AGENTS.md를 읽는 도구, 기타 | claude.ai 유저 프리퍼런스 | 상시 지침 개수와 서식 |
| A2 | 대상 환경에서 스킬을 쓸 수 있는가 | 쓸 수 있음, 쓸 수 없음, 모름 | 모름이면 모델이 확인 | 모듈 전달 방식 |
| A3 | 기존 상시 지침이나 스킬이 있는가 | 없음, 상시 지침만 있음, 상시 지침과 스킬 모두 있음 | 없음 | 통합 절차 실행 여부 |

A2에서 "모름"을 고르면 references/router.md의 환경별 배치 표를 기준으로 판단하고 판단 근거를 한 줄로 알린다.

## B. 작업과 독자

| 번호 | 질문 | 선택지 | 기본값 | 답이 바꾸는 위치 |
|---|---|---|---|---|
| B1 | 주로 하는 작업은 무엇인가 (복수 선택) | 보고서와 기획 문서 작성, 조사와 분석, 코딩과 자동화, 데이터 시각화와 디자인 | 보고서와 기획 문서 작성, 조사와 분석 | C묶음의 기본 선택 |
| B2 | 결과물을 주로 읽는 사람은 누구인가 | 해당 분야 입문 수준 실무자, 해당 분야 전문가, 일반 대중, 직접 입력 | 해당 분야 입문 수준 실무자 | write-standard의 (대상 독자) |
| B3 | 모델이 어떤 관점으로 답하기를 원하는가 | 경제, 경영, 행정 분야 경험이 많은 전략 컨설턴트, 해당 분야 실무 전문가, 따로 정하지 않음, 직접 입력 | 경제, 경영, 행정 분야 경험이 많은 전략 컨설턴트 | write-standard의 (작성자 관점) |
| B4 | 결과물은 어떤 언어로 받기를 원하는가 | 대화에 쓰는 언어, 한국어, 영어, 직접 입력 | 대화에 쓰는 언어 | write-standard와 code-standard의 (출력 언어) |
| B5 | 모델의 중간 추론과 작업 기록은 어떤 언어로 할까 | 영어, 출력 언어와 같게 | 영어 | write-standard와 code-standard의 (추론 언어) |

B5의 기본값이 영어인 이유는 토큰 비용이다. 같은 내용이라도 언어마다 토큰 수가 크게 다르며 영어가 대체로 가장 적다. 출력 언어가 영어이면 B5는 묻지 않는다.

## C. 모듈 선택

| 번호 | 질문 | 선택지 | 기본값 | 답이 바꾸는 위치 |
|---|---|---|---|---|
| C1 | 어떤 동봉 모듈을 설치할까 (복수 선택) | write-standard, code-standard, staged-work, token-lean | 모두 설치 | 생성할 모듈 목록과 상시 지침의 로드 규칙 |

선택지를 보여 줄 때 모듈마다 한 줄 설명을 붙인다.

- write-standard는 글의 문장, 구조, 근거, 어휘 기준을 담는다.
- code-standard는 코드 품질, 보안, 차트, 디자인 기준을 담는다.
- staged-work는 큰 작업을 단계로 나누고 단계마다 검증하는 절차를 담는다.
- token-lean은 불필요한 파일 로드, 재출력, 턴 반복을 줄이는 절차를 담는다.

B1에서 코딩이나 시각화를 고르지 않았다면 code-standard를 기본 선택에서 제외하고 이유를 알린다. 사용자가 원하면 다시 추가한다. 기존 스킬 중 같은 역할을 하는 스킬이 있으면 references/integration.md의 겹침 처리 절차를 따른다.

## D. write-standard 설정

| 번호 | 질문 | 선택지 | 기본값 | 답이 바꾸는 위치 |
|---|---|---|---|---|
| D1 | 문장은 어떻게 끝내기를 원하는가 | 개조식 명사형 종결(예: 도입 필요), 평서형 종결(예: 도입이 필요하다), 대화체 | 개조식 명사형 종결 | (문체) |
| D2 | 불릿은 몇 단계까지 쓸까 | 2단(주장은 '-', 근거는 들여쓴 '+'), 1단과 산문 조합 | 2단 | (불릿 단계) |
| D3 | 글 전체 구조는 어떤 틀을 기본으로 할까 | 목적에 맞게 WWH나 SCQA 중 선택, WWH 고정, SCQA 고정, 틀 없음 | 목적에 맞게 선택 | (글 구조) |
| D4 | 요청하지 않았을 때 웹 검색을 해도 되는가 | 요청할 때만 검색, 필요하면 검색 | 요청할 때만 검색 | (웹 검색) |
| D5 | 한 글에 쓰는 핵심 정량 데이터와 표의 상한은 | 각 3개, 각 5개, 제한 없음 | 각 3개 | (정량 데이터 상한), (표 상한) |
| D6 | 출력이 한국어일 때 한국어 어휘 목록을 적용할까 | 적용, 적용 안 함 | 적용 | (한국어 어휘 목록) |

D1은 출력이 한국어일 때 적용한다. D2의 1단을 고르면 write-standard 출력 서식에서 '+' 줄을 쓰지 않고 근거를 주장 문장 뒤의 산문으로 붙인다. D5 기본값 3은 핵심을 세 개 이내로 추려 전달하는 컨설팅 실무 관행(3의 법칙)에서 나온 값이다. 사람이 한 번에 붙잡아 두는 정보 묶음이 4개 안팎이라는 작업 기억 연구도 같은 방향을 가리킨다. 다만 숫자와 표의 상한 자체를 정한 연구는 없으므로 사용자가 바꿔도 된다.

## E. code-standard 설정

| 번호 | 질문 | 선택지 | 기본값 | 답이 바꾸는 위치 |
|---|---|---|---|---|
| E1 | 명령어를 실행할 셸은 무엇인가 | 환경이 제공하는 셸, bash나 zsh, PowerShell, 직접 입력 | 환경이 제공하는 셸 | (셸) |
| E2 | 프로젝트 환경은 무엇으로 분리하는가 | venv, conda, uv, 쓰지 않음, 직접 입력 | 이미 쓰는 도구가 있으면 그 도구, 없으면 venv | (환경 분리 도구) |
| E3 | 기본 프로그래밍 언어는 무엇인가 | 작업에 맞게 모델이 선택, Python 우선, JavaScript나 TypeScript 우선, 직접 입력 | 작업에 맞게 모델이 선택 | (기본 언어) |
| E4 | 차트와 디자인의 기본 색은 무엇인가 | 파스텔톤 네이비 블루 단일 계열(기본 #6B8EC2, 강조 #F5A962), 회사나 개인 색 직접 입력 | 파스텔톤 네이비 블루 단일 계열 | (기본 색), (강조 색) |
| E5 | 차트와 디자인의 기본 글꼴은 무엇인가 | 출력 언어를 지원하는 글꼴 중 모델이 선택, 직접 입력 | 한국어 출력이면 NanumGothic, 그 외에는 출력 언어를 지원하는 글꼴 | (글꼴) |

E2의 기본값은 이미 쓰는 도구를 우선한다. 사용 중인 도구를 바꾸게 하면 사용자의 다른 프로젝트 환경과 어긋나기 때문이다. E5의 NanumGothic은 SIL Open Font License 1.1로 배포되어 자유롭게 쓸 수 있다.

## F. 공통 작업 규칙

아래 규칙은 모듈과 상관없이 모든 대화에 적용되므로 상시 지침에 들어간다. 사용자가 켠 규칙만 추가한다.

| 번호 | 규칙 | 기본값 | 두는 이유 |
|---|---|---|---|
| F1 | 서브 에이전트는 실행 전에 사용자 승인을 받는다 | 켬 | 서브 에이전트는 결과 품질, 토큰 사용량, 작업 속도를 크게 바꾼다 |
| F2 | 요청하지 않은 파일을 만들기 전에 먼저 묻는다 | 켬 | 사용자가 결과물 범위를 관리할 수 있다 |
| F3 | 요청하지 않은 스킬을 불러오기 전에 먼저 묻고 비슷한 스킬이 있으면 대안으로 함께 제시한다. 상시 지침이 지정한 모듈은 묻지 않고 불러온다 | 켬 | 스킬마다 작업 방식이 달라 결과가 바뀐다 |
| F4 | 사용자 동의 없이 프로젝트 지식이나 지침 파일에 내용을 추가하지 않는다 | 켬 | 지침 파일은 이후 모든 대화에 영향을 준다 |
| F5 | 최종 산출 전에 요청의 요구사항과 제약을 모두 확인한다 | 켬 | 마지막 확인으로 누락을 줄인다 |
| F6 | 사용자가 요청하지 않은 역규칙, 역논리, 역설, 반례를 임의로 추가하지 않는다 | write-standard와 code-standard를 모두 설치하지 않을 때만 켬 | 두 표준 모듈 본문에 같은 규칙이 있어 모듈을 설치하면 상시 지침에 다시 둘 필요가 없다 |
| F7 | 스킬을 만들거나 고치면 설치 파일(.skill), SKILL.md, 부속 md를 모두 파일로 전달한다 | 파일 전달이 가능한 환경에서만 켬 | 사용자가 내용을 검토한 뒤 바로 설치할 수 있다 |
| F8 | 모듈과 관계없이 모든 출력에 적용할 짧은 선호(직접 입력) | 없음 | 사용자가 어떤 작업에서든 지키기를 원하는 선호를 담는다 |

F묶음은 표를 보여 주고 끌 규칙만 고르게 한다. 사용자가 F8이나 새 규칙을 적으면 먼저 설치할 모듈에 같은 규칙이 이미 있는지 본다. 이미 있으면 상시 지침에 다시 추가하지 않고 모듈에 있다고 알린다. 이어서 모든 대화에 필요한 규칙인지 본다. 특정 작업에만 필요한 규칙이면 해당 모듈의 본문에 두자고 제안한다.
