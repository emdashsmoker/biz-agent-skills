# 원인 렌즈

문제가 왜 생기는지 "왜"를 반복해 물어서 근본 원인까지 추적하고 해결 방향을 짝지어 낸다.

## 배경

도요타 생산 방식에서 쓰던 "5 WHY" 기법을 바탕으로 한다. 이 기법은 원인을 한 줄로만 따라가게 만들고 가장 깊은 원인이 가장 좋은 개입 지점이라고 가정하는 한계가 있다는 비판을 받는다(Card, 2017, BMJ Quality & Safety). 이 렌즈는 그 한계를 보완하려고 원인 가지를 기록하고 개입 지점을 효과로 고른다.

## 핵심 원리

- 증상과 원인을 나눈다. 증상은 문제가 생겼을 때 바로 보이는 현상이다. 증상만 없애는 대책은 일시적이다.
- 근본 원인은 그 원인을 없애면 문제가 구조적으로 다시 생기지 않는 지점이다.
- 각 "왜"의 답이 다음 "왜"의 대상이 된다. 표면 증상에서 구조 원인으로 한 단계씩 이동한다.
- "5"는 경험상 권장 횟수다. 3번으로 충분할 때도 있고 7번 이상 필요할 때도 있다. 횟수를 맞추려고 단계를 늘리거나 줄이지 않는다.
- 추적은 아래 기준 가운데 하나를 충족하면 멈춘다. 해당 원인을 없애면 문제가 다시 생기지 않는가. 더 물어도 의미 있는 답이 나오지 않거나 대상이 통제할 수 없는 영역으로 넘어가는가.
- 원인이 여러 갈래로 나뉘면 가지를 모두 기록한다. 가장 유력한 가지부터 끝까지 추적한다. 나머지 가지를 이어서 추적할지 사용자에게 묻는다.
- 개입 지점은 깊이로 고르지 않는다. 고쳤을 때 재발을 가장 크게 줄이고 대상이 실제로 바꿀 수 있는 지점을 고른다.

## 진단 절차

### 1. 입력 확인

입력은 아래 가운데 하나다. 사용자가 문제를 직접 서술한 경우, 기획안만 준 경우, 기획안과 분석할 문제를 함께 지정한 경우다. 아무 입력 없이 호출되면 분석할 문제나 기획안을 요청한다.

### 2. 문제 정의

출발점이 되는 문제를 정한다. 문제 정의가 흐리면 분석 전체가 방향을 잃는다.

- 사용자가 문제를 서술했으면 그 서술을 문제 정의로 쓴다.
- 기획안만 받았으면 추진 배경이나 현황 문제점 서술에서 핵심 문제를 뽑는다.
- 사용자가 따로 지정한 문제가 있으면 그 문제를 먼저 쓴다.

문제 정의는 세 요건을 갖춘다.

- 관찰할 수 있는 구체적 현상을 쓴다.
- 원인이나 해결책을 미리 담지 않는다.
- 문제 하나에 집중한다. 복합 문제는 나눠서 각각 분석한다.

정한 문제를 사용자에게 보여 주고 "이 문제를 출발점으로 원인을 추적한다"고 알려서 바로잡을 기회를 준다.

### 3. 답변 깊이 질문

사용자에게 대응 방안의 깊이를 묻는다.

- A: 해결 방향마다 핵심 1-2줄
- B: 해결 방향마다 현재 상태와 바뀐 상태를 비교하는 표

### 4. 원인 사슬 추적

- 각 답이 바로 앞 질문의 원인인지 단계마다 확인한다.
- 누가 잘못했는지 묻지 않는다. 어떤 절차나 구조가 문제를 허용했는지 묻는다.
- 개인의 실수가 답으로 나오면 그 실수를 허용한 조건을 한 번 더 묻는다.
- 각 답은 입력 자료에서 확인되는 사실로 쓴다. 자료에 없는 원인을 추측으로 채우지 않는다.
- 사슬을 다 만들면 근본 원인에서 문제 정의까지 "A라서 B가 생긴다"로 거꾸로 읽는다. 중간에 논리가 끊기면 그 단계를 다시 쓴다.

### 5. 출력

아래 순서로 쓴다.

분석 개요는 분석할 문제를 2-3문장으로 요약한다. 기획안이 함께 있으면 기획안의 핵심도 넣는다.

원인 사슬은 표로 쓴다. 해결 방향은 근본 원인 행에만 적는다.

| 단계 | 질문 | 답변 | 해결 방향 |
|---|---|---|---|
| 문제 정의 | - | (문제 정의) | - |
| 왜 1 | 왜 (문제 정의)인가 | (답변) | - |
| 왜 2 | 왜 (왜 1 답변)인가 | (답변) | - |
| ... | ... | ... | - |
| 근본 원인 | 왜 (직전 답변)인가 | (근본 원인) | (해결 방향) |

원인 가지가 여러 개였으면 표 아래에 추적하지 않은 가지를 한 줄씩 적는다.

근본 원인 진단에는 이 원인이 근본 원인이라고 보는 이유, 그리고 이 원인이 미치는 범위와 그대로 두었을 때 예상되는 결과를 쓴다.

대응 방안은 3단계에서 고른 깊이(A 또는 B)로 쓴다.

## 반영할 때

사용자가 "근본 원인 관점에서 써줘", "5 WHY 기준으로 이슈 뽑아줘"처럼 요청하면 요청한 산출물만 쓴다.

- 원인 사슬 표, "왜 1" 같은 단계 표기, 진단 섹션을 쓰지 않는다.
- 증상 수준의 서술을 피하고 각 이슈를 근본 원인 수준에서 정의한다.
- 개인 책임으로 돌리는 표현을 피하고 절차와 구조의 문제로 쓴다.

## 예시

문제 정의: 고객 문의 답변이 약속한 기한을 자주 넘긴다.

| 단계 | 답변 |
|---|---|
| 왜 1 | 문의 담당자가 기술 부서 확인을 기다리는 시간이 길다 |
| 왜 2 | 기술 부서가 문의 확인 요청을 우선순위 없이 받는다 |
| 왜 3 | 확인 요청이 개인 메신저로 오가서 요청 목록이 없다 |
| 근본 원인 | 부서 간 확인 요청을 접수하고 기한을 붙이는 절차가 없다 |

해결 방향은 부서 간 확인 요청을 한곳에서 접수하고 요청마다 응답 기한을 붙이는 절차를 만드는 일이다. "담당자가 늦게 확인했다"에서 멈추면 사람만 바뀌고 문제는 반복된다.

## 예외

- 사용자가 분석, 진단, 원인 도출을 요청하지 않았으면 원인 사슬 표나 진단 섹션을 임의로 내지 않는다.
- 웹 검색은 사용자가 요청한 경우에만 한다.
